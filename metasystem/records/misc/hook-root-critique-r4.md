## SHR-R4-DEADLINE-PARENT-01 — high, material=True

CLAIM: Revision 4 is not complete: the Stop-deadline parent remains a second, contradictory root and engine owner, so revision 5 is required before any build. The design promises that payload cwd is deleted from world resolution and that, in a mapped worktree, “every moving part of the turn names the primary” and “nothing in the turn reads or writes sandbox state.” Current code instead computes `deadline_repo=$(git -C "$deadline_cwd" rev-parse --show-toplevel ...)`, without the scrub, and sets both `deadline_validator` and `deadline_canonical` beneath the unmapped `deadline_harness_root`. In an engine-less delegate worktree, the revision-4 worker would reach the primary engine, but its parent could not validate the worker's ordinary JSON: the no-validator fallback accepts only the exact missing-engine block and otherwise replaces the answer with a generic block. On timeout, the parent either writes the refusal record under the cwd-derived worktree or wrapper root, or cannot invoke its absent canonical engine and emits the record-failure allow response. Revision 5 should preserve the previously certified worker-first deadline ordering, then make the parent resolve the same script-derived, scrubbed, mapped installation while the worker runs; select its canonical engine from that mapped installation; derive the refusal-record root through `path state-root <world_installation>`, never payload cwd; and add normal-completion and timeout fixtures for an engine-less worktree under Git steering and METASYSTEM_BIN. Until that is done, turn-verdict-hardening slice 1b is unsafe: it edits worker verdict responses whose parent can discard, replace, or record against another world.

## SHR-R4-UP-GIT-STEERING-01 — high, material=True

CLAIM: The Git-steering fold fixes the mapper but leaves the mapped turn steerable again inside `up`, invalidating the one-world claim. Revision 4 deliberately keeps Git variables in engine children and declares up's unsanitized census query out of scope because it “never” selects the state world. But `upRepositoryScope` runs `git -C <supplied> rev-parse --show-toplevel` with the inherited environment, and the resulting scope controls the census fingerprint, supervision owner scope, and owner tag. The read-only reproduction showed the round-three GIT_DIR/GIT_WORK_TREE steering changes this query from the primary wrapper to the delegate worktree. Revision 5 must either scrub upRepositoryScope with the compiled authority's same list or invoke this consumer under that scrub, and the steered-worktree fixture must assert the resulting census scope rather than merely tolerate an up failure.

## SHR-R4-COPIED-HOOK-OVERRIDE-01 — high, material=True

CLAIM: Revision 4 reopens round-two copied-hook provenance whenever METASYSTEM_BIN is set. It says a copied hook with no engine “stops benignly” and that the invocation pathname is only a candidate, but the normative executable check is `ms="${METASYSTEM_BIN:-$world_installation/bin/metasystem}"`; with an override it never requires an engine at the candidate. Revision 5 must require independent installation provenance under an override—such as the canonical engine's presence at the mapped installation—or explicitly reject that combination, and repeat copied-hook case 6 with METASYSTEM_BIN set.

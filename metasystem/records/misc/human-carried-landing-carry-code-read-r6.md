### HCL-C-83 (low)

Claim: The new lock test catches round 5's race in only about half of its runs. TestHCL79RegisterLockSurvivesRelease (metasystem/internal/counselor/counselor_test.go:546-611) starts sixteen goroutines that all append to one register. The register is seeded with 3000 lines, and over 100 iterations each writer alternates between an id every writer shares and an id of its own. At the end the test checks that no id appears twice. This is exactly the shape fold decision 1 asked for, and it does drive the race. But the race depends on timing, so if round 5's release order came back, the test would fail only some of the time rather than every run, and a reader could mistake that for a flaky test. Round 6's fix does not rely on this test for its correctness: the trace in mandate 2 shows the race is closed. What changes if it stands: nothing for this chain. If a steadier guard is wanted later, the test could repeat its body several times in one run to raise the odds of catching a regression.

Evidence: Ran the test in a scratch copy of the reviewed tree with round 5's register.go (from tree 70c7e1ba) put back. It failed in 6 of 11 runs, each time with one duplicated shared id (for example 'register id "repeated-060" appears 2 times' and 'register id "repeated-040" appears 2 times'), and passed in the other 5. On the round 6 code it passed 3 of 3 plain runs (about 4 to 6 seconds each), passed 1 of 1 under the Go race detector (29.9 seconds), and the whole counselor package passed (15.5 seconds). The scratch copies were removed afterwards.

### HCL-C-84 (low)

Claim: One error branch in the new lock-acquire loop deletes the lock file before it has checked that the file is the live one. In metasystem/internal/counselor/register.go:289-292, if reading the identity (inode) of the just-locked file fails, the code calls releaseRegisterLock, and that function's first step deletes the lock path (:310). The writer in this branch may hold a lock on an old lock file that has already been deleted, while a different writer holds the lock on the file the path now names and is inside the critical section, reading and appending the register. The delete would remove that live file, and a fourth writer could then create a new lock file and enter at the same time: the HCL-C-79 race again. The sibling branch (:298-300, where reading the path's identity fails) correctly unlocks and closes without deleting. To reach this branch, fstat must fail on a descriptor this process has just opened and locked, which in practice means a disk I/O error. The damage would be the same low-severity duplicated register line HCL-C-79 described. What changes if it stands: nothing now. The fix is one line: call unlockAndCloseRegisterLock at :291.

Evidence: Read register.go:279-331. releaseRegisterLock (:308-320) deletes the path, then unlocks, then closes. unlockAndCloseRegisterLock (:322-331) never deletes. The acquire loop uses the non-deleting helper everywhere except :291.

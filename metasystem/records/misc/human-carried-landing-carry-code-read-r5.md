## Findings

### HCL-C-79 (low, material)

Claim: Removing the counselor lock file on release breaks the lock, so two writers can be inside it at once. The change introduced this. In metasystem/internal/counselor/register.go:251-261, appendRegisterLine unlocks, closes, and only then deletes <register>.lock. The lock is an flock on whatever file is open, so here is how it fails. Writer B has already opened the old lock file and is waiting. Writer A unlocks, and B gets the lock on the old file. A then deletes the path. Writer C arrives, finds no file, creates a new one, and locks it straight away. B and C now both scan the register, and neither sees the id the other is about to write, so both append it. The error path at register.go:246-249 also deletes a path that another writer may still be holding. Every counselor register uses this one function: the carried-landings register (:118, called from the goal carried hook at :197-203), the accepted-risk register (:128 human-carried, :226 critic chains) and the misclassification register (:233). The design relies on 'appendRegisterLine is idempotent by id' (design lines 1147, 1198, 1433), and that guarantee no longer holds under contention. The effect is a duplicated id on an append-only register. The counselor sitting then drops every copy of a duplicated accepted-risk id and reports only a limitation (metasystem/internal/counselor/sources.go:254-275), so a paid debt vanishes from its view. The carried landing admission accepts identical duplicates (HCL-C-78), so landings are not blocked. It takes three writers on the same register within one append, which is rare in a single checkout, hence low severity. What changes if it stands: keep fold decision 3's removal, but make it safe. Delete the lock file while still holding the lock. After taking the lock, compare the open file with what the path names now (fstat against stat), and if the path is missing or names another file, close and retry. The .gitignore rule stays as the safety net for a crashed writer.

Evidence: Ran a scratch test (not in the repository) in extracted copies of the round 5 tree (70c7e1ba) and the round 3 tree (17a09a326). Sixteen goroutines appended to one register seeded with 5000 lines. Each of 100 iterations mixed three unique ids with four appends of the same id. Separate os.OpenFile calls get separate open file descriptions, so goroutines compete for flock the way separate processes do. Round 5 put the same id on two lines in 2 of 3 runs, 3 duplicated ids each time ('two writers were inside the register lock at once: 3 duplicated ids'); the third run had none. Round 3 had 0 duplicated ids in 3 of 3 runs. That control shows the test detects exactly the removal. Read register.go:236-288 and sources.go:254-275.

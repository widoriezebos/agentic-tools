## LRF-01 — low, material=False

CLAIM: The advance verb does not refuse an untracked file, although the design page's step D says every status record with a non-blank index column refuses with the code that means the index is not empty, and an untracked record's index column is a question mark rather than a blank. The code implements the design's evident intent (catch staged entries) rather than its letter, and I judge the code right and the sentence loose: the same design's drift rules put untracked files in their own category ahead of the staged rule, so treating them as a separate case is consistent with the rest of the page.

EVIDENCE: In advance.go the sweep at lines 110-114 skips a record whose two status columns are both question marks. I traced every untracked outcome from there. If the rebased commit would add that path, the record still lands in the overlap set at line 130, is not a declared register, and refuses with the unstaged-drift code at lines 178-182. If the rebased commit would not add it, git's reset --keep leaves untracked files alone, which is also what the plain 'git rebase' this verb replaces did, so the exemption preserves rather than widens the old behaviour. In the only production caller, land.sh, the post-commit cleanliness step already refuses untracked paths before the advance step runs. No path lets a branch move that should not have moved.

## LRF-02 — low, material=False

CLAIM: The advance verb has no interrupt handling around its private worktree, so a signal during the rebase leaves a registered linked worktree and its temporary directory behind. The receipt verb, which creates the same kind of worktree, does install interrupt handling so its cleanup always runs.

EVIDENCE: advance.go lines 80-85 create the worktree and remove it with a Close call on the normal and conflicted paths; there is no signal handling anywhere in the file, and the file does not import the signal package. By contrast receipt.go installs a handler and checks it between steps so the deferred close still runs. The worktree cleanup routine in detached.go lines 207-226 deliberately never runs 'git worktree prune', with a comment saying why, so a leaked registration is not swept later. Consequence: after an interrupted landing the repository carries an extra worktree registration, which the fixtures' own 'exactly one worktree' assertions would then trip on. Recovery is a single 'git worktree prune'. No proof is weakened and no branch is moved, so this is not material, but it is the kind of leak that compounds across runs.

## LRF-03 — low, material=False

CLAIM: The drift verb's append shape and the register-carriage rule disagree in one narrow case: a register whose file permission bits changed in the working tree while its content grew by a genuine append. The drift verb tolerates it and the advance verb calls it a contended register, but the register-carriage landing that the repair route names would refuse it. The design page claims the drift verb tolerates exactly what the carriage rule accepts.

EVIDENCE: The new append-shape test in drift.go lines 1123-1156 checks only that the working-tree entry is a regular file, then compares bytes. The carriage rule in observe.go lines 958-962 additionally compares the tree mode on both sides and refuses with 'was deleted or changed mode' when it differs. Every other clause is mirrored exactly, including the newline requirements and the strict-growth prefix test. Reaching the divergence takes someone changing the mode of a log file; the outcome is a loud refusal in the repair step rather than a bad landing, which is why I do not call it material.

## LRF-04 — low, material=False

CLAIM: The pre-commit untracked check widened from the workspace directory to the whole repository. A file left untracked in a sibling directory of the workspace now refuses staging where before it did not.

EVIDENCE: The replaced check used 'git ls-files --others --exclude-standard', which git scopes to the directory it is invoked from, and land.sh invokes it from the workspace. The new drift verb runs 'git status' at the repository toplevel. The design chose toplevel scope explicitly and gave its reason, and the post-commit cleanliness check was already toplevel-scoped, so the same file would have refused a few steps later in any case. The only change in outcome is that the refusal now arrives before the battery instead of after the commit, which is the safer order.

## LRF-05 — low, material=False

CLAIM: The append-shape test rebuilds the whole workspace index on every call, so a landing pays for several full index reconstructions it does not need.

EVIDENCE: The test calls StagedTree, which (snapshotscope.go line 324) reads every staged entry, loads them into a fresh isolated index and writes a tree. It is called once per candidate register per drift run, land.sh runs the drift verb twice per landing, and the advance verb calls it once per overlapping register. Four to six full index reconstructions per landing where one would do. Cost only; nothing about the answer changes.

## LRF-06 — low, material=False

CLAIM: The new shell passing canary replaces the fixture bed's cleanup trap with a kill-only trap and restores it several commands later; an exit inside that window would leave the bed's temporary directory behind.

EVIDENCE: land-fixtures.sh line 853 installs a trap that only kills the background appender, replacing the bed's own trap from line 36 that removes the temporary directory, and line 878 restores it. Every command between them runs with errexit disabled, so the window is practically unreachable, and the appender's process identifier is initialised to the empty string first so the trap cannot trip the unset-variable guard. Worth a note only because a later edit inside that window would silently start leaking the bed's temporary tree.

# Fable model alias design — Sol critique, round 1

Critic: codex gpt-5.6-sol (job fma-critique-2, DESIGN-BEARING, read-only) over plans/fable-model-alias-design.md revision 1 at bc227e39. Seven material findings (five high, two medium), three non-material confirmations. Persisted verbatim by the m3 seat, 2026-09-03. Dispositions follow the findings.

## FMA-R1-FOLLOWUP-BYPASS — high
CLAIM: The claimed single application point excludes legacy follow-ups, allowing the retired identifier to reach every forbidden downstream surface. The design says the roster read is “the only place a model id is BORN” and “No other file rewrites ids,” but follow_up reads requestedModel directly from the newest record at metasystem/scripts/agents/dispatch.sh:1762 without calling ResolveRoster. BuildFollowRecord reads and copies the same value at metasystem/internal/dispatch/build.go:524 and :596. With the temporary dual maximal-model overlay explicitly allowed by the rollover, composition and claim admission accept claude-fable-5; CanonicalModel leaves that already-canonical string unchanged; the child record receives requestedModel and canonicalModelKey claude-fable-5; and the Claude adapter passes it to --model. The design must either resolve inherited models through the alias helper before follow-up composition or explicitly refuse legacy-source follow-ups. Past records can remain literal for closure safety; a newly resolved follow-up must use the target and record its own alias event.
EVIDENCE: metasystem/scripts/agents/dispatch.sh:1762, :1900-1904, :1932-1941, :1963-1974 and :2004-2015 form a complete follow-up path outside ResolveRoster. metasystem/scripts/agents/adapters/runtime-common.sh:84 reads the resulting requestedModel, and metasystem/scripts/agents/adapters/claude.sh:126 forwards it into command construction. metasystem/plans/fable-5-1-rollover-design.md:41-43 explicitly permits an effective maximal-model list containing the retired source while an old chain drains.
MATERIAL: True

## FMA-R1-TARGET-NOT-ADMITTED — high
CLAIM: Allowing an alias target that is absent from maximal-models recreates Wido's original refusal under a less informative name. Section 2 says “The target is not required in maximal-models: after aliasing it is the id the gate checks.” That is the reason it must be admitted: runtimeProvesMaximalExecution compares the target literally and returns false when it is absent. This also contradicts the design brief's requirement that the target be listed wherever the source would have needed admission. Validation must require the target in the effective maximal-model mapping for this maximal-effort alias, including the case where a machine-local maximal-models row shadows the committed row, or produce an alias-specific pre-admission refusal naming source, target, and missing mapping. Tests must cover both a missing tracked target and a local overlay that shadows an admitted tracked target.
EVIDENCE: metasystem/plans/fable-model-alias-design.md:47-49 declines the requirement; metasystem/plans/fable-model-alias-design-brief.md:58-61 requires it. metasystem/internal/dispatch/hazard.go:113-138 checks literal membership, while metasystem/internal/config/resolve.go:67-112 allows environment and machine-local values to shadow the committed maximal-models row.
MATERIAL: True

## FMA-R1-READ-ORIGIN-AUTHORITY — high
CLAIM: Committed-only alias authority is a human policy decision that the design both makes and labels as an unresolved gap. Section 2 admits, “The order does not say this in words,” yet section 7's proposed ruling attributes “the alias key is read from the committed file only” to Wido. The restriction is not a necessary consequence of the rollover: an overlay target still keeps claude-fable-5 away from the Claude command-line interface, and the hazard gate still refuses a non-maximal target. A local alias is broader than today's local roster override because it reinterprets every matching role and an explicit --model argument, which is a good reason to recommend tracked-only authority, but not authority to record it as Wido's ruling. Wido must decide whether the family name has one fleet-wide committed meaning or may be redefined per machine or environment.
EVIDENCE: metasystem/plans/fable-model-alias-design.md:40-44 acknowledges the missing order, while :98 records the unapproved restriction in the ruling. metasystem/internal/config/resolve.go:67-95 shows that local and environment roster selection is permitted today. Neither Wido quotation in metasystem/plans/fable-model-alias-design.md:3-5 specifies configuration origin.
MATERIAL: True

## FMA-R1-CAP-ROW-FALLTHROUGH — high
CLAIM: Canonical-only cap lookup does not provide the directional protection claimed and can silently enlarge or shrink the operator's cap. With only cap.min.code-critic.claude.claude-fable-5=30, the source row is ignored and the current committed general value gives 120 minutes. Conversely, a general value below the source row silently shortens the run. The example in section 3 considers only an old 30-minute role row incorrectly outranking a new 200-minute target pair row; an ordered fallback can avoid that by checking every canonical target-specific row first, then alias-source rows, then the general row. If canonical-only behavior remains, validation should emit a non-failing informational line naming the ignored row and replacement key, not refuse it, because this goal expressly avoids forcing local-overlay edits. The cap fixture must assert both the selected number and provenance rule, including the 30-to-120 enlargement case.
EVIDENCE: metasystem/internal/dispatch/cap.go:36-59 falls from canonical role and pair keys to dispatch.cap-min and then 120. metasystem/metasystem.conf:40 sets dispatch.cap-min=120. metasystem/plans/fable-model-alias-design.md:51-59 chooses canonical-only and leaves stale-row reporting unresolved; its proposed test at :83 asserts only a general rule in an underspecified fixture.
MATERIAL: True

## FMA-R1-VALIDATOR-TEST-MATRIX — medium
CLAIM: Section 5 does not discriminate every validator rule promised by section 2. It has no alias-specific rejection for an unrostered runtime, an empty source, a non-canonical target, or an environment alias. It tests only the validator's machine-local refusal, not ResolveModelAlias's runtime refusal, so the dispatcher could still honor a forbidden overlay even while config validate rejects it. Once target admission is corrected, missing-target and shadowing-local-maximal tests are also required. Each rule needs a positive counterpart or focused rejection so an implementer cannot omit half of the policy while satisfying the listed suite.
EVIDENCE: metasystem/plans/fable-model-alias-design.md:44-49 lists runtime membership, two non-empty values, canonical source and target, inequality, no chains, source exclusion, and two uncommitted-source refusals. Tests at :81-82 cover self-alias, chain, empty target, non-canonical source, source admission, and only the machine-local validator case.
MATERIAL: True

## FMA-R1-END-TO-END-PROOF — high
CLAIM: The proof plan does not traverse the boundary whose correctness is the design's central claim. TestHazardConfigurationAcceptsAliasedRoster directly calls ResolveRoster, the hazard validator, and BuildRecord. BuildRecord cannot prove canonicalModelKey because that field is added by claim reservation and preserved by RecordSetup; it cannot prove effectiveModel because that field starts null and is written by handshake; and it cannot prove the Claude --model argument because BuildClaudeCommand receives the adapter's supplied string verbatim. A dispatcher-level fixture must begin with a source-valued roster or --model override and assert the composed model, cap key, reservation canonicalModelKey, final requestedModel and effectiveModel, aliasedFrom relay, and generated Claude argument are all claude-fable-5-1 with no claude-fable-5 argument. Without it, omitting the shell's aliasedFrom flag or bypassing any downstream leg still passes every proposed test.
EVIDENCE: metasystem/plans/fable-model-alias-design.md:77-80 describes direct component calls. metasystem/internal/dispatch/build.go:409-410 writes requestedModel and null effectiveModel but no canonicalModelKey. metasystem/internal/dispatch/claim.go:694 supplies canonicalModelKey; metasystem/internal/dispatch/record.go:346-360 preserves it; metasystem/internal/dispatch/handshake.go:101-108 supplies effectiveModel; metasystem/internal/adapter/claude.go:286-288 puts the supplied model on the command line.
MATERIAL: True

## FMA-R1-ALIAS-PROVENANCE-SHAPE — medium
CLAIM: One aliasedFrom string is underspecified once more than one direct alias exists. ResolveRoster is told to alias the roster model, requested model, and override independently, but the field is merely “empty when nothing fired, else the literal effective id.” A future roster on claude-fable-5 combined with --model claude-fable-5-1 can fire two direct aliases with different sources after the 5.2 rollover, leaving an implementer to choose which literal to record. If aliasedFrom means only the selected effective input, it cannot support the promised sweep for stale roster entries when an override masks them; if it means any fired alias, it cannot faithfully name both. The schema must distinguish effective-input provenance from literal roster provenance, define the combined case, and protect the audit fields as immutable record provenance. Ordinary follow-ups should not blindly copy an event that did not occur, but a legacy follow-up canonicalized under finding FMA-R1-FOLLOWUP-BYPASS must record its own event.
EVIDENCE: metasystem/plans/fable-model-alias-design.md:20-25 specifies three alias applications but one string, and :63-67 makes that string the fleet audit surface. Direct fan-in is the intended rollover shape. metasystem/internal/dispatch/record.go:60-75 enumerates immutable provenance fields; the design does not require adding aliasedFrom or any literal-roster field there.
MATERIAL: True

## Gaps reported by the critic

- Human decision required from Wido: must claude-fable-5 have one fleet-wide meaning controlled only by the committed pointer, or may a machine-local configuration or environment variable redefine it? ## Dispositions (m3 seat, dispatch delegate, 2026-09-03)

- FMA-R1-FOLLOWUP-BYPASS: ACCEPT. The alias is applied to the inherited requestedModel at follow-up composition too; a follow-up whose parent record carries an alias source is rewritten to the target and records its own alias event. Past records stay literal (closure safety, rollover design section 5).
- FMA-R1-TARGET-NOT-ADMITTED: ACCEPT. The validator requires the target of every alias line to be present in the tracked maximal-models line of its runtime; the design brief item 2 said so and the design dropped it. A machine-local maximal-models overlay that shadows the tracked row is named by the validator as it is for the alias key itself.
- FMA-R1-READ-ORIGIN-AUTHORITY: ACCEPT THE ATTRIBUTION POINT; the choice goes to Wido as a question. Until he answers, the design carries committed-only as the seat's recommendation with its reason (a local alias reinterprets every role and every explicit --model, which a local roster line does not), and the R-71-m3 row does not attribute the read origin to him.
- FMA-R1-CAP-ROW-FALLTHROUGH: ACCEPT the ordered fallback the critic offers: canonical role-pair, canonical pair, source role-pair, source pair, general. It keeps the design's own objection answered (a row written for the dispatched model always wins) and stops a stale 30-minute family row from silently becoming 120. No validator line needed then. The fixture asserts the number and the rule, including 30-not-120.
- FMA-R1-VALIDATOR-TEST-MATRIX: ACCEPT. Every validator rule gets a focused test; ResolveModelAlias's own overlay and environment refusals are tested at the resolver, not only at config validate.
- FMA-R1-END-TO-END-PROOF: ACCEPT. One dispatcher-level fixture from a source-valued roster (and one from a --model source override) asserts the composed model, the cap key, the reservation's canonicalModelKey, requestedModel, effectiveModel where the fake handshake writes it, the alias provenance and the generated Claude command arguments: all target, no source anywhere.
- FMA-R1-ALIAS-PROVENANCE-SHAPE: ACCEPT. Two immutable provenance fields: aliasedFrom (the literal of the effective input, or null) and rosterAliasedFrom (the literal roster id when the roster alias fired, or null); both listed among the immutable provenance fields the record patch refuses to change; the sweep reads either.
- FMA-R1-ROLLOVER-SHAPE-SOUND, FMA-R1-OVERRIDE-FINGERPRINT-SOUND, FMA-R1-EXISTING-FIXTURES-SOUND: confirmations, no change.

## SVC7-01 — critical — material=True

CLAIM: The last step of the stop transaction throws away every live thing it just found that is not an untracked process, and the run can then tell the person the checkout is stopped, with exit code 0, while a metasystem process it owns is running. After the late-arrivals loop, stop takes one more inventory of every family and then keeps only the items whose key begins 'untracked:'; a plain continue discards a mission runner, a job, a run, a proof-run suite, a steward runner or a supervision component that the same inventory reported alive a line earlier. Nothing is signalled, no line is printed, and no entry is written to the durable notStopped list, so the closing line is the success sentence and the fence record says the checkout reached the stopped phase. This is exactly the case the late-arrivals pass exists to catch, reached through a window the pass leaves open: the loop stops as soon as one round finds nothing eligible, and anything that publishes after that round but before the final inventory lands in the discard.

EVIDENCE: internal/stoptransition/transition.go lines 277-294: 'finalItems := t.inventoryDuringStop(...)' followed by 'if !strings.HasPrefix(item.Key, "untracked:") { continue }'. Proven by running a probe test in a scratch copy of the tree: a family whose live item first appears in the third post-fence inventory yields inventories=3, stops=0, exit=0, and a report reading 'nothing is running' then 'stopped <checkout>; start again: metasystem arm --repo <checkout>'. The item was alive and owned by that family throughout. This contradicts section 2's rule that anything still live after the passes is NOT STOPPED, section 6's rule that every printed line comes from an outcome, section 14.6's rule that a run which did not end everything must not close by saying the checkout is stopped, and section 15.1's rule that every survivor reason is written into the record.

## SVC7-03 — medium — material=True

CLAIM: Repairing a malformed fence record moves the generation counter backwards, contrary to the stated purpose of the field that exists to prevent exactly that. The reader recovers the previous generation by re-parsing the same bytes into a one-field envelope, which can only succeed when the document is valid JSON with an unsupported schema version. In the ordinary corruption case, a truncated or malformed file, the second parse fails too, the recovered generation stays zero, and arm writes a fresh open record at generation 1. Because the creation handshake is built on this counter, the rollback has teeth: stopfence.InspectClaims and the late-arrivals pass both admit only claims and records at or below the generation the stop closed with, so any claim or published record left over from the higher pre-corruption generations is invisible to the completion barrier, and a creator holding one of those older generations is neither waited for nor collected.

EVIDENCE: Proven by running a probe test in a scratch copy: a readable record at generation 7 is truncated, and the next arm prints 'fence record replaced (was unreadable: stop fence is unreadable: unexpected end of JSON input)' followed by 'armed <checkout> generation 1'. Code: internal/stopfence/fence.go:80-86 documents the field as keeping the generation 'so the human arm path can replace it without moving the generation backwards'; fence.go:139-148 fills it only when json.Unmarshal of the same bytes succeeds; internal/stoptransition/transition.go:698-703 writes HighestGeneration+1. The filters that then read stale numbers are fence.go:293 (claim.Generation <= maximumGeneration) and transition.go:234 (*item.FenceGeneration <= generation).

## SVC7-04 — medium — material=True

CLAIM: The late-arrivals pass acts at most twice, not the three times section 2 specifies. The loop runs three iterations, but on the third it takes a branch that only records survivors and breaks, without calling any family's stop path. An arrival first seen in that third inventory is therefore declared NOT STOPPED with the reason 'arrived during stop', sets exit 1, and is written into the durable survivor list that arm will refuse over, without stop ever having sent it a signal. The report line says 'did: left it listed in the fence record', which is honest about what happened, but the behaviour is one retry short of the promise, and each unattempted survivor is a fence entry the next arm must refuse over.

EVIDENCE: internal/stoptransition/transition.go lines 220-272: the loop header is 'for pass := 0; pass < 3; pass++', and at 'if pass == 2' the body appends survivors and report lines and breaks before reaching the stopItem call at line 253. So iterations 0 and 1 act and iteration 2 only lists. Section 2 of metasystem/plans/metasystem-stop-verb-design.md: 'the pass repeats until an inventory is empty, at most three times, and what is still live after that is NOT STOPPED with the reason arrived during stop'.

## SVC7-N1 — low — material=False

CLAIM: The AfterStep observer can still end the stop transaction after the fence has been closed, which section 14.1 says must never happen for any reason. When the hook returns an error that is not an unknown-family error, Stop returns it and the caller prints a refusal instead of the report, so the fence is left closed in the stopping phase with no survivor list and no printed page. Today this is unreachable in production, because the only registered hook is the fixture crash injector, which either returns nil or exits the process outright. It is the same shape as the latent trap section 16.6 closed for unknown family names: harmless until someone registers a second observer.

EVIDENCE: internal/stoptransition/transition.go lines 209-217, 273-275 and 295-297 return report, err on an AfterStep error. cmd/metasystem/process_verbs.go:88-97 is the only registration and calls os.Exit(1) rather than returning an error. Section 14.1: 'Once stop has written the record closed, it does not exit early for any reason.'

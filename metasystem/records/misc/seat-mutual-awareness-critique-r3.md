## Findings

### SMA-C-21 (material: True, severity: high)

Claim: SMA-C-21, the enable marker is forgeable because historical trailer presence proves neither human authority nor authorship of the current bytes. The validator treats `authority: proven` and the `human:` prefix as self-asserted text, checks only the operation identifier's machine segment, and accepts that identifier if it occurs anywhere in history. It does not bind the marker to the commit that introduced or last changed it, to an approval-bearing History event, or to terminal classification. An old landing can therefore reuse an existing transaction identifier from the same machine, or type a Goal-Transaction trailer through the existing commit wrapper, and create or alter a marker that upgraded writers accept. Retaining an older valid identifier while editing another seat record defeats the claimed binding in the same way. An implementer following metasystem/plans/seat-mutual-awareness-design.md would build a content-shape check, not the unforgeable enable act the design promises.

Evidence: The proposed checks and the claim that an old landing lacks a usable trailer are at metasystem/plans/seat-mutual-awareness-design.md:182-213 and 586-627. TrailerPresent searches the entire history at metasystem/internal/goal/txn.go:375-390. Metasystem/internal/goal/file.go:1491-1496 states that the operation identifier attributes execution while History attributes authority, and its approval validator binds actor, time, verb, and operation identifier at lines 572-612. The executed search found no Goal-Transaction guard in metasystem/scripts/agents/commit.sh, while that wrapper explicitly guards Goal-Item message text at lines 127-203.

### SMA-C-22 (material: True, severity: high)

Claim: SMA-C-22, the preferred repair exemption cannot travel through the transaction hook the design names, and the fallback is not a sound transaction path. PublishRequest.Validate sees only the built commit; the invalid captured tip is rejected earlier by a hard-coded ValidateCommit call. The fallback then proposes calling BuildCommit and the compare-and-swap push directly, which would bypass or duplicate the ordinary loop's acceptance gates, synchronization-mode gate, journal lifecycle, compare-and-swap retry classification, pushed-before-push durability, postcondition confirmation, and accepted-ref advancement. The design leaves an implementer choosing between changing the shared transaction interface without a contract or shipping a human repair path that lacks the engine's safety and recovery behavior. Metasystem/plans/seat-mutual-awareness-design.md must name an ordinary transaction-engine seam for scoped captured-tip validation and retain the existing goal validation unchanged.

Evidence: The proposed mechanism and fallback are at metasystem/plans/seat-mutual-awareness-design.md:629-656 and 874-884. The captured-tip validation is hard-coded before mutation at metasystem/internal/goal/txn.go:595-620; PublishRequest.Validate is documented for the built commit at lines 466-482 and called only at lines 631-642. The omitted transaction obligations occupy lines 572-725. Recovery completes rebuildable work through runTransaction at metasystem/internal/goal/recover.go:137-199, not through a direct BuildCommit and PublishCAS sequence.

### SMA-C-23 (material: True, severity: high)

Claim: SMA-C-23, the repair command's replace form contradicts the writer identity rules for records owned by another machine. The design requires replacement content to carry the repair transaction's operation identifier and requires the built tree to validate without an exemption. That identifier names the terminal's machine, while the validator requires a presence identifier to name the presence machine and an ask identifier to name the asking machine. A human repairing machine B's presence or ask from the enrolled terminal on machine A therefore produces content the required whole-tree validation rejects. The unrestricted `--path` interface leaves the implementer to guess whether replacement is limited to locally owned records, whether the repair transaction may impersonate the record owner, or whether built-tree validation receives a second exemption.

Evidence: The unrestricted remove-or-replace interface, terminal operation identifier, mandatory unexempted built validation, and replacement identifier rule are at metasystem/plans/seat-mutual-awareness-design.md:629-650. The conflicting machine checks are at lines 590-592: presence identifiers must name the presence machine and ask identifiers must name `from`. The spoiled-tip fixture repairs on machine A and the command contract names no same-owner restriction at lines 709-715.

### SMA-C-24 (material: True, severity: medium)

Claim: SMA-C-24, the at-rest expiration language still permits two meanings at the exact deadline second. Live answer is on time when its timestamp equals deadlineAt, and live expiration is permitted only when now is later. The validator, however, rejects expiredAt only when it is earlier than deadlineAt, so it accepts an expired record whose expiredAt equals the deadline. Such a record prevents the answer outcome that the transition table says is still lawful at that instant. The expiration predicate and its malformed-tree fixture in metasystem/plans/seat-mutual-awareness-design.md must use the same strict boundary.

Evidence: The transition table makes equality on time and expiration strictly later at metasystem/plans/seat-mutual-awareness-design.md:394-421. The validator permits equality by refusing only an expiredAt earlier than deadlineAt at line 596. SMA-F-DEADLINE-SECOND proves an answer at equality and an answer one second later, but no fixture rejects an expired record stamped at equality at lines 753-755 and 798-805.

### SMA-C-25 (material: True, severity: high)

Claim: SMA-C-25, the four-slice order makes questions writable before addressed seats have the mechanism that tells them to answer. The global enable marker is already active after slice one. Slice three then exposes seat ask, but RunSeatAttention, the seat-questions health role, digest notification, and status clause do not land until slice four. A machine running slice three can therefore ask a member still running slice two, and that target receives no turn-end notification or health signal; discovering the question requires the polling behavior the design says it removes. Metasystem/plans/seat-mutual-awareness-design.md must either land the reader and notification path before the ask writer or retain a separate activation gate until slice four is deployed.

Evidence: The no-poll notification contract is at metasystem/plans/seat-mutual-awareness-design.md:464-531. The build order puts ask, answer, close, wait, and show in slice three, then the health role, digest, and status clause in slice four at lines 835-841. The only rollout gate is the marker enabled after the slice-one fleet rebuild at lines 606-617; no later capability or activation gate prevents slice-three asks.

## BIRTH-R1-FAKE-WRITER-001 — high, material=True

CLAIM: The design knowingly leaves a post-contract wholesale writer that creates tokenless records and can erase an existing token. Section 3 says, “Fake host simulator … Writes a fake completed record with no token” and disposes it as “pre-contract by construction,” while section 4 says “every record created after landing carries a token.” In metasystem/internal/host/fake.go:80-99, FakeReturn constructs a complete record without birthToken and writes it to artifacts/agents/jobs through atomicWriteJSON; metasystem/internal/host/host.go:24-36 publishes that map by atomic replacement, without a record lock or collision refusal. Repeating the fake-host behavior for the same mission identifier replaces the prior record and drops any token it carried. Fixture-only provenance does not make a record born after the contract a pre-contract record. The implementation must route this writer through the minting owner or explicitly narrow the promised invariant; either choice changes the claimed eight-file boundary.

EVIDENCE: Disagreeing design text is at metasystem/plans/job-record-birth-token-design.md:196 and :282-288. The complete tokenless record and replacement are at metasystem/internal/host/fake.go:80-99 and metasystem/internal/host/host.go:24-36. Metasystem/internal/host/host_test.go:208-230 proves this is an exercised writer after startup, not merely dead helper code.

## BIRTH-R1-JSON-SET-BYPASS-002 — medium, material=True

CLAIM: The writer enumeration misses the shipped `metasystem json set` record bypass, so the proposed immutability and no-backfill statements are not true for all repository verbs. The design says, “No verb, sweep, migration, or setup path ever adds birthToken to an existing record” and that its table lists every job-record writer. Metasystem/cmd/metasystem/json.go:17-57 reads any caller-selected JSON object, applies caller-named fields, and rewrites it through writeIdentityJSON; metasystem/cmd/metasystem/helpers.go:23-36 performs the atomic replacement. Existing calls in metasystem/scripts/agents/dispatch-fixtures.sh:1732-1735, :1951-1956, and :2779-2783 target live job records. A caller can therefore add, empty, or replace birthToken without the immutable-fields map or typed *OpError ever running. The design must decide whether this command is a declared maintenance escape from the invariant or must refuse birthToken edits on job records; leaving that choice to the implementer makes the contract and diff boundary ambiguous.

EVIDENCE: The exhaustive assertion is at metasystem/plans/job-record-birth-token-design.md:172-177 and the no-verb assertion at :256-260. The unrestricted field write is at metasystem/cmd/metasystem/json.go:17-57, its atomic writer at metasystem/cmd/metasystem/helpers.go:23-36, and the public verb registration at metasystem/cmd/metasystem/main.go:372-378. The cited fixture calls demonstrate that job records are an intentional target of this command.

## BIRTH-R1-CALLER-ENUMERATION-003 — high, material=True

CLAIM: Section 5's supposedly complete incarnation-caller table omits consumers that already collapse or overwrite lawful reused identifiers, so “Nothing else” and the eight-file boundary are not established. Metasystem/internal/metrics/data.go:485-542 loads both local and durable records, groups them only as `byID[record.JobID]`, and keeps one winner; an old archived incarnation and a fresh local incarnation with the same job ID are therefore treated as duplicates even when their birth tokens differ. Metasystem/internal/dispatch/mirror.go:60-87 addresses durable chain evidence only as checkout segment plus root job ID, carries the old manifest forward, and metasystem/internal/dispatch/mirror.go:198-246 copies the new incarnation over the same job and round paths. After the lawful collection-and-reuse sequence assumed by this design, metrics first hides the old incarnation and a later mirror can overwrite its durable evidence. The table also understates the disclosed parent-name residual: name-only lineage is consumed by CloseCheck, ChainUsage, review-reference reconciliation, critique-state resolution, ChainMemberStatuses, mission usage attribution, and landing observation, not only follow-up dispatch. The design must assign switch, stay, or out-of-scope dispositions to these callers and account for the durable-evidence behavior; switching the first two requires files outside the declared boundary, while accepting evidence overwrite would require an explicit human decision.

## BIRTH-R1-RANDOM-FIXTURE-005 — medium, material=True

CLAIM: The same-second reuse fixture is probabilistic despite the design's deterministic-test requirement. Section 6 begins “All deterministic: … injected clock and entropy,” but TestBirthTokenSameSecondReuseIsDistinct says “Real crypto/rand is fine here because the assertion is inequality.” Two independent 128-bit random values can be equal, however unlikely, so the fixture does not deterministically prove distinct same-second reuse. It must inject two fixed, distinct 16-byte entropy blocks and assert the resulting tokens and common timestamp prefix.

EVIDENCE: The conflicting statements are both in metasystem/plans/job-record-birth-token-design.md:315-319 and :338-342. Metasystem/docs/design/design-principles.md requires controlled, deterministic fixtures. The field shape itself is otherwise consistent: 20 timestamp bytes plus one hyphen plus 32 hexadecimal bytes equals 53 bytes.

## BIRTH-R1-REPAIR-FIXTURE-006 — medium, material=True

CLAIM: The pre-contract fixture's stated operation order never exercises the RepairClaim write it claims to verify. The design orders RecordSetup, pending-to-running RecordCAS, RecordProtocolError, then RepairClaim. Metasystem/internal/dispatch/record.go:453-463 makes RecordProtocolError set status to failed, while RepairClaim at metasystem/internal/dispatch/record.go:732-750 returns before its write whenever status is not running. The test can still observe an absent token after that refusal, but it proves nothing about RepairClaim's read-modify-write preservation. RepairClaim must run while the record is running, before ProtocolError, or on a separate running pre-contract record.

# MV-2 findings, carried. All nine OPEN, none dispositioned.

### MV-2-1 (sev=critical)
The new entry check still does not prevent an already-authorized dispatch subprocess from writing after its main dies and a successor claims the lease. The old holder can pass the entry check, die while its child creates a worktree, payload, capability snapshot, or mission reservation, and let the successor claim during those side effects. The final record check will eventually refuse, but the interference and abandoned state have already happened. Thus the fold closes a static non-holder case but not the death race that the one-writer rule must fence.
EVIDENCE: Read: D-5 explicitly calls the entry check advisory and does not take the lease lock until record creation. The shipped integration performs the named side effects between those points. Liveness is based only on the announced main's process identifier and start time, so its surviving dispatch child does not delay a successor's claim. The Proof tests a caller that is already a non-holder at entry, not a holder dying during pre-record work.

### MV-2-2 (sev=critical)
The pre-commit guard cannot prove that the commit wrapper holds the lease merely because a non-blocking lock attempt returns would-block. Any concurrent lease-locked operation—such as record creation, adapter launch, or another wrapped commit—produces the same result. An agent bypassing the wrapper can therefore be admitted whenever an unrelated operation holds the lock, leaving Git's mutation outside the fence.
EVIDENCE: Read: D-6 says the guard's would-block result proves the lock is held around “this commit,” but the probe observes only global lock contention and carries no wrapper identity or ownership token. D-5 deliberately uses the same lease lock for dispatch creation and launch. The Commit Proof checks bypass with no unrelated contender and therefore cannot expose this false-positive case.

### MV-2-3 (sev=critical)
The protocol-error transition cannot be the single atomic write D-10 requires for follow-up rounds. The terminal status belongs to the follow-up child record, while protocolErrors belongs to the chain root record. Those are different files with different locks, so one per-record compare-and-swap cannot update both. An implementer must either abandon the stated atomicity, move the error set, or introduce a multi-record transaction contract that the design does not specify.
EVIDENCE: Read: D-10 places protocolErrors on the chain root and says the same locked write both appends there and transitions the round to failed/protocol_error. Shipped follow-up records have child identifiers such as root-r2 and a parentJob link. atomic_record_python opens only record-locks/<job>.lock and replaces only jobs/<job>.json, so round two and later necessarily require two record writes under the proposed layout.

### MV-2-4 (sev=high)
One generation field is assigned two incompatible jobs: mutation revision and ownership epoch. D-3 increments it for renewals as well as claims, while D-5 requires the launch-time lease generation to equal the job record's dispatch-time generation and D-7 binds cleanup to the claim generation. A legitimate renewal between record creation and launch therefore looks exactly like a takeover and aborts the holder's launch. The design also leaves implementers to guess whether a cleanup stamp survives later renewals or must equal the current generation.
EVIDENCE: Read: D-3 says every claim, renewal, and takeover write increments generation. D-5 requires exact generation equality at launch. D-7 stores the claim's generation in reapedAfterClaim but defines no separate claim epoch in the lease schema. A correct implementation therefore needs either different counters or comparison rules not present in the design.

### MV-2-5 (sev=high)
The authority matrix contains an unreachable supervision class and omits the trusted adapter-supervisor class needed by the shipped lifecycle. D-2's supposedly complete caller walk classifies a process with no announcement or adapter-signature ancestor as HUMAN; it never checks supervision instance tags. Detached adapter supervisors are deliberately excluded from adapter signatures, yet they must update handshake, custody, effective-model, and terminal job fields. Implementers must either grant these processes unrestricted human authority, block required lifecycle writes, or invent another authenticated class.
EVIDENCE: Read: D-2 tests only announcements and adapter signatures before falling through to HUMAN. D-4 separately says the supervision set is identified by instance tags but gives no place in that walk. The shipped adapters call __handshake, __register-custody, and __record-cas, and their adapter shell commands are excluded by every runtime's signature declaration. After their launching dispatcher exits, they have no announced main ancestor. The Authority Proof tests holder, advisor, delegate, and bare-shell callers but omits the supervision-set row entirely.

### MV-2-6 (sev=high)
The authority matrix says who may invoke cancel, close, manual reap, supervision shutdown, and evidence collection, but it does not fence those mutations across lease transfer. A holder can pass an entry authorization, die, and leave one of these child operations running while a successor claims. A stale shutdown can stop the successor's supervision, a stale reap can signal jobs, and stale collection can delete shared artifacts. Dispatch and commit receive operation-spanning rules; the other holder-only writers do not.
EVIDENCE: Read: D-4 lists these operations as holder writes but specifies no final generation recheck, lease-lock scope, or stale-child outcome for them. D-5 and D-6 explicitly add such scopes only for dispatch launch and Git commit. The shipped cancel, close, reap, shutdown, and evidence collector all perform mutations after their entry points. The matrix Proof observes static caller classes, not a claim racing each holder-only operation.

### MV-2-7 (sev=high)
The consolidated return contract reverses the settled single-literal decision and will make implementers build different schemas and assertions. It now requires unobserved for unavailable session identity but unreported for unavailable effective model, even though the retained adjudication says every unobserved state uses the one literal unobserved.
EVIDENCE: Read: D-9 lines 157 through 160 specify two literals. The accepted MM-3-10 disposition states “One literal: unobserved,” and the design says settled decisions remain carried by those dispositions. The current telemetry fixture's unreported model value explains the rewrite's choice but does not adjudicate the contradiction. Literal values are protocol behavior, not prose.

### MV-2-8 (sev=high)
D-11 still does not specify an implementable semantic configuration filter, and the rewritten Proof drops filter validation entirely. The filter file has no grammar for key paths, justification records, or CLI version ranges; no rules explain parsing and merging JSON and TOML sources, canonicalizing values, handling malformed files, or retaining per-key state so a refusal can name changed keys. Reasonable implementations will hash different behavior and emit different diagnostics.
EVIDENCE: Read: D-11 names a text filename and desired outcomes only. The shipped Claude and Devin adapters hash multiple JSON layers, while Codex hashes TOML, using one raw-path-and-bytes function. Capability snapshots retain only an aggregate configHash, so naming changed keys requires an additional representation absent from the design. Unlike the previous Proof, the consolidated Proof has no identity-filter bullet or fixture.

### MV-2-9 (sev=medium)
The second-session helper's promise to copy local configuration is still an unresolved interface. The design does not identify source files, destination rules, overwrite behavior, symlink handling, or whether permissions and ignored local files are preserved. Implementers can produce worktrees with different runtime behavior or accidentally retain absolute links into the primary checkout, contradicting the promised isolation.
EVIDENCE: Read: D-8 says only “copies local configuration.” The shipped adapters use different project-local sources, including Claude settings and settings.local JSON, Codex config.toml, and Devin config, config.local, and hooks JSON. Git worktree creation copies tracked files but not ignored local files. The isolation Proof checks artifact and evidence paths, not the copied configuration set or links back to the primary checkout.

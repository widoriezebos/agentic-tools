# Project Adaptation

These steps assume a repository without existing agent instruction assets. If the repository already has agent contracts, skills, prompts, or rule files, follow `docs/metasystem-reconciliation.md`, which wraps these steps with inventory, classification, and cutover.

The fast path is the adopter script, run from the template checkout: `scripts/adopt.sh <target> [--runtimes <names>] [--copy-skills] [--enable debug-java]` (the adoptable set and Claude default come from `bin/metasystem runtime list --adoptable` and `bin/metasystem runtime adoption-default`). It performs steps 1, 3, 4, 8, and 9 below mechanically, refuses targets that need reconciliation instead of guessing at them, and prints the finish line: replace the explicit incomplete `testing.json` with reviewed application groups, fill `docs/project-rules.md` (step 2), then run both `bin/metasystem test check --root .` and `scripts/validate-metasystem.sh`. A script can detect only file-shaped instruction assets; confirm by hand that no agent-directed prose, prompt directories under other names, or agent-encoding hooks and CI exist before treating a repository as fresh. The numbered steps below remain the specification and the manual fallback. The guided path through the human half — step 2's facts plus covenant v1, doctrine v1, and the first goals — is the inception interview (`skills/inception/SKILL.md`), run on the coordinator seat, with the human present, for fresh and retrofit repositories alike.

1. Install with `scripts/adopt.sh <target> [--runtimes <names>] [--enable <optional-skill>]` from the template checkout. The payload is an explicit allowlist — what is not named does not ship — and the script also installs an explicit `TEST_CONTRACT_REQUIRED` application-contract template, registers skills and subagent profiles for the selected runtimes, installs the shipped CI workflow, hooks, and the new-plan commit guard, creates the gitignored `artifacts/` directory, seeds `plans/` with its README and fresh goal ledgers, seeds `memory/` with fresh empty living registers (never the template repository's own), and records the template SHA. The template never contains MetaSystem's own test groups and update must never overwrite a filled application contract. If adoption must ever be done by hand, reproduce exactly what the script does — its source is the specification — and merge shipped dotfiles such as `.gitattributes` into existing ones instead of overwriting them.
2. Replace `docs/project-rules.md` with verified project facts and commands, including project-specific delegation facts (see `docs/orchestration.md`), the team's additions to the decisions reserved for humans, the budget facts where agents can spend real money, the durable evidence root where run evidence must survive, the refactor acceptance gate with its cadence backstop, and, where the project chases measured goals, the improvement evaluation with its metrics and noise floor.
3. Enable optional skills only where they apply: move `optional-skills/debug-java` into `skills/` only for repositories with a JVM runtime, and configure its launcher path in the skill reference. Leave the rest of `optional-skills/` out.
4. Prepare or check host registration with the shared owner: `bin/metasystem runtime setup --repo <path-inside-installation>` configures every adoptable host, while `--runtimes claude,codex`, `--runtimes none`, and `--copy-skills` make selection and copy mode explicit. For an adopted installation below an application's Git root, name the installation or a directory beneath it; registrations remain in that installation while generated lifecycle launchers resolve it from the containing Git root. Add `--check` for a non-writing registration check. The command preserves unrelated instruction text, hook settings and foreign skill entries; it refuses conflicts instead of forcing them. Its separate `TEST_CONTRACT_REQUIRED`, `TEST_CONTRACT_INVALID`, or `TEST_CONTRACT_READY` line reports application-contract readiness without conflating that state with `CONFIG_READY` runtime registration. `scripts/adopt.sh` calls this owner for its selected runtimes and keeps Claude as adoption's default. The registration contract is declared, never remembered: `bin/metasystem runtime registration <name>` lists every artifact the owner consumes. Without registration, no runtime auto-triggers skills and routing depends entirely on the model reading `wow.md`.
5. Keep only design principles relevant to the system's risk. Do not weaken ownership, invariant, failure, or proof rules without documenting why.
6. Add project-specific skills only for specialist workflows used repeatedly. Initialize and validate each skill; keep detailed references one hop from `SKILL.md`.
7. Put task state in `plans/`, generated evidence in the gitignored `artifacts/` directory at the repository root (create it and add it to the project's `.gitignore`), and durable decisions in code and docs. Do not keep them in root prompt history. Programs start with `goal open`: before a multi-session effort's first commit, declare its goal through the verb — the engine owns where the ledger lives (the legacy single file or the converted `plans/goals/` tree) — and adoption seeds the ledger with a Goal-free declaration (never an example goal), which the turn verdict expires when the plans world moves.
8. Replace the incomplete `testing.json` with the project's reviewed contract, then run `bin/metasystem test check --root .`. The lawful fresh route has one initialization boundary: from the enrolled human terminal, commit and publish the reviewed adoption, project-rule, configuration, filled-contract, and legacy goal-ledger bytes; run the normal reviewed `goal migrate` against that committed source; publish and fast-forward the resulting accepted baseline; then open and claim the first implementation goal through the ordinary goal verbs. The first agent change runs `bin/metasystem test run --root . --mode auto --purpose delivery`, projects only that committed attempt with `bin/metasystem landing test-receipt --root . --mode auto`, and uses the normal commit and land wrappers with `--test-receipt`. It neither calls the agent HUMAN nor bypasses the installed hook, and it never seeds a successful proof record by hand. `records/goals/` starts absent/empty until the goal owner concludes a real goal; no placeholder file represents a conclusion. A missing local landing ref, unpublished initialization baseline, or checkout not fast-forwarded to that baseline is setup still to finish, not permission to weaken this sequence.

   A missing, static-only, no-test, or still-incomplete contract is migration work and must never print application readiness. Existing installations may finish structural runtime setup while reporting migration required, but their upgraded commit and landing consumers cannot accept legacy evidence as schema-2 proof. The validator invokes setup's check mode for the installed runtime set and validates each real event, action, runtime, matcher and timeout. `CONFIG_READY` proves only runtime-registration structure; `TEST_CONTRACT_READY` proves contract structure, not provider trust, a runtime restart, lifecycle observation, or a successful application test. Run `scripts/validate-metasystem.sh` after initialization. Do not edit trust stores or credentials as part of setup. Arm a repository's first supervision explicitly with `bin/metasystem up --repo <path>`; later session hooks are the steady-state path. Claude retains its receipt notice and fail-closed Stop behavior, Codex rejoins after compaction, and Devin's non-tool lifecycle groups have no matcher. Hard checks must not depend on anyone remembering to run them.
9. Replace the `<template sha>` placeholder in `docs/project-rules.md` with the template commit SHA adopted from; future template migrations diff against it (see the README's updating section). `scripts/adopt.sh` fills it automatically.

## What Not to Copy Forward

- `meta/` and its rationale documents.
- Old benchmark thresholds, frontier SHAs, provider or model names, fixture terminology, or incident-specific stop budgets.
- Language or framework rules irrelevant to the new repository.
- Multiple compatibility instruction files containing the same policy; compatibility files should point to `AGENTS.md`.
- Long tool manuals in root instructions; runtime subagent mechanics belong to the runtime's own manual.
- Rules already enforced by the compiler, tests, schemas, permissions, or CI, unless the routing instruction is still necessary.

## Receipts and Retro

The metasystem is judged by shipped outcomes rather than by whether its documents were followed. Evidence is collected continuously and consumed periodically.

Every task that changes the repository appends one receipt line at completion via `scripts/receipt.sh add`: task type, outcome, skills triggered, what verification showed, corrections received, stop-loss events, and a ceremony note when a rule cost more than it earned. Receipts are committed with the work. Review-only tasks propose the receipt line in the report instead of writing it. Purely conversational tasks get no receipt.

When `scripts/receipt.sh check` reports a retro due (default: more than 25 receipts or 30 days since the last retro), run the retro per `skills/retro/SKILL.md`. The previous retro's changes are reviewed against evidence first and kept, amended, or reverted. Period numbers are recorded so retros stay comparable. New proposals pass the change gate below before a human accepts or vetoes them. Every adopted change carries a testable expected effect in `memory/instruction-ledger.md` so the next retro can judge it.

Do not add a new global rule after a single ambiguous miss; receipts exist precisely so rules rest on repeated evidence. In the first week, run the first retro after a handful of tasks instead of waiting for the cadence. Early routing errors are the cheapest to fix.

### The Change Gate

Every instruction change (retro proposal, correction capture, or any other addition) answers these before it lands:

- What observed failure does this prevent?
- Is the model unable to infer it from the task, code, or tool feedback?
- Does an existing owner already cover it?
- Must it load always, or only for one task type or phase?
- Can a schema, permission, test, linter, or script enforce it better?
- What evidence will justify keeping it after models or products change?

If the answers are weak, do not add the instruction.

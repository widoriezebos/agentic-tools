Why this page exists. On 2026-09-14 Wido watched a day of builds and asked why they are slow. The answer he accepted: the seat relays between build and test because the delegate cannot run the beds; beds stop at the first failure so several defects cost several rounds; some checks give false negatives. He then asked what smarts are missing. The answer was observation, not a smarter model: a builder's fix was confidently wrong because it debugged from a one-line failure message, and the real cause only appeared when the seat captured the emitted bytes by hand and ran the same fixture row on trunk beside the candidate. What worked all day was evidence: real output, and trunk against candidate on the same input. His instruction: a proper design on the backlog, split into goals, high priority because it is efficiency.

The shape of the answer. Every step of the round writes a record beside the round. One controller runs the steps, composes the next brief from the records and dispatches it. The seat keeps the points doctrine gives it, listed in section 2.1, and nothing else waits on the seat. No step asks anyone to try harder. Where an approved contract and today's doctrine disagree, this page builds the doctrine as it stands and puts the change to Wido; no member that can be built today waits on his answer, and the members that do wait are named.

## 1. What the code shows today

### 1.1 The round as the seat runs it

1. The seat writes a brief from `scripts/agents/templates/brief.md` and dispatches an implementer. The packet is the brief plus `job testing-requirement` (`scripts/agents/dispatch.sh:1740`; text in `internal/dispatch/build.go:1122`) plus the role recipe (`scripts/agents/role-packets.json`, read by `internal/dispatch/composition.go:19`). The delegate returns version-2 JSON (`scripts/agents/roles/implementer.md:11`) into `artifacts/agents/<root>/rounds/<n>/return.json`. Its `gaps[]` are free strings (`scripts/agents/schemas/implementer.schema.json`); doctrine says an implementer gap-stop reopens design with the gap as input (`docs/orchestration.md:46-47`).
2. The seat runs `validate conformance --stage review --job <job>`. The interface is string triples: stdout lines, stderr lines and an exit code (`internal/validate/conformance.go:196-205`). `reviewStage` (`:354-427`) snapshots the worktree, refuses paths outside the declared boundary, and writes `rounds/<n>/diff.patch` and `rounds/<n>/review.json` with `reviewedTree` only after every check passes (`:421-427`); a refusal leaves nothing beside the round but stderr lines. Goal 28's page makes this the seat's step before any read is paid.
3. The seat dispatches a code critic with `--reviews <job>`. `job read-subject` computes the subject from `review.json` (`internal/dispatch/read_subject_compute.go:85-140`; fields in `internal/readsubject/subject.go:22-35`) and `CritiqueReadAdmission` (`internal/dispatch/read_admission.go:53`) refuses a redundant read of a subject a clean read already covers. The critic returns version-3 JSON with `findings[]`; `job critique-register-advance` folds them into the critic root's register (`internal/dispatch/finding_register.go:65-70`), and a later critic that returns a prior id with `material: false` resolves that finding as withdrawn (`:1079-1083`). The critic runs under the read-only envelope (`scripts/agents/permissions/critic.json`). At merge, conformance requires the critic's effective model to differ from the implementer's unless `independence=session-only` (`conformance.go:1337-1340`; `metasystem.conf:85-88`). A critic root cannot be opened for a goal whose review-round limit is zero (`internal/dispatch/build.go:608-611`), which is every tier-1 goal (`skills/code-critique/SKILL.md:64-66`; row 24 is tier 1). The orchestrator adjudicates every finding (`SKILL.md:12`).
4. The seat runs `job prove-round --job <job>` (`cmd/metasystem/prove_round.go:62-144`): the installation's `test run --tree <snapshot> --purpose diagnostic` (`:100`). When the goal's newest attempt failed, admission wants `--retry-decision FILE` (`:66`, `:101-105`; `internal/proofrun/attempt.go:818-826`) with `priorAttempt`, `cause`, `evidencePath` and `rationale` (`attempt.go:190-196`); nothing writes that file for the seat today. The result is `rounds/<n>/proof.json` and an attempt whose groups carry `Status`, `LogPath`, `Expected`, `Observed`, `Missing` and `Unexpected` (`internal/proofrun/test_result.go:30-70`). Each group runs in a detached worktree of the candidate tree (`internal/proofrun/test_build.go:654`).
5. The seat reads the failing logs, writes a follow-up from `scripts/agents/templates/follow-up.md` and dispatches `follow-up`. The packet is the seat's message plus the testing requirement (`dispatch.sh:2702`) plus the fixed continuation slots `prior-brief`, `prior-return`, `critique-register` and `prior-worktree` (`internal/dispatch/composition.go:199-206`). A follow-up resumes the parent session when the runtime snapshot says it can (`dispatch.sh:1997`, `:2548`); it composes a fresh context only after a cap or with a continuation (`:2715-2716`). Every brief must carry exactly one `Working Mode:` line (`internal/dispatch/brief.go:41-55`) and its cited paths must exist (`:62`; `dispatch.sh:862-864`).
6. When the register is clean and the proof is green, the seat lands with `land.sh --chain <root>`. `commit.sh:592-593` runs `landing observe`, which binds the closed critic chain's `reviewedTree` to the candidate and classifies the change against HEAD's tree (`internal/landing/observe.go:156`, `:324-360`). The accepted tip is `refs/remotes/origin/main`, or `refs/heads/main` in local mode (`internal/landing/carried.go:59-62`, `:202-205`). A landing over a red group has one form today: a verified human issues `goal carry` for one tree and one `group:<id>`, and `land.sh --carried <opid>` carries only that fact (`docs/orchestration.md:150-156`; `carried.go:197`).

Nothing runs steps 2 to 5 for the seat. `metasystem wait --job` (`cmd/metasystem/wait_verb.go:61`) returns on the recorded terminal event and executes nothing; its callbacks observe ownership and open work (`:266-330`). The mission runner spawns `dispatch.sh` per active job (`internal/missionrunner/drain.go:61-69`) and has no round step. When a job goes terminal the reaper's `mirror_record` calls `job mirror` for it (`dispatch.sh:1186-1194`), which copies the round directory into the evidence root, so a file written beside the round is durable evidence without new plumbing.

## 2. The loop and its owners

One round, ten steps. The controller (goal 23, `internal/roundloop`) owns every transition: it runs each step, reads the records earlier steps wrote, and decides what happens next. The other goals are producers: each owns the shape and the words of one record. No two goals write the same record.

| Step | What happens | Producer of the record | Reads | Writes |
| --- | --- | --- | --- | --- |
| 1 brief | the seat writes the first brief; every later brief is composed | seat, then the controller | `rounds/<n-1>/findings.json` | the packet |
| 2 build | the delegate builds and runs its focused tests and full-package runs; it runs no bed in this turn until Wido's word on section 8, question 3 | delegate; the wrapper writes the package receipts | the packet | `return.json`, `package-runs/` |
| 3 review | the controller runs review conformance in-process; a refusal the builder can correct is recorded, not thrown | conformance (goal 28 for the boundary, goal 22 for the evidence) | the worktree | `diff.patch`, `review.json` or `review-refusal.json` |
| 4 read | the controller dispatches an independent reader on the diff; the step ends when the read is terminal and valid | independent read | `diff.patch`, `review.json`, the brief, the prior record | `read.json`, the critic register |
| 5 prove | the controller proves the round on the seat's engine, writing the retry decision the admission wants; every bed the run touches writes a report | proofrun; the harness writes the bed reports | the snapshot | `proof.json`, the attempt, `bed-reports/seat/`, `retry-decision.json` |
| 6 compare | carried inconclusive rows and every failed row are run on the accepted tree and again on the candidate as D12 says; declared inputs are compared; outputs are classified | trunk-versus-candidate | the prior record, failed rows, the brief's inputs | `compare.json` |
| 7 findings | every failure, read finding and undeclared difference becomes one finding with its producer's words and evidence | the controller assembles; the words are the helper's | steps 3 to 6 | `findings.json`, `findings/<id>.log` |
| 8 compose | the next brief is composed from the record | the controller | `findings.json`, `dispositions.md` | `next-brief.md` |
| 9 dispatch | the follow-up is dispatched with the composed brief, or the driver stops naming why | the controller (the driver, D2) | `next-brief.md`, the record | the next round |
| 10 close | the seat runs `validate critique-closed` and lands | seat | the register, the receipt | the landing |

What flows between the goals:

- The companion of row 24 hands step 7 the harness bed report with its `failures[]` (D6): one file per bed, one JSON line per failed assertion, the bed's own words, expected and observed with their digests, and one terminal record per scenario. The report's schema has one owner, that goal's first member; goal 22 extends it with the members it needs and owns the transport into the round (its page, D6).
- Goal 22 hands step 3 the package receipts and, once Wido's word allows delegate-run beds (section 8, question 3), the delegate's bed reports and `bed-assignment.json`; it hands step 7 the assignment so a finding says who ran the bed.
- The independent read hands step 7 its findings through the critic register. The record's `read` section is a projection of the register, recomputed whenever step 7 runs, never edited by hand (D4).
- Trunk-versus-candidate hands step 7 `onBase` and the assertion-level comparison for every failed row and its `compare` findings, and hands the landing the comparison it consumes (D11).
- Goal 23 owns the verb (D1), the driver (D2), the record (D4), the composed brief (D5) and the retry decision (D5). It never decides what a failure says, what a bed needs, or what a class is.

### 2.1 What stays manual, and why

Everything from a returned round to the next dispatch runs without a seat action (D2), except these points, each of which is doctrine or judgment today:

| Point | Who | Why it is the right call |
| --- | --- | --- |
| the first brief and its dispatch | seat | judgment: the goal, the design, the boundary |
| starting the driver, once per chain | seat, or the mission runner when it drives a chain headless (member 5b) | the driver is a foreground verb like `metasystem wait`; nothing starts a foreground process for the seat |
| adjudicating every material read finding | seat | doctrine: the orchestrator adjudicates every finding and returns accepted corrections (`SKILL.md:12`); the driver waits for the dispositions row (D2); section 8, question 1 offers accepted-by-default |
| a builder gap | seat | doctrine: a gap-stop reopens design with the gap as input (`docs/orchestration.md:46-47`); the driver stops and prints the gaps (D2) |
| a red on the accepted tree | seat | the exits are a trunk fix or a human carry (`docs/orchestration.md:150-156`); D12 marks it and prints both; the carry is human-only |
| an inconclusive finding the builder answered but could not fix | seat | the choice is a fix, a cleared line or a goal; the driver stops on the builder's answer and keeps the finding open until then (D2, D12) |
| a read that failed twice | seat | a round is not proved without a valid read (D7); the seat repairs the reader's lane or raises |
| a retry decision for a red attempt that is not this chain's | seat | the goal's newest failed attempt belongs to another chain or a cadence run; the engine cannot say why it failed |
| declaring a decision change | seat | a `Compare-Decisions` line says a goal permits the change; that is a design act |
| closing the register and landing | seat | certification and the landing are the seat's by doctrine (`docs/orchestration.md:38-42`); unchanged |

Not manual, because a mechanism owns it: an agent-correctable review refusal (D1), waiting for a pending read (D2), one retry of a failed read (D7), a reader withdrawing a finding it raised earlier (D7), the two clearing runs of a carried inconclusive row (D12), and the follow-up dispatch when every open finding is the builder's (D2).

## 3. Decisions

### D1. One loop verb, run by the engine, idempotent, with typed review outcomes

`metasystem job round-advance --root ROOT --job <implementer job>` (Go, `internal/roundloop/advance.go`; wired in `cmd/metasystem/dispatch_verbs.go` and the `job` family). It runs steps 3 to 8 of section 2 in order. Each step writes its record beside the round and one line in `rounds/<n>/loop.json`: the step, its execution identity, and its outcome. A step is skipped when `loop.json` has it with the same identity, so the verb can be run again after a crash or a wait and continues where it stopped.

Execution identity per step: review binds `candidateTree` and the boundary base tree; read binds the read subject digest (`readsubject.ReadSubject`); prove binds the proof identity the attempt records; compare binds both trees, every input spec, the digest of every seeded state file, both engines' digests, the clock anchor (D9) and the classifier version; findings and compose bind the digests of every source they read. A base tip that moved between two runs changes compare's identity, and compare runs again.

Step 3 distinguishes two outcomes. An agent-correctable refusal (a path outside the boundary, a ceiling exceeded, an evidence refusal of goal 22's D6) is written to `rounds/<n>/review-refusal.json` as typed rows (`code`, `item`, `words`), and the verb continues: steps 4 to 6 are skipped and named as skipped, step 7 turns every row into a `review` finding, step 8 composes. So a refused round still ends with a closed record and a composed follow-up, and no read is paid on it. An operational failure (the worktree cannot be snapshotted, a record is unreadable) stops the verb with the step's own message. `review.json` and `diff.patch` are written by conformance exactly as today (`conformance.go:421-427`). The typed rows come from a new function `validate.ReviewStage(root, job) (ReviewOutcome, error)` in `internal/validate/conformance.go` that the string interface (`:196-205`) keeps wrapping, so the shell gate's contract is unchanged; that boundary is member 2a's.

Exit codes: 0 the record is closed; 5 waiting on a job (the read is running; the message names it); 1 an operational failure; 2 a refusal of the verb's own inputs. Step 5 refuses `READ_MISSING` when no read was dispatched for the round and the goal's tier has a critic root, and `READ_NOT_VALID <outcome>` when `read.json` is present but its outcome is not one of `clean`, `findings`, `redundant` or `tier-1-no-read` (D7). A round is never proved on a read that did not happen or did not finish.

The steps are a Go table, one row per step, with the producer's package behind it. Goal 23 lands the table with review, prove, findings and compose. Compare registers its row in member 4c, the read registers its row in member 6a. A row that is not registered is skipped and named in the verb's output, so the loop works from the first member and grows.

### D2. The driver: what owns the transitions, and where it stops

`metasystem job round-drive --root ROOT --job <root job>` (Go, `internal/roundloop/drive.go`). It is the one component that owns automatic advancement. It is a foreground verb like `metasystem wait`, started once per chain by the seat, or by the mission runner when it drives a chain headless (member 5b adds that call; today the runner only spawns `dispatch.sh`); it registers a wait row on the job it waits for, so the steward sees it like any waiter, and it is never a daemon. Its loop:

1. Wait for the current implementer round's terminal event through the wait machinery (`metarun.Wait` with the `--job` selector, the code `wait_verb.go:266` builds).
2. Run `round-advance`. On exit 5, wait for the named job's terminal event and run it again. When the read step reports `outcome: failed` for the first time in the chain, dispatch the read once more (D7) and wait for it.
3. Read the return and the closed record, then take the first branch that applies:
   - `BUILDER_GAP`: the return's `gaps[]` carries an entry that is not an evidence token (`bed:<bed>`, `package:<pkg>`) and not an inconclusive answer; stop with exit 3 and print the gaps. A gap reopens design by doctrine; the seat answers it in a judgment brief or reopens the design.
   - `INCONCLUSIVE_ANSWERED`: the return's `gaps[]` carries `inconclusive:<id>`; stop with exit 3 and print the id and the builder's words. The seat chooses a fix, a cleared line or a goal (D12); the finding stays open until then.
   - `READ_FAILED`: the round's read failed twice; stop with exit 3. No proof was run.
   - `READ_FINDINGS_UNADJUDICATED`: the record has a material `read` finding with `disposition: none`; stop with exit 3 and print the finding ids. The seat writes the dispositions rows (`SKILL.md:49-58`) into `rounds/<n>/dispositions.md` and runs the driver again; step 8 then carries every `accepted` finding as work and marks every `refuted` one. Under section 8, question 1 option (a) this branch is removed and the composed brief carries the findings as accepted by default.
   - `DECISION_UNDECLARED`: a `compare` finding no `Compare-Decisions` line declares; stop with exit 3.
   - `RETRY_DECISION_NEEDED`, the chain's round member spent, a cap or budget stop: exit 3 with the line.
   - `BASELINE_RED`: the record has no finding with status `open` or `inconclusive` and at least one `baseline-red`; stop with exit 6 and print, per red group, the two exits of D12.
   - green: the record is empty, or every finding is `refuted` or `cleared`; exit 0.
   - otherwise every open finding is the builder's (`bed`, `go`, `review`, `inconclusive` not yet answered, and `read` findings with `disposition: accepted`): call `dispatch.sh follow-up` with the composed brief and no seat brief (D5), then go to step 1.

A stop is a message, not a wedge: the seat does what the line names (a dispositions row, a `Compare-Decisions` line, a retry decision, a carry, a raise, an answer to a gap or an inconclusive) and runs `round-drive` again; the driver picks up from the records. The driver never proves, never composes and never launches an adapter itself: it calls the verbs the seat can call by hand, `round-advance` and `dispatch.sh follow-up`, so every step is reproducible from the terminal.

The reaper is not the driver. It marks a round terminal and mirrors it; running beds from inside it would make the reaper own a proof attempt and a delegate dispatch. The wait verb is not the driver: it observes and executes nothing (`wait_verb.go:266-330`), and this page does not change that.

### D3. The seat's proof writes the same bed reports the delegate writes

`prove-round` sets `METASYSTEM_BED_REPORT_DIR` for its `test run` to `<attempt dir>/bed-reports/` and, on return, copies the reports into `rounds/<n>/bed-reports/seat/<bed>.json`. The harness writes a report whenever the variable is set (D6, this program's first member); the seat's run gets the same file for nothing. The delegate's own reports, when Wido's word allows delegate-run beds, stay under `rounds/<n>/bed-reports/<bed>.json` (goal 22's transport). Step 7 reads both and marks each finding with who ran the bed.

For a Go group the attempt's `GroupResult` names the failed tests and the log (`test_result.go:30-70`). For a section group the bed report is the structured source; when a bed has no report (a bed not yet on the harness), step 7 falls back to the harness's failed-scenarios block in the section log (`fixture-bed-scenarios.sh:191-201`), whose shape is fixed, and for a sequential bed to the bed's last stderr lines with `words` only.

The `assert_` family keeps going under errexit, which every process bed enables (`set -euo pipefail` at line 2 of each): it records the failure, prints the block, and returns 0, so a standalone `assert_equal` statement never ends the scenario. The record is durable: one JSON line appended to the file `METASYSTEM_BED_FAILURES` names, or, when the variable is unset, to `${TMPDIR:-/tmp}/metasystem-bed-failures.<pid>.jsonl`, whose path the helper prints once at the first failure. An ownership helper that returns 1 before killing must still refuse to kill after conversion: it converts to `require_`, or its caller checks the return; the migration reviewer's checklist names every kill site.

`<what>` is unique within a scenario, by construction: the helper keeps the labels it has recorded for the scenario and, on a repeated label, records a `duplicate-label` failure naming both call sites instead of a second record under the same label. A migration that converts two sites with the same verdict text gives them different labels; the audit does not check that, the helper does at run time and the bed goes red on the first run.

Every failure prints exactly this to stderr:

### D9. Compare: materialising the accepted tree beside the candidate, and the clock

`--base` defaults to `refs/remotes/origin/main`, or `refs/heads/main` in local mode, the rule the landing uses (`carried.go:59-62`); `--tree` is the candidate. Both are resolved to trees and each is checked out with `NewDetachedWorktree` (`detached.go:28`). Each side gets its own engine from `go-build.sh --out <side>/bin/metasystem --trimpath` run in that side's worktree. The accepted side's engine is kept at `artifacts/agents/compare/engines/<tree>/metasystem` and reused while the base tree is the same; `artifacts/agents/compare` joins the reserved directories (`internal/evidence/gc.go:44-52`). Each side's environment is scrubbed of the git steering family (`gittree.ScrubbedEnviron`) and gets its own `TMPDIR` and `GOTMPDIR`. `GOCACHE` is shared.

Clock. The goal's DONE says both sides run "with the same input and clock". What the code has is in section 1.3: fourteen seams, 343 direct `time.Now()` sites in 132 files, and eighteen beds that read the host clock from the shell. Revision 3's base-per-process was wrong: a second engine process started inside a row would restart at the base and lose the elapsed time. The anchor is therefore a constant offset shared by the whole process tree: `METASYSTEM_CLOCK_ANCHOR=<virtual instant>@<host instant>`, set once per side by `test compare`, and `internal/clock.Now()` returns the host clock plus the constant difference between the two instants. Every process that reads the variable sees one timeline; elapsed values are real; both sides start at the same virtual instant. Two things bound what that delivers, and the member's first unit is the fixture that shows them rather than more prose (fixture first): `TestSharedClockAcrossProcesses` starts two engine invocations one second apart under one anchor and asserts the second reads one second later on the virtual timeline; and `TestClockInventoryRatchet` counts direct `time.Now()` sites outside tests against `internal/clock/allowlist.txt`, refuses growth, and prints the count. A shell clock is not the engine's: `test compare` scans a `row:` input's bed and a `cmd:` input's script for `date`, `$SECONDS` and `$EPOCHSECONDS` and marks the input `clock: host`; a time-dependent decision difference on a `host`-clock input, or on any input while the ratchet is above zero on its paths, is reported `inconclusive`, never causal, and `compare.json` says why. Masking alone does not implement the clause; the anchor plus the ratchet does, when the ratchet reaches zero.

### D10. Compare: how outputs are classified, per input contract, and the first surface

Every record of D8 gets one class from the contract of the input that produced it. A contract is a Go value in `internal/compare/contract.go`: the decision fields, the nondeterministic fields, and whether unknown fields fail closed. The default contract for `cmd:`, `row:` and `stop:` inputs:

| Class | What lands in it |
| --- | --- |
| `decision` | an exit status; a JSON member named `decision`, `shouldBlock`, `blockSource`, `idleRefusal`, `countSpent`, `class`, `causeCode`, `sufficient`, `status`, `state`, `outcome`, `action`, `valid`, `verdict`; any token that is a row in `refusal.Rows`; a `stop response decision=` or `outcome=` line; a `section <id> pass|fail|gated` line; every record of a surface |
| `evidence` | only what the contract declares nondeterministic: RFC 3339 timestamps, `elapsed=Ns` and `(Ns)` durations, `startedAt`, `endedAt`, `durationMs`, ULIDs, pids, session ids, and the scratch paths the sides created |
| `text` | `systemMessage`, `reason`, `display`, diagnostics, a `Task:` line, and any non-JSON line that matches no decision pattern |
| `unclassified` | every other JSON member, every digest and every path the contract did not declare |

An `unclassified` difference is treated like a decision difference: refused unless `--permit unclassified`. A contract may extend the lists; a surface row is its own contract. A JSON line is parsed and classified per member. Evidence values are masked to `<ts>`, `<n>s`, `<ulid>`, `<pid>`, `<tmp>` before the diff. Per input and per class the report lists the records present on one side only. `compare.json` beside the round carries `base`, `candidate`, the inputs with their `clock` marks, their contracts, their classified differences, both sides' logs, both engines' digests, the clock anchor and the permitted classes. Exit 0: no difference. Exit 3: differences only in permitted classes. Exit 1: a difference in a class that is not permitted.

The surfaces table, `internal/compare/surfaces.go`, has one row at first: `stop-decisions`, ported from the scratchpad script verbatim. Lines are normalised the way the script does and compared per file as sets: `added` is reported, `removed` refuses without a declaration, a change is a removal plus an addition. The two beds' compatibility rows keep matching. A future surface is a row with its files and patterns, never a script.

### D11. Compare: the declaration a landing carries, and the landing gate

In a round, the implementer brief may carry `Compare-Permits: text, evidence` (the default when absent), `Compare-Decisions: <input>=<goal id>` lines, one per decision change the design permits, and `Compare:` lines naming dynamic inputs, next to goal 28's `Boundary:` header. Step 6 marks every decision or unclassified difference that no line declares as an open `compare` finding.

At a landing, `land.sh --compare rounds/<n>/compare.json [--compare-permits CLASSES] [--decision-change <surface>=<goal id>]` passes through `commit.sh` to `landing observe`. `landing observe` re-runs every surface over its base tree and the candidate (static, well under a second), and consumes the round's `compare.json` for the dynamic inputs: it refuses `compare-stale` when the file's `base` is not the landing's base tree or its `candidate` is not the staged tree. It refuses `decision-change-undeclared` when a surface has removals or changes and no declaration names it, when the declaration names a goal that is not on the ledger at the candidate tree, or when the consumed comparison has a decision or unclassified difference outside the permitted classes. The codes join `knownRefusalCode` (`internal/landing/promotion.go:114`). The commit gets the trailers `Compare-Permits: <classes>`, `Compare-Decisions: <surface> goal=<id> moved=<n> digest=<sha256 of the moved set>` and `Compare-Digest: <sha256 of compare.json>`. Additions are printed and never refused.

The fast gate (`go-gate.sh:502-505`) runs `test compare --input surface:stop-decisions` against the base after the refusal register when the checkout has a remote main, and prints the moved lines. The refusal that binds is the landing's.

### D12. Compare in the round: the base re-run, baseline-red by assertion identity, and inconclusive

Step 6 runs, in this order and bounded: every surface (static, always); every `inconclusive` finding carried from the previous record, as its `row:` or `cmd:` input, run twice on the candidate, outside the cap, so a carried finding always gets its clearing runs; then every failed bed scenario of this round's proof as `row:` and every failed Go test as `cmd:go test ./<package> -run '^<Test>$'`, up to `compare.max-inputs` (default eight) dynamic inputs, the rest listed `not-compared`; then every input the brief names in `Compare:` lines. For a re-run failed row the record says what the accepted tree did, at the level of the assertion, not the scenario.

The comparison is by assertion identity, which D6 makes unique: the pair scenario and `what` names one assertion, and the record carries `expectedDigest` and `observedDigest` over the full values. Both runs of a `row:` input write helper records. A finding of the candidate run is `baseline-red` only when the base run holds a record with the same `what`, the same `expectedDigest`, and an observed value that is either the same digest (`observedMatch: exact`) or equal after masking only the classes the input's contract declares nondeterministic (`observedMatch: masked`); the brief prints which. A masked match is a match modulo pids, timestamps and scratch paths, and nothing else, because masking never touches an undeclared value (D10). Every other failure of a scenario that is red on both sides stays `open`, with `onBase: fails-other` and the base run's records beside it, so a regression the candidate adds to an already-red scenario cannot hide behind the scenario's colour. A Go failure is compared the same way when it went through the helper (package, test, `what`, digests); one that did not stays `open` with `onBase: fails (test)`. A bed without helper records (not yet migrated, or sequential) cannot be compared at that level: its finding stays `open` with `onBase: fails (scenario)` and the brief says the scenario is red on base too and the assertion could not be matched. That is fail-closed on purpose, and it is one more reason the migrations follow the helper.

The three outcomes of a failed row:

| Candidate | Base | Second candidate run | Status | What the brief says |
| --- | --- | --- | --- | --- |
| fails | the identical failure | not run | `baseline-red` | red on the accepted tree too; not this round's; the base log is beside the candidate log |
| fails | passes, or fails differently | fails | `open` | the accepted tree does not fail this way; here is the byte difference in the engine's output |
| fails | passes | passes | `inconclusive` | not reproduced on base, reproduced once on yours: fix the cause, or return `inconclusive:<id>` in gaps with what you found and the seat decides; a flake is fixed, never retried (R-103-m1e) |

The second candidate run exists because one asymmetric result is not a cause. It is diagnostic only and is never recorded as a green. An `inconclusive` finding is blocking and persistent: it stays in every later record of the chain with its `firstSeen` round until its input passes on both of its clearing runs in a later round's step 6 (the two runs above, scheduled first and outside the cap), or the seat writes the cleared line for it. The driver dispatches with it in the brief and never drops it. A builder that answers it with `inconclusive:<id>` in gaps has answered, not cleared: the driver stops with `INCONCLUSIVE_ANSWERED` (D2) and the seat decides between a fix, a cleared line and a goal (section 2.1).

The completion path for a red on the accepted tree. A `baseline-red` finding is not the builder's: the summary counts it apart, the brief lists it last under its own heading, and the driver does not wait for the builder to fix it. When the record has no `open` or `inconclusive` finding and at least one `baseline-red`, the driver stops with exit 6 and prints, per red group, the two exits that exist today: open the trunk defect as its own goal with the blocker named (goal 6's rule; the driver prints the `goal open` line with the group, the base tree and the evidence path), then fix it on trunk and re-run the driver, whose compare identity changes with the base tip and re-runs the row; or have Wido issue `goal carry group:<id>` and land with `land.sh --carried <opid>` (`docs/orchestration.md:150-156`), which is human-only and stays so. The proof is still insufficient on that group whichever tree; this page adds no landing rule and no new authority. Retry admission is unchanged: the next proof of the chain carries the engine's retry decision with cause `baseline-red: <group>` and `compare.json` as evidence.

## 5. Risks

- The driver dispatches a follow-up the seat would not have: it dispatches only when every open finding is the builder's, every material read finding has a disposition, and no gap is open; every dispatch is a job record the seat sees.
- The read and the proof run in series, so a round's wall time is their sum; the contract chose the order. A failed read costs one retry before the round stops.
- A record composed from a flaky bed sends the builder after a defect that is not theirs: the assertion-level base comparison, the second candidate run and the persistent `inconclusive` status answer it.
- The composed brief grows with the number of failures. The inline bound truncates to ids and the file path; a builder with sixty findings has a member-size problem, which row 27 owns.
- Two engine builds per compare: the base engine is cached by tree; the candidate's build is seconds on the shared cache; dynamic inputs are bounded, and carried inconclusive rows are the only inputs outside the bound.
- The surface is a text extraction: a decision moved into a file the table does not list is invisible. The table is in Go and the audit fixture asserts every listed file exists.
- The audit's allowlist can be raised by a landing: it is a text file in the tree, so raising it is a visible diff the read's threat model names.
- The `assert_` family continues past a failure, so a later assertion can fail on the consequences of an earlier one and add noise. The `require_` family exists for exactly the preconditions where that happens.
- The clock ratchet starts at 343 sites; until it reaches zero on a path, a time-dependent difference on that path is `inconclusive`, never a false pass and never a false cause.
- Duplicate labels turn a bed red on its first run after migration; the migration reviewer's checklist includes a label scan per scenario.

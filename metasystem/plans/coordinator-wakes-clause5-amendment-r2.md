## 7. Amendment: how clause 5 is measured (revision 2)

Revision 2 for the m1b seat on 2026-09-16, folding the Codex critique of revision 1 (`metasystem/plans/coordinator-wakes-clause5-amendment-critique-r1.md`, eleven findings, two critical). It settles the wire behind lines 228 to 231 of this page and changes nothing that members one to three landed. Every citation below was re-read against the tree at a64d4408a.

Three things changed from revision 1. The consuming request is no longer inferred from the adapter's `blocking` answer plus time order; it is proven by a token the engine mints at return and the resumed turn echoes. Every edge of the latency bracket is now on the host's boot clock, so a wall-clock step cannot produce a false pass. The turn-end witness, the usage-key change and the observer change are withdrawn.

Clause 5 says: for each event, measure durable publication to the first resumed model turn consuming its wait result; every sample under 60 seconds; notification time, command return time and averages are not substitutes (`metasystem/plans/coordinator-wakes-on-events-not-polls-design.md:228`). Line 216 fixes the source of inference starts (adapters, through `metasystem/internal/usage`; missing data is unavailable, never estimated) and line 219 says a turn is one inference request.

### 7.2 The carrier: an engine-minted token, echoed by the resumed turn

Decision. At every `finishV2`, the waiter mints a `resumeToken` with the nonce helper (`mintNonce`, called at `metasystem/internal/run/waiter.go:876`), stores it in the result (`WaitResult.ResumeToken`), persists it with the row's result, emits it in `wait-returned` and prints it: the plain `WAIT` line gains ` resume=TOKEN` and a second line `Run first: metasystem wait consumed --root DIR --token TOKEN`; the JSON result carries `resumeToken` and `consumeCommand`. The token exists nowhere before the return.

The resumed turn's first act is `metasystem wait consumed --root DIR --token TOKEN`. That verb authenticates the caller exactly as `wait` does (`metasystem/cmd/metasystem/wait_verb.go:141` to `:160`), samples the host boot clock, and appends `wait-consumed` with a checked write (7.3). This is the consumption event line 215 asks for.

Why this is a definition and not an estimate. The request that produced the echo had the wait result in its context: it knew a value minted at the return and delivered only inside the result. So the first consuming request began at or before the echo. Nothing about tool-call foregrounding, result delivery order or the runtime's internals is assumed; the row's `delivery` answer is recorded and unused. A runtime that backgrounds the call, a runtime that interleaves an automatic request, and a runtime with no hook and no usage stream all get the same rule from the same record.

What the echo bounds. The echo is an upper edge on the start of the consuming request: it comes one model response after that request began (the doctrine makes the echo the first act, so the slack is one response, not a turn). The clause's endpoint is the request start; the sample is `consumedUpper` = the echo, and a pass at the echo is a pass of the clause. A fail at the echo is reported with the reason naming the edge; it is not refuted by any accelerator (7.4).

Ownership of the echo. The echo is accepted when the caller's main equals the row's `mainId` and the caller's effective runtime session equals the row's `runtimeSession`, or equals it through the announcement's one recorded predecessor (`metasystem/internal/lease/classify.go:24`); the second case records `sessionChanged` true. A resume, clear or compaction between return and echo is therefore lawful and measured. Any other caller is refused with `ExitWaiterBusy`.

Validation of the token. The verb accepts a token that matches the retained result of a row of the caller's main (rows keep their result until the key is registered again, `metasystem/plans/coordinator-wakes-on-events-not-polls-design.md:74`) or a `wait-returned` event of the caller's main carrying that token. When neither exists the verb refuses with `ExitInvalidWait` and emits, best-effort, `wait-consumed` with `verdict` `token-unknown` and no stamps, so the loss is counted (7.5). The residual case is a dropped `wait-returned` append followed by a replacement wait before the echo; the doctrine's echo-first rule keeps it out of normal operation and `wait measure` counts it when it happens.

Replays. `ResumeWait` replays a retained result with a fresh `returnedAt` (`metasystem/internal/run/waiter.go:1172`). A replay prints the retained token; its `wait-returned` carries `mode` replay and is not a sample source. The sample of a replayed token uses the first echo per token and the original return's stamps, so a result that went unconsumed until a replay is measured with its honest latency.

What each side supplies. The adapter supplies nothing new: the session at session start and Stop (`metasystem/scripts/agents/supervision-hook.sh:1552`, `:1569`, `:1073` to `:1075`), the existing `wait-delivery` answer, and the usage stream its reader already parses. The engine mints, persists, prints, authenticates and records. The seat's model runs one small verb per wait. No transcript text is matched; no notification stamp is used; no mean appears.

Durability, exactly once. `wait-consumed` is written by a new `Emitter.EmitChecked` that returns the registry refusal, the cap overflow or the write error instead of dropping (`Emit` at `metasystem/internal/events/emit.go:43` stays best-effort for everything else); the verb exits `ExitWaiterIO` with `consumption not recorded; run the command again`, so the seat retries. Duplicates of one token are lawful and `wait measure` keeps the earliest `consumedBootNanos`. `wait-returned` is emitted in the waiter's own process between the persist and the print: if the append fails or the process dies first, the model never receives the result, so no echo and no sample is expected, and the row still holds the token for a later replay. `wait-published` is a tightener: dropped means a looser bracket, repeated means the window rule of 7.4 picks one. `wait measure` emits nothing, so concurrent runs cannot duplicate anything.

### 7.4 The clocks, the edges and the rule

Every edge is a boot-clock stamp written on the seat host, and a sample is comparable only when every stamp it uses carries the same `bootId`. Wall stamps are printed in the report and never subtracted. This is what closes finding 2: a wall step before, during or after the return changes no edge, because no edge is a wall value.

Stamps and where they come from:

- `registeredBootNanos`: the registration's boot sample (`metasystem/internal/run/waiter.go:850`), stored in a new optional row field `registeredBootNanos`.
- `prevObservedBootNanos`: the row's `lastObservedBootNanos` (`:163`) as it stood when `finishV2` was entered; the loop rewrites it after every pending observation (`:765` to `:766`), so it is the last observation that did not see the event.
- `observedBootNanos`: the loop iteration's own boot sample (`:696`), passed into `finishV2`; for an at-entry finish (`:983`) it is the registration sample.
- `returnedBootNanos`: sampled inside `finishV2` beside `now` (`:644`). `finishV2` gains one argument, `finishStamps{AtEntry bool; ObservedBootNanos int64}`, supplied by every caller.
- `beganBootNanos`, `publishedBootNanos`: the owner's pre-write sample and `NotifyWaiters`' post-write sample (7.3). The three Go owners sample before their durable write: the job transition that calls `notifyJobWaiters` (`metasystem/internal/dispatch/record.go:37`), the launcher before `FinalizeAttempt` (`metasystem/internal/proofrun/launcher.go:488`), and the publish that calls `hintConfirmedWaiters` (`metasystem/internal/goal/txn.go:500`). The landing script samples with a new `metasystem util bootclock` (prints `bootId nanos`, beside `util sha256` used at `metasystem/scripts/agents/supervision-hook.sh:1567`) before its landing write and passes `--began-boot-nanos N --boot-id ID` to `wait notify` (`metasystem/cmd/metasystem/wait_verb.go:234`).
- `consumedBootNanos`: sampled by `wait consumed`.

Edges, for one sample:

- `publishedLower` = `beganBootNanos` when the matching `wait-published` carries a non-zero one, else `prevObservedBootNanos`. Both are true lower edges: the publication was not durable before the owner began writing, and it was not visible at the previous observation. The previous observation is the loose one on the fifo route; it is the whole reason the owners sample before writing.
- `publishedUpper` = the smaller of `observedBootNanos` and the matching `wait-published`'s `publishedBootNanos`; `observedBootNanos` alone when there is none.
- The matching `wait-published` is the one for the sample's `kind` and `targetId` with the same `bootId` whose `publishedBootNanos` lies in `(prevObservedBootNanos, observedBootNanos]`; when several lie there the earliest is taken; when none does the sample has no tightener and says so. A `wait-published` with another `bootId` is recorded as `cross-host` and never used.
- `consumedLower` = `returnedBootNanos`. A result cannot be consumed before it was returned.
- `consumedUpper` = `consumedBootNanos` of the earliest `wait-consumed` for the token.
- `latencyUpperNanos` = `consumedUpper` minus `publishedLower`; `latencyLowerNanos` = max(0, `consumedLower` minus `publishedUpper`). The report prints both, their difference as the uncertainty, and which edge supplied each.

Validation before arithmetic, each failure an unavailable reason:

- `clock-not-comparable`: any used stamp is zero, or the `bootId`s of the return, the echo and the used `wait-published` differ.
- `stamp-order`: `registeredBootNanos` <= `prevObservedBootNanos` <= `observedBootNanos` <= `returnedBootNanos` <= `consumedBootNanos` fails, or `publishedLower` > `publishedUpper`.

The rule. A sample passes when `latencyUpperNanos` is below 60 seconds. It fails otherwise with reason `witnessed-above-60`; the report names the edge that made it loose (`lower-edge-prev-observation` when no owner sample was available, `echo-after-response` otherwise). There is no mean; the report prints raw samples and the maximum per runtime (`metasystem/plans/coordinator-wakes-on-events-not-polls-design.md:230`).

The usage stream is a tightener only. For a sample whose runtime reader reports `per-call` (`metasystem/internal/usage/calls.go:16`), `wait measure` first runs ingestion, `usage.LatestCall` (`metasystem/internal/usage/calls.go:93`) with the `ReadOptions` the steward builds for its own call (`metasystem/internal/steward/context.go:121`; the builder exports that construction if it is not already reachable), for (`runtime`, `runtimeSession`); then reads `Calls` (`metasystem/internal/usage/cursor.go:222`) from `returnedAt`. The request that produced the echo is the last main-chain sample with `at` at or before `consumedAt`; sidechain records are already skipped by the reader (`metasystem/internal/usage/cursor.go:151` to `:154`). The report prints that sample's `at`, `ordinal`, `invocationId`, the wall gap to the echo as `responseBeforeEchoMillis`, and `compactionBetween` when a `Marker` lies between `returnedAt` and it. None of this touches the verdict: a usage stamp is a harness wall value with no boot pair and, per this repository's rule, an accelerator may tighten a report and may never carry a result. Absent cursor, `per-invocation`, `none`, an ingestion error or a benign reason (`metasystem/internal/steward/context.go:338` to `:349`) all print `usage: absent` with the reason and change nothing. This is finding 8 folded and the reason the usage-key change of revision 1 is withdrawn: a cursor registered under a key other than `runtimeSession` (`metasystem/internal/steward/context.go:217`) means the tightener is absent, not that the sample is.

### 7.5 Which returns are samples, and the unavailable reasons

The universe is the set of `wait-returned` events with `state` ready and `mode` register, renew or takeover, joined by `resumeToken` to `wait-consumed` events with `verdict` ok, plus any `wait-consumed` whose token has no return event. Classes:

- sample: a ready return with an echo, or an echo whose stamps came from the row (`stampsFrom` row, `returnEventMissing` true recorded, not disqualifying).
- `already-published`: `atEntry` true; there was nothing to wake. Counted, listed, excluded from the 60-second rule. Late registration hiding latency is caught by the polling proof over the full stream (`metasystem/plans/coordinator-wakes-on-events-not-polls-design.md:231`).
- not sampled: deadline, failed and interrupted returns; replay returns. Counted and listed.
- `pending-at-cut`: a `wait-registered` with no `wait-returned` before the measurement's `--until`. Counted; not a sample and not a failure.
- `unavailable: no-echo`: a ready return with no `wait-consumed` before the cut. The seat did not run the echo; the legs require zero of these.
- `unavailable: token-unknown`: a refused echo (7.2).
- `unavailable: clock-not-comparable`, `unavailable: stamp-order`: as 7.4.

Clause 5 is unproven for a runtime while any unavailable sample remains; unavailable is never filled in. Revision 1's `no-wait-returned`, `delivery-not-blocking`, `session-key-mismatch`, `no-usage-cursor`, `no-witness-before-stream-end`, `clock-drift` and `usage-reason-unknown` are all withdrawn: each either cannot happen under 7.2 or is now a report line rather than a verdict.

### 7.6 The verbs and the fixtures

`metasystem wait consumed --root DIR --token TOKEN [--json]`, dispatched beside `wait notify` (`metasystem/cmd/metasystem/wait_verb.go:61` to `:66`). Exit 0 when recorded (prints the `wait-consumed` line or its JSON), `ExitInvalidWait` for bad arguments or an unknown token, `ExitWaiterBusy` for a caller that is neither the row's session nor its recorded predecessor, `ExitWaiterIO` when the checked append failed.

`metasystem wait measure --root DIR [--since RFC3339] [--until RFC3339] [--runtime NAME] [--json]`. It reads the state root's `events.jsonl` (`metasystem/internal/events/emit.go:124`), runs the usage tightener of 7.4, builds the samples of 7.5 and prints per runtime (grouped by the events' own `runtime` field; `--runtime` only filters): the raw samples with both edges, the uncertainty and the edge names; the maximum; the counts by class; the unavailable list with reasons; the usage tightener column. Exit 0 when every sample passed; 1 when any failed; 2 when none failed but any is unavailable; `ExitInvalidWait` on invalid arguments. The logic lives in `metasystem/internal/usage/waitmeasure.go` so the fixture this page reserves at section 5 row 5 keeps its owner file. The two real legs (`metasystem/plans/coordinator-wakes-on-events-not-polls-design.md:246`) end by running it and keep its JSON.

`wait notify` gains `--began-boot-nanos N --boot-id ID`; `metasystem util bootclock` prints `bootId nanos` from `identity.BootClock`.

Doctrine, in `metasystem/docs/orchestration.md` and the wait section of `metasystem/docs/design/turn-verdict-delivery-contract.md:60`: a `WAIT` line carrying `resume=` is answered first, before any other act, by the printed `wait consumed` command; nothing else is asked of a runtime or an adapter; the cost is one small verb per wait return.

### What this measures, plainly

On every runtime the sample is: the owner's pre-write boot instant, to the boot instant at which the resumed turn's first act reached the engine, both on the seat host's monotonic clock. That is an upper bound on the clause's own quantity, tight to one model response. It is the same rule with the same records for a runtime with a hook and a usage stream and for one with neither; the accelerator only annotates. If the real legs fail the 60-second bound only by the response time before the echo, the choice is to change the bound or to move the endpoint to the request start, and the second is not available from engine records alone on any runtime; that decision is Wido's, and this amendment does not pre-empt it by measuring something looser.

# role-names-say-what-the-role-does

- State: queued
- Risk: severity=2 novelty=2 exposure=3 accumulation=2 basis="severity 2: a misread role selects the wrong model for a job, which is a correctness risk on a design-bearing chain rather than a cosmetic one, but nothing wedges and nothing is lost; novelty 2: a rename across tracked configuration keys, a validator assertion, role definition files, refusal text and docs, with a compatibility path because the keys reach adopters; exposure 3: every dispatch, every roster resolution and every reader of the orchestration docs; accumulation 2: it costs a clarification every time the roster is discussed and it has already produced one wrong-model risk in conversation"
- Tier: 3
- Intent: Role names describe where a role runs instead of what it does, and the same name means two different jobs. The clearest case: the role called 'implementer' is the DESIGN AUTHOR in design mode and the CODE WRITER in implement mode, selected by the same word through the configuration key mode.design.role.implementer. On 2026-09-09 that cost Wido a direct question, in his words: 'Wait, I'm confused. We are using Sol for the implementation or not?', asked after being told the design lane moved to Fable 5.1 under R-89-m1b. The answer was yes, Sol still implements, and nothing about code implementation had changed; the only thing that moved was who authors designs. The same overloading shows elsewhere: design-critic resolves in implement mode too, and code-critic critiques implementations while design-critic critiques designs, so one pair is named by its subject and the other by its object. This is the one-word-two-behaviours defect shape that has already cost this program repeatedly. DONE means every role has one name and one meaning, the name states what the role produces rather than which mode it runs in, and the role definition files, the tracked configuration keys, the validator assertion, docs/orchestration.md, the delegate verb's role validation and every refusal message that names a role all agree; the rename carries an explicit compatibility path because the configuration keys are tracked and reach adopters.
- Origin: main
- Next step: Start from the concrete collision: bin/metasystem job resolve-roster --conf metasystem.conf --mode design --role implementer returns the DESIGN AUTHOR, and the same command with --mode implement returns the CODE WRITER. Then inventory the vocabulary before proposing anything. The role definition files are scripts/agents/roles/ and today hold behavior-judge, code-critic, design-critic, implementer, investigator, orchestrator, steward-continuation, verifier and warden. The delegate verb in cmd/metasystem/delegate.go validates roles and special-cases three of them for --reviews (code-critic, warden, verifier) and one for --outputs and --design (design-critic), so the names carry behaviour, not just labels. The tracked configuration keys are mode.design.role.implementer.runtime and mode.design.role.implementer.model.codex in metasystem.conf, asserted verbatim in scripts/validate-metasystem.sh around line 1214 and described in prose in docs/orchestration.md around line 104. Propose names that say what the role PRODUCES rather than which mode it runs in, and check each candidate against every one of those surfaces plus the refusal messages that name a role. Because the keys are tracked and travel to adopters, say explicitly whether old key names keep working for a period and how a checkout with an old local override behaves during it; a silent change of meaning on an inherited key is worse than the current confusion. This is a design decision about vocabulary with adopter reach, so it goes to the design lane before any rename lands.

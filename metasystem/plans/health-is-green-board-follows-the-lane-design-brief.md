HEALTH-CARD-UPDATE-RACE. `board.LiveCard` reads without the seat lock (`internal/board/card.go:433-454`) and the write only carries history (`internal/board/card.go:285-347`), so a seat's `build` or `released` written between the lane's read and its write is overwritten. Make the lane's write a conditional update decided on the card as it stands under the seat lock: a board primitive that reads, decides and writes inside the lock the write already takes (for example `board.Update(home, seat, goal, func(current Card) (Card, bool))`). The decision runs on the current card: terminal or gone means no write; process-bound means only the count; otherwise the stage change. Add the red test: a card that moved between finding it and writing it is not overwritten.
2. HEALTH-LANDED-LEGACY-CARDS. Terminal `landed` cards written by the hand route exist today and were never released (`internal/goal/verbs.go:6341-6353`); making `landed` non-terminal turns them into unclaimed live cards the bridge never expires (`internal/board/bridge.go:405-420`). Recommended fix: leave `landed` terminal with its hand-route meaning, and have the lane move a held card to a stage that already waits without stalling and is not terminal (`claimed-idle`, or `joined` while a newer hand-in waits), carrying the count; drop the open question on `landed`. If you keep a non-terminal `landed`, say how cards already landed at deployment end, and test it.
3. HEALTH-LANDED-SUPERSEDED-HANDIN. `plain.Waiting` excludes superseded lines (`internal/landing/plain/queue.go:160-205`), and the lane can push a HEAD that merged an older sha after a newer hand-in superseded it. Select the cards to write by containment over every hand-in line that is not returned (waiting and superseded): head contains the sha, old main does not. Keep the channel message's selection unless you say why it should change too (then it is a moved effect). Add the superseded case to the push test.
4. HEALTH-LANDED-COUNT-LIFETIME. Every stage writer builds a fresh card (`internal/launch/launch.go:845-866`, `internal/launch/unit_run.go:587-596`, `internal/proofrun/launcher.go:1127-1148`), so the next write drops the count. The board's write carries `Landed` forward from the previous card of the same claim, as it carries the stage spans, so no other writer needs to know the field; only the lane's update sets it. Add the red test: a `build` write after a landed count keeps the count.
5. MOVED-EFFECTS-NO-ROWS. The moved-effects inventory must use the header `| Effect | From | To | Code |` with existing backticked repository paths in Code and a named old owner; "nobody" is a weak owner and fails (`internal/validate/movedeffects.go:27-31`, `internal/validate/movedeffects.go:95-133`). List only effects whose owner moves; a new effect (the lane writing a card, the count) is not a move and belongs in section 3. If no owner moves, write the line `No owner moves.` under the heading.

## Decisions the seat has taken (build on them; argue only with evidence)

- D1 Step 1 is the lane's landing reaching the card. When `landing push` changes main, each hand-in it put on main (the set `landedMessage` already computes) moves its goal's card out of every progressing stage, and the card states how many of the goal's units are on main. The lane's push is the writer: it owns the transition, and it writes the cards in the same act as its push record, as the channel post and deploy are. A card that cannot be written never fails or undoes the push; it is reported the way a failed channel post is.
- D2 The card says "N units landed" as a number on the card (identifiers and numbers only, fact 1), shown by the text view and by the Fleet page's Doing column. You decide what N counts (unit commits through the landed sha, or hand-ins landed) and how the lane computes it from what it already has (the queue line, the merged branch, main); say why.
- D3 You decide the stage a landed card takes, with one constraint: it is not progressing, so it never reads `stalled`. Cover both cases: the seat still holds the claim (more units will be built; the next build moves the card on as today) and the seat released it (the card is already `released`; say whether the count is still written). Say what `landed` means afterwards, since today it is terminal and written only by the hand route.
- D4 A hand-in's own card. Between hand-in and push a goal may wait hours; today its card stays at `judgement` or `land-ready` and stalls. Say whether step 1 has the hand-in write a waiting, non-progressing stage (the vocabulary has `joined`, "waiting to land" on the Fleet page), or defers it; recommend one.
- D5 Behaviour tests stub Git (project rule; `development/project-rules-local.md`). Name the seams the push-side test uses (the push's owner functions, `plain.ContainedIn`, a board home under a temporary directory through `METASYSTEM_SUPERVISION_REGISTRY_HOME`).

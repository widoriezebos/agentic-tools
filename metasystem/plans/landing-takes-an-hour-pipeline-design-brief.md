# Design brief: landing-takes-an-hour-pipeline (follow-up of landing-takes-an-hour, before switch-on)

Working Mode: Design
Opened under R-148-m1e as part of Wido's goal landing-takes-an-hour (Wido 2026-10-08 19:45: "will the lane also behave in the efficient way, not like you just did?"; 17:25: before switch-on).

## Intent

While the lane proves one goal, the next goal in the queue is already merged with the main it will land on and has passed its cheap tier (static, its changed packages' tests), so the moment main moves it needs only its own full proof. Merge conflicts and merge breakage are found and returned to the seat during the previous proof, never after it.

## What is true today

The lane takes one batch at a time (internal/landing/plain/batch.go, queue.go); a waiting goal is merged with main only when its turn comes; conflicts-resolve-unattended (goal of m1h; check its state) resolves conflicts at that moment. By hand on 10-08, machinery-measures waited 2h40 after goal 2 landed, most of it for work that could have run during goal 2's proof.

## What the design must deliver

| Unit | Intent | Lines |
| --- | --- | ---: |
| P0 branches stay current | after every push to main, each seat with a goal branch in progress rebases it onto main through the existing `work rebase` owner (internal/goal/branch/rebase.go with the carry's subject-commit check from goal 2), never a merge commit (the lane refuses a goal-branch commit with two parents, internal/goal/branch/range.go:278), resolves conflicts and runs its cheap tier there, so conflicts with landed goals are found and fixed in parallel while goals build, never at the branch's own landing; a conflict an agent cannot resolve is returned to the seat as a unit, a person's branch is never merged without that person; landing then merges only what landed since the last update | 200 |
| P1 prepared next | while a proof runs, the lane merges the next waiting goal with the proving tree's expected main (the proving batch's merge result), runs its cheap tier with the host share the proof leaves, and records it as prepared against that base | 200 |
| P2 prepared stays valid | when the proof pushes, a prepared goal whose base equals the pushed main goes straight to its full proof; when the proof fails, the prepared merge is redone against the unchanged main; a person's hand-in is never refused for preparation | 150 |
| P3 the lane fixes forward as a seat | a red proof is classified per package; the lane agent fixes forward on the batch tree itself, as a seat does: one fix unit per red package, in parallel, each with a read, under the unit stop rule (one build, at most two corrections), committed on the batch tree; it returns a goal to its seat only when a fix needs a decision that seat owns (a design change) or the stop rule trips; the lane never loosens a test to get green | 150 |
| P4 eject, don't wait | a goal whose fix was returned to its seat (P3) leaves the batch, and the rest land after an impacted reprove of what its removal can affect (lane-reproves' selection); main moves once per batch | 200 |

Each unit at most 250 production lines. The proof's host hold (landing-takes-an-hour U2) allows the preparation's cheap tier but no builds.

## Acceptance

Two consecutive landings where the second goal's full proof starts within 5 minutes of the first goal's push.

## Added 2026-10-08 21:35 (Fable): the lane as a merge queue

Wido asked whether the lane still makes sense. It does, as a merge queue with batching: it is the one mechanism that keeps main green with the fewest full proofs, and a batch proof is the only check that catches two goals each green alone and red together. What was inefficient on 10-08 was not the lane's concept but its inputs and mechanics: goals handed in with their changed packages' tests never run (L1), branches stale against main and each other (P0), a whole-package serial proof (goal 8 U1/U1b), one fix per batch instead of per package (U3), the lane fixing code itself instead of attributing (P3), waiting for every red before landing anything (P4), and one goal per batch by hand (the 10-05 rule, set while the lane was broken). Entry condition for a hand-in: rebased on main and cheap-tier green on its own branch. Measure: proof minutes per landed goal; target under 15 with batches of three or more.

Correction 21:55 (Wido): "since everything required to fix anything in the lane during merging in the lane [is there], the agent in the lane can do just fine acting like a proper seat." The lane does fix forward, on the batch tree, with the same tools and rules as a seat (parallel per-package fix units, reads, the stop rule, never a loosened assertion); the 21:35 line "the lane never edits code" is withdrawn. Today's hand landings were exactly this and worked; what was slow was one serial fix job per gate, not who fixed. Returning to a seat is the exception (a decision the seat owns, or the stop rule), and only then does P4 eject.

## Decided 2026-10-08 22:05 (Wido: "Acting like a seat makes more sense to me"): the lane IS the seat of its batch

Not a dedicated seat process beside the lane. The principle, which every unit of this design follows:
1. A hand-in hands the goal to the lane: while the goal is in a batch, the lane is that goal's seat (custody moves with the hand-in, as the seat cannot change the branch meanwhile anyway); a return hands custody back; a landing ends it. lane-lands-finished-goals has no custody move today (its returns go back to the seat's claim): P3 adds it.
2. The lane uses the ordinary seat verbs on the batch tree, which is its worktree: `work build G --work <fix-unit>` for a fix unit of the goal that owns the red package, `work review`, `work revise`, the declared check, the unit stop rule, the reads. No lane-only fix machinery; the one new thing is the batch tree as the worktree and the fix commits landing with the batch.
3. Records go on the goal the fix belongs to (its unit table gains the fix unit, as a seat's fix units do), never on a lane-owned goal, so attribution and the landing clock read per goal.
4. The landing agent keeps its own loop (batch, prove, classify, push); "acting as a seat" is the fix step inside that loop, in parallel per red package, under the host hold (landing-takes-an-hour U2 allows the lane's own builds).
5. A person's goal in the batch is fixed by the lane the same way (the fix is part of landing, not a decision the person owns); a decision the person owns (a design change, a widened scope) is returned with the question, and the goal is ejected (P4).

## Added 2026-10-08 22:05 (Fable; the time is `date`'s): round 4 of landing-takes-an-hour, B1: the rebuild carries the fixes

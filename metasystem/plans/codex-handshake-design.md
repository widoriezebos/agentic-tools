## 1. Problem and evidence

- The goal record's measurement: on m1, codex-cli 0.148.0 takes 16 to 18 seconds from launch to its `thread.started` event with the operator's ten interactive plugins loaded, and 1 second with `-c 'plugins={}'`; MCP servers change nothing. Jobs breach-design-crit2 and breach-design-crit2b failed `handshake_timeout` while the child was alive. R-35-m3 (memory/rulings.md:62) names any mechanism that turns slowness into failure a defect: patience is progress-based, the number is a hang bound.
- Second machine, second result. Goal codex-handshake-budget (m1b, now marked duplicate) recorded 8 to 14 second starts on m1b where "plugins disabled changed nothing", against m1's 1-second `plugins={}` measurement; Part 1 is therefore expected to fix m1 and is unproven on m1b, and Part 2 is the fix that covers both machines whether or not Part 1 helps on m1b. (orchestrator's evidence note)
- The chain today. The adapter probe writes `sessionEstablishedTimeoutSec` into the snapshot (scripts/agents/adapters/codex.sh:64-71); `capability.Select` validates it as 1..60 and copies it out (internal/capability/select.go:101-104, 164); `job build-record` puts it on the job record (internal/dispatch/build.go:416, 627). ## 2. Part 1 — delegates run without the operator's plugins

- D1.1 The override is the argv pair `-c`, `plugins={}` (the value is TOML, `codex exec --help`: the `-c` value "is parsed as TOML"; `{}` is an empty inline table, so the `plugins` table is empty for that process). It is one package constant in internal/adapter/codex.go, `codexPluginsOverride = "plugins={}"`, used by both verbs.
- D1.2 Position: immediately after the `-c approval_policy="never"` pair on both verbs, before `sandbox_workspace_write.network_access`. Dispatch argv: `codex exec --json -m M --sandbox S -C W -c approval_policy="never" -c plugins={} -c sandbox_workspace_write.network_access=N -c metasystem_instance_tag="T" [-c model_reasoning_effort=…] [--add-dir …] --output-schema … -o … -`. Resume argv: `codex exec resume --json -c model="M" -c sandbox_mode="S" -c approval_policy="never" -c plugins={} -c sandbox_workspace_write.network_access=N -c metasystem_instance_tag="T" [-c model_reasoning_effort=…] [-c sandbox_workspace_write.writable_roots=…] --output-schema … -o … SESSION -`. The two fixed policy settings (approvals, plugins) come first; the envelope-derived settings follow. Positions are pinned by test, so the choice is a contract, not a preference.
- D1.3 Repeated on resume: yes. Every `codex exec` process loads its configuration from the files afresh; `-c` is a per-process override, not thread state, and the rollout a resumed thread reads back carries the conversation, not the previous process's overrides. codex.go:91-98 already repeats `approval_policy`, network and the tag on resume for exactly this reason. Omitting it on resume would load the plugins on every follow-up and reproduce the 16 to 18 second start there.
- D1.4 Rationale for the record. A delegate's whole surface is the brief, the role file, the return schema and the sandbox envelope; the operator's plugins are interactive conveniences that no role requirement names, no snapshot probes, and no job hashes. Passing `plugins={}` makes the runtime surface identical on m1 (ten plugins), m0b (none) and the VM seats: the run becomes deterministic across machines, and the handshake time stops depending on whose account launched it.
- D1.5 Configuration identity: the override is invisible to `codex_config_identity` (codex.sh:32-44 → `config identity` → `BuildConfigIdentity`, internal/config/confidentity.go:22-57, which hashes the contents of config.toml files) and stays invisible by design. The identity fingerprints the operator's files so a snapshot matches the configuration the probe saw; the override is adapter code, changes on every machine at once with the script, and is covered by the supervision fingerprint of the active scripts. Accepted consequence: an operator editing their `plugins` table still changes `configHash` and forces a re-probe although delegates ignore plugins; the config-identity filter was retired under R-33-m0 and is not reopened here.
- D1.6 Tests. internal/adapter/runtime_test.go `TestBuildCodexCommand` (:88-120): the exact `want` argv gains `"-c", "plugins={}"` after `approval_policy="never"`; the resume needle list gains `plugins={}`. internal/adapter/codexcommand_test.go (the brief's named file; today it holds only `TestCodexPermissionSettings`) gains `TestBuildCodexCommandDisablesOperatorPlugins`: for both verbs, exactly one adjacent pair `-c`,`plugins={}`, at the index directly after the `approval_policy="never"` pair, and no other argv element containing `plugins`. `TestBuildCodexCommandCarriesReasoningEffort` and `…CarriesExtraDirs` are substring tests and stay unchanged. codex.sh itself does not change for Part 1.

## 3. Part 2 — liveness-based patience replaces the fixed cap

Definitions. The custodian is the adapter supervisor process (record `pid`, `ownershipProof`). The child is the CLI process it forked, registered as a `custodyProcesses` entry by `register_cli_custody` → `CustodyAdd` (runtime-common.sh:102-115; internal/dispatch/custody.go:16-95). The waiter is the dispatcher's `await_handshake`. The backstop is `reap_one_locked` and the Go reaper (internal/supervise/reaper.go:122-157). The session signal for Codex is the first `thread.started` / `thread.created` / `session.created` event carrying an id (`CodexEventField`, codex.go:16-37) → `record_handshake` → `__handshake` → `HandshakeEval` → status running with `sessionId`. The bound `B` is the record's `sessionEstablishedTimeoutSec`. Times on the record: `handshakeDeadline` and `handshakeProgressAt` are integer epoch seconds from the writer's clock (`date +%s` in shell, `time.Now().Unix()` in Go), the clock `handshakeDeadline` already uses; `endedAt`, `startedAt` and `ownershipProof.provenAt` stay ISO strings as today.

- D2.1 Progress is exactly three events; each sets `handshakeDeadline := now + B` and `handshakeProgressAt := now` on the record, so `handshakeDeadline == handshakeProgressAt + B` holds after every stamp. P1 launch: the ownership patch (dispatch.sh:825-835 → `BuildOwnershipPatch`, ownership.go:78-80) writes BOTH fields from one clock reading (D2.4). P2 child registered: `CustodyAdd` refreshes both fields in the same locked record write when the record has no `sessionId` yet (a post-session custody entry, such as the fake's critique child, refreshes nothing). P3 output growth: the custodian's pre-session loop compares the byte sizes of the events stream (`$events`) and the job log (`$log`, the child's stderr sink) with the last observed sizes and calls `__handshake-progress` when either grew, at most once per second. For Codex 0.148 P3 never fires before `thread.started` (§1 evidence); a healthy Codex start must therefore signal within `B` seconds of P2, which is the child's fork, not the dispatcher's launch. Rejected as progress: the child's CPU time or process-tree growth (motion, not progress: a spinning deadlock advances both, and each needs a per-platform prober the measured cause does not justify once Part 1 removes it) and the heartbeat file (touched unconditionally by the custodian's loop, so it proves the custodian, not the child).
- D2.2 Liveness the waiter checks is the custodian's exact identity: `tag_state pid tag` (`proc classify`, dispatch.sh:280-283), where `live` and `unknown` keep waiting and `dead` or `stale` ends the wait. The child's liveness is the custodian's own business: its loop `while kill -0 "$cli_pid"` (codex.sh:154) ends the instant the child exits, and the custodian names that exit (D2.5). No new liveness verb is needed.
- D2.3 The bound and its snapshot-level discriminator. [closes CHS-R1-SNAPSHOT-01] The snapshot is immutable evidence, so its old field keeps its old meaning forever and the new meaning gets a new field:

  - `capability.Select` (select.go:101-104, 160-166): when `handshakeProgressBoundSec` is present it is validated exactly like the old field (integer, 1..60, else "capability snapshot has an invalid handshake progress bound") and `Result` gains `HandshakeBound: "progress"` (`json:"handshakeBound"`) and `HandshakeBoundSec: <that value>` (`json:"handshakeBoundSec"`); when it is absent, `HandshakeBound: "launch"` and `HandshakeBoundSec: <sessionEstablishedTimeoutSec>`. `SessionEstablishedTimeoutSec` stays in `Result` unchanged for its other readers. An old snapshot therefore keeps its launch semantics until it is re-probed; no snapshot is reinterpreted.
  - dispatch.sh `read_snapshot_fields` (:1592-1598) reads `handshakeBound` into `handshake_bound` and takes `handshake_budget` from `handshakeBoundSec` (equal to the old field on every shipped snapshot). [closes CHS-R1-DEADLINE-03] The custodian fires on the first tick where `now >= handshakeDeadline + HandshakeCustodianGraceSec` (new constant `HandshakeCustodianGraceSec int64 = 1` beside `HandshakeBackstopGraceSec` in reapfacts.go:44, mirrored as `handshake_custodian_grace_sec=1` in runtime-common.sh with the same one-constant comment dispatch.sh:75-77 carries): runtime-common.sh:290 becomes `(( now_epoch < handshake_deadline_epoch + handshake_custodian_grace_sec )) || enforce_expired_deadline handshake "$cli_child"`, the same instant the present `<=` test fires at, now spelled through the constant. On firing it terminates the child, sweeps the group, and writes `handshake_timeout` through `fail_pending`, standing down if the session landed (:261-263), all unchanged.

One equality boundary, integer seconds, three actors [closes CHS-R1-DEADLINE-03]: the waiter refuses on the first poll where `now >= handshakeDeadline`; the custodian on the first tick where `now >= handshakeDeadline + 1`; the reaper's `HandshakeWaiting` is `now < handshakeDeadline + 2` (reapfacts.go:94, unchanged). Consequence: with the waiter's 50 ms poll and the custodian's 100 ms heartbeat, each verdict lands within one poll interval after its boundary second begins, so the waiter's refusal is written no earlier than `handshakeDeadline` and at most one poll interval after it, one full second before the custodian could act and two before the backstop.

Waiter algorithm (`await_handshake`, dispatch.sh:870-895, rewritten; the `-le 60` guard on the argument stays as the fallback bound when a record carries no deadline):

```
every 50 ms, in this order, until one branch returns:
  status running|completed with a sessionId   -> accepted, return 0
  status failed|cancelled|timeout              -> refused; outcome text from record.error
  tag_state(pid, instanceTag) is dead or stale -> lease_run_held __reap-held --job (process-lost path); refused
  now >= handshakeDeadline (re-read each poll) -> __handshake-timeout (hung); refused
  now >= capDeadline (ISO, lexical compare)    -> __handshake-timeout; refused (the never-hit fail-stop)
```

The dispatcher's outcome line (dispatch.sh:1623) names the verdict read from the record, for every role alike: `handshake_failed:exit=N` → "the runtime exited with status N before establishing its session"; `handshake_timeout` with `handshakeBound` `progress` → "the runtime made no progress for B seconds before establishing its session", with `launch` or absent → "the runtime did not establish its session within B seconds of launch"; `process-lost` → "the runtime's supervisor was lost before establishing its session". `HANDSHAKE-FAILED` stays the outcome class.

Verdict table:

| Observation | Who writes | Record | Dispatcher |
| --- | --- | --- | --- |
| Session signal seen before any verdict | custodian via `__handshake` | running, sessionId | accepted |
| Child exited before the signal | custodian, adjudicate initial, no role fold | failed, `handshake_failed:exit=N`, phase handshake, every role including the critics | HANDSHAKE-FAILED, "exited with status N" |
| Child alive, no progress for the bound | waiter at `now >= deadline`; custodian at `now >= deadline + 1` if the waiter is gone | failed, `handshake_timeout`, phase handshake | HANDSHAKE-FAILED, bound quoted, worded by `handshakeBound` |
| Custodian provably dead | reaper (`reap_one_locked` or the Go reaper), any time | failed, `process-lost`, phase supervision | HANDSHAKE-FAILED |
| Dispatcher gone, custodian alive | nobody until the custodian's own verdict (exit or `deadline + 1` hang); the reaper defers while `HandshakeWaiting` and takes no action on a live custodian afterwards (dispatch.sh:1064-1075; reaper.go:147-157, unchanged) | as the custodian decides | none |
| Session lands after a verdict was written | the late writer stands down (dispatch.sh:2368-2401; runtime-common.sh:261-263) | unchanged | unchanged |

What the reaper reads and decides: `status`, `sessionId`, `sessionEstablishedTimeoutSec`, `handshakeDeadline`, `startedAt`, through `ComputeReapFacts` unchanged; it does not read `handshakeBound`, because under `launch` the deadline is simply never refreshed. Because the custodian refreshes the same `handshakeDeadline` the waiter polls, `HandshakeWaiting` tracks the very window the waiter is inside and the two cannot disagree. With the dispatcher gone it decides exactly what it decides today: defer to a live or unreadable custodian, wind down and record `process-lost` for a dead one, never kill a live custodian in the handshake. The custodian's in-process enforcement (D2.6) is what makes a dead dispatcher harmless.

## 1. Problem and evidence

- The goal record's measurement: on m1, codex-cli 0.148.0 takes 16 to 18 seconds from launch to its `thread.started` event with the operator's ten interactive plugins loaded, and 1 second with `-c 'plugins={}'`; MCP servers change nothing. Jobs breach-design-crit2 and breach-design-crit2b failed `handshake_timeout` while the child was alive. R-35-m3 (memory/rulings.md:62) names any mechanism that turns slowness into failure a defect: patience is progress-based, the number is a hang bound.
- The chain today. The adapter probe writes `sessionEstablishedTimeoutSec` into the snapshot (scripts/agents/adapters/codex.sh:64-71); `capability.Select` validates it as 1..60 and copies it out (internal/capability/select.go:101-104, 164); `job build-record` puts it on the job record (internal/dispatch/build.go:416, 627). At launch the dispatcher stamps `handshakeDeadline = now + budget` through the ownership patch (scripts/agents/dispatch.sh:825-835; internal/dispatch/ownership.go:78-80). `await_handshake` polls the record until that deadline and then calls `__handshake-timeout` (dispatch.sh:870-895), whose `internal_handshake_timeout` writes `{"error":"handshake_timeout","phase":"handshake"}` after its stand-down checks (dispatch.sh:2351-2417). `ComputeReapFacts` derives `HandshakeWaiting = now < handshakeDeadline + 2` (internal/dispatch/reapfacts.go:87-102) and `reap_one_locked` defers to a live supervisor while it is true (dispatch.sh:1026-1039).
- Two premise corrections against the brief. (a) The literal is no longer 10: commit ec17b373 raised codex.sh:71 to 30 on Wido's word (R-47-m1b, rulings.md:93); claude.sh:73 says 20, devin.sh:81 says 30. The design below does not depend on the number. (b) `metasystem proc alive --identity-file` does not exist: `runCensusAlive` accepts only `--pid --start-time --start-ticks --boot-id --root` (cmd/metasystem/census.go:154-171); the built engine answers `flag provided but not defined: -identity-file` (exit 2). dispatch.sh:311 and :854-859 call it anyway and always get a refusal. This design uses `proc classify` (the `tag_state` helper, dispatch.sh:280-283) for the supervisor, which is what `job_supervisor_matches` already trusts (dispatch.sh:298-308). The dead flag is recorded in §7, not fixed here.
- Codex is silent before its session signal. Real event streams on this machine (artifacts/agents/design-critic-*/rounds/1/events.jsonl, twelve inspected) begin with `{"type":"thread.started",...}` as line one, and the matching job logs hold only the supervisor's own start line before it. Nothing reaches stdout or stderr before `thread.started`; the goal record's failed specimens had empty event files.
- The custodian's own deadline enforcement never runs before the session: `check_record_deadlines` (scripts/agents/adapters/runtime-common.sh:285-295) is called only from `wait_for_cli` (:298-310), which the adapter reaches after its pre-session loop (codex.sh:154-166) has already seen the session or the child has exited. A hung child whose dispatcher has died is therefore bounded by nothing until `capMin`, and pending→timeout is not a lawful transition (internal/dispatch/record.go:40).

## 2. Part 1 — delegates run without the operator's plugins

- D1.1 The override is the argv pair `-c`, `plugins={}` (the value is TOML, `codex exec --help`: the `-c` value "is parsed as TOML"; `{}` is an empty inline table, so the `plugins` table is empty for that process). It is one package constant in internal/adapter/codex.go, `codexPluginsOverride = "plugins={}"`, used by both verbs.
- D1.2 Position: immediately after the `-c approval_policy="never"` pair on both verbs, before `sandbox_workspace_write.network_access`. Dispatch argv: `codex exec --json -m M --sandbox S -C W -c approval_policy="never" -c plugins={} -c sandbox_workspace_write.network_access=N -c metasystem_instance_tag="T" [-c model_reasoning_effort=…] [--add-dir …] --output-schema … -o … -`. Resume argv: `codex exec resume --json -c model="M" -c sandbox_mode="S" -c approval_policy="never" -c plugins={} -c sandbox_workspace_write.network_access=N -c metasystem_instance_tag="T" [-c model_reasoning_effort=…] [-c sandbox_workspace_write.writable_roots=…] --output-schema … -o … SESSION -`. The two fixed policy settings (approvals, plugins) come first; the envelope-derived settings follow. Positions are pinned by test, so the choice is a contract, not a preference.
- D1.3 Repeated on resume: yes. Every `codex exec` process loads its configuration from the files afresh; `-c` is a per-process override, not thread state, and the rollout a resumed thread reads back carries the conversation, not the previous process's overrides. codex.go:91-98 already repeats `approval_policy`, network and the tag on resume for exactly this reason. Omitting it on resume would load the plugins on every follow-up and reproduce the 16 to 18 second start there.
- D1.4 Rationale for the record. A delegate's whole surface is the brief, the role file, the return schema and the sandbox envelope; the operator's plugins are interactive conveniences that no role requirement names, no snapshot probes, and no job hashes. Passing `plugins={}` makes the runtime surface identical on m1 (ten plugins), m0b (none) and the VM seats: the run becomes deterministic across machines, and the handshake time stops depending on whose account launched it.
- D1.5 Configuration identity: the override is invisible to `codex_config_identity` (codex.sh:32-44 → `config identity` → `BuildConfigIdentity`, internal/config/confidentity.go:22-57, which hashes the contents of config.toml files) and stays invisible by design. The identity fingerprints the operator's files so a snapshot matches the configuration the probe saw; the override is adapter code, changes on every machine at once with the script, and is covered by the supervision fingerprint of the active scripts. Accepted consequence: an operator editing their `plugins` table still changes `configHash` and forces a re-probe although delegates ignore plugins; the config-identity filter was retired under R-33-m0 and is not reopened here.
- D1.6 Tests. internal/adapter/runtime_test.go `TestBuildCodexCommand` (:88-120): the exact `want` argv gains `"-c", "plugins={}"` after `approval_policy="never"`; the resume needle list gains `plugins={}`. internal/adapter/codexcommand_test.go (the brief's named file; today it holds only `TestCodexPermissionSettings`) gains `TestBuildCodexCommandDisablesOperatorPlugins`: for both verbs, exactly one adjacent pair `-c`,`plugins={}`, at the index directly after the `approval_policy="never"` pair, and no other argv element containing `plugins`. `TestBuildCodexCommandCarriesReasoningEffort` and `…CarriesExtraDirs` are substring tests and stay unchanged. codex.sh itself does not change for Part 1.

## 3. Part 2 — liveness-based patience replaces the fixed cap

Definitions. The custodian is the adapter supervisor process (record `pid`, `ownershipProof`). The child is the CLI process it forked, registered as a `custodyProcesses` entry by `register_cli_custody` → `CustodyAdd` (runtime-common.sh:102-115; internal/dispatch/custody.go:16-95). The waiter is the dispatcher's `await_handshake`. The backstop is `reap_one_locked` and the Go reaper (internal/supervise/reaper.go:122-157). The session signal for Codex is the first `thread.started` / `thread.created` / `session.created` event carrying an id (`CodexEventField`, codex.go:16-37) → `record_handshake` → `__handshake` → `HandshakeEval` → status running with `sessionId`.

- D2.1 Progress is exactly three events; each sets `handshakeDeadline := now + bound` and `handshakeProgressAt := now` on the record. P1 launch: the existing ownership-patch stamp (dispatch.sh:825-835), unchanged; it bounds the interval before the child exists. P2 child registered: `CustodyAdd` writes both fields in the same locked record write when the record has no `sessionId` yet (a post-session custody entry, such as the fake's critique child, refreshes nothing). P3 output growth: the custodian's pre-session loop compares the byte sizes of the events stream (`$events`) and the job log (`$log`, the child's stderr sink) with the last observed sizes and calls `__handshake-progress` when either grew, at most once per second. For Codex 0.148 P3 never fires before `thread.started` (§1 evidence); a healthy Codex start must therefore signal within `bound` seconds of P2, which is the child's fork, not the dispatcher's launch. Rejected as progress: the child's CPU time or process-tree growth (motion, not progress: a spinning deadlock advances both, and each needs a per-platform prober the measured cause does not justify once Part 1 removes it) and the heartbeat file (touched unconditionally by the custodian's loop, so it proves the custodian, not the child).
- D2.2 Liveness the waiter checks is the custodian's exact identity: `tag_state pid tag` (`proc classify`, dispatch.sh:280-283), where `live` and `unknown` keep waiting and `dead` or `stale` ends the wait. The child's liveness is the custodian's own business: its loop `while kill -0 "$cli_pid"` (codex.sh:154) ends the instant the child exits, and the custodian names that exit (D2.5). No new liveness verb is needed.
- D2.3 The hang bound is `sessionEstablishedTimeoutSec`, name kept, values kept (codex 30 at codex.sh:71; claude 20; devin 30), meaning from now on: the seconds a live child may go without progress before the wait is called hung. Name kept because the snapshot is immutable evidence on every machine and carries one integer whose only reader is the engine: the meaning moves with the code that reads it, a rename would invalidate every existing snapshot's selection for nothing, and select.go's 1..60 validation stays as the ceiling on the ceiling. Versioning lives on the job record: `handshakeProgressAt` is present exactly when the deadline is progress-stamped; a record without it (one mid-flight across the upgrade) reads under the launch-anchored rule, which is reapfacts.go's existing `startedAt + budget` fallback (:95-100). The comment at codex.sh:64-65 is rewritten to describe the hang bound; the number does not move.
- D2.4 `handshakeDeadline` stays the ONE number waiter, custodian and reaper read. It becomes refreshable: it is in neither `immutableFields` (record.go:60-73) nor `ownershipPatchFields` (ownership.go:9-13), so a pending→pending record CAS may carry it. Exactly two writers refresh it, `CustodyAdd` (P2) and the new engine verb `job handshake-progress` behind `__handshake-progress` (P3); both go through one function `RefreshHandshakeDeadline(record, now)` in internal/dispatch that sets `now + sessionEstablishedTimeoutSec` and `handshakeProgressAt`, refuses when the record is not pending or already has a `sessionId`, and never moves the deadline earlier.
- D2.5 Exit verdict. In `adjudicateTurnStage` initial stage (internal/adapter/adjudicate.go:198-207), a CLI that ended before the handshake yields `fail-pending handshake_failed:exit=<status> handshake` for every status, zero included; `<status>` is the shell wait status (128 plus the signal number on signal death). This replaces `runtime_error` (non-zero) and `handshake_missing_session_id` (zero) on that path only; `HandshakeEval`'s `handshake_missing_session_id` (internal/dispatch/handshake.go:123-125) is a different fact, a session signal without an id, and stays. `criticFailureFold` (adjudicate.go:159-180) matches the prefix `fail-pending handshake_failed:` and folds it to `fail-pending protocol_error handshake` for critic roles, so the register-consumable class is preserved; the exit status is kept in the job log line `child exited before the session signal with status N`. `patienceNeverStarted` (internal/missionrunner/patience.go:44-53) treats the prefix `handshake_failed:` as never-started next to `permissions_mismatch:`.
- D2.6 Custodian enforcement before the session. codex.sh's pre-session loop calls `note_cli_progress` (P3, new in runtime-common.sh) and `check_record_deadlines "$cli_pid"` on every tick, so the F4/D32 in-process enforcement (runtime-common.sh:259-283) finally covers the handshake phase. `cache_record_deadlines` re-arms after `register_cli_custody` and after each `__handshake-progress` (the custodian is the writer, so its cached copy is deterministic); the cap deadline keeps its read-once rule. The custodian fires at `handshakeDeadline + 1` (new constant `HandshakeCustodianGraceSec = 1` beside `HandshakeBackstopGraceSec` in reapfacts.go:44, mirrored as `handshake_custodian_grace_sec=1` in runtime-common.sh with the same one-constant comment dispatch.sh:75-77 carries): the live waiter acts at the deadline, the custodian one second later, the reaper's backstop grace of two seconds last. On firing it terminates the child, sweeps the group, and writes `handshake_timeout` through `fail_pending`, standing down if the session landed (:261-263), all unchanged.

Waiter algorithm (`await_handshake`, dispatch.sh:870-895, rewritten; the `-le 60` guard on the argument stays as the fallback bound when a record carries no deadline):

```
every 50 ms, in this order, until one branch returns:
  status running|completed with a sessionId   -> accepted, return 0
  status failed|cancelled|timeout              -> refused; outcome text from record.error
  tag_state(pid, instanceTag) is dead or stale -> lease_run_held __reap-held --job (process-lost path); refused
  now > handshakeDeadline (re-read each poll)  -> __handshake-timeout (hung); refused
  now >= capDeadline (ISO, lexical compare)    -> __handshake-timeout; refused (the never-hit fail-stop)
```

The dispatcher's outcome line (dispatch.sh:1623) names the verdict read from the record: `handshake_failed:exit=N` → "the runtime exited with status N before establishing its session"; `handshake_timeout` → "the runtime made no progress for B seconds before establishing its session"; `process-lost` → "the runtime's supervisor was lost before establishing its session". `HANDSHAKE-FAILED` stays the outcome class.

Verdict table:

| Observation | Who writes | Record | Dispatcher |
| --- | --- | --- | --- |
| Session signal seen before any verdict | custodian via `__handshake` | running, sessionId | accepted |
| Child exited before the signal | custodian, adjudicate initial | failed, `handshake_failed:exit=N`, phase handshake | HANDSHAKE-FAILED, status quoted |
| Child alive, no progress for the bound | waiter at the deadline; custodian at +1 s if the waiter is gone | failed, `handshake_timeout`, phase handshake | HANDSHAKE-FAILED, bound quoted |
| Custodian provably dead | reaper (`reap_one_locked` or the Go reaper), any time | failed, `process-lost`, phase supervision | HANDSHAKE-FAILED |
| Dispatcher gone, custodian alive | nobody until the custodian's own verdict (exit or +1 s hang); the reaper defers while `HandshakeWaiting` and takes no action on a live custodian afterwards (dispatch.sh:1064-1075; reaper.go:147-157, unchanged) | as the custodian decides | none |
| Session lands after a verdict was written | the late writer stands down (dispatch.sh:2368-2401; runtime-common.sh:261-263) | unchanged | unchanged |

What the reaper reads and decides: `status`, `sessionId`, `sessionEstablishedTimeoutSec`, `handshakeDeadline`, `startedAt`, through `ComputeReapFacts` unchanged. Because the custodian refreshes the same `handshakeDeadline` the waiter polls, `HandshakeWaiting` tracks the very window the waiter is inside and the two cannot disagree. With the dispatcher gone it decides exactly what it decides today: defer to a live or unreadable custodian, wind down and record `process-lost` for a dead one, never kill a live custodian in the handshake. The custodian's in-process enforcement (D2.6) is what makes a dead dispatcher harmless.

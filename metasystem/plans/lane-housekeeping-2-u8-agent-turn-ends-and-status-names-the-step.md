## Problem (findings 134, 135 of 2026-10-11)
After a person returned the batch's last member (`landing return lane-recovers-and-pauses --cause other`, 14:59Z), the landing agent's session stayed up and silent for 55 minutes until it was killed by hand (SIGTERM, 17:58). `landing status` showed "agent running" and nothing else: no step, no start time, so a stalled agent and a long legitimate step look the same.

## Build
1. The engine records the agent's step: every `landing` verb the landing agent's session runs (prove, prove --gate/--trunk/--classify, push, resolve, return, run, status is excluded) writes `artifacts/agents/landing/agent-step.json` {verb, args (sanitised), started_at, pid} on start and clears it on exit (a record that carries a value stores it; a crash leaves the record with its pid, which status reports as "step X started HH:MM, process gone"). `landing status` prints one line: "agent: <verb> since HH:MM (N min)" or "agent: idle since HH:MM" or "agent: running, no step for N min" (the silent case — a finding line, never a stop). JSON status carries the same fields.
2. The skill (skills/landing-agent/SKILL.md) says, in its loop and in one sentence under the batch section: when `landing status --json` shows no member left waiting or running (every member landed, returned or superseded), end the turn at once — the keeper wakes the agent when there is work; a person's return of the last member ends the turn. The skill test asserts the sentence.
3. The keeper (the tick that wakes the agent) treats an agent session whose last step ended more than `landing.agent-idle-minutes` ago (compiled default 10, internal/config defaults, never metasystem.conf) with no step running and an empty batch as finished: it records "agent turn ended by keeper: idle N min after the batch emptied" and ends the session the way `landing stop` would end it (reuse that path; if `landing stop` does not end the session today, say so and leave the keeper part as a status finding line only — do not invent a kill).

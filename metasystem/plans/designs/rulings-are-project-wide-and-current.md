## Step 1, in one paragraph

The file every critic and seat reads, `memory/rulings.md`, becomes a short register of standing law: one row per KEEP ruling, rewritten verbatim from the table, same id, with a theme. The file as it stands today moves to `memory/rulings-archive.md` with ten short rows padded to six cells and nothing else touched, so every id ever minted stays findable and Wido's original words stay where they were. No new resolver: the two engine readers that look an id up by its row do so only for a fresh `--approved-ref`, and nothing live holds one. The parser learns one trailing column and one second file; the landing rule changes from "append only" to "rows move, never vanish". Then the interface gives Rulings its own tab under Project, grouped by theme, and the Decisions page keeps only what waits on Wido. Nothing else.

**Resolving an id.** A FOLDed id resolves by text: the register row whose `context` names it is the ruling that stands (`grep R-128-ui memory/rulings.md` finds R-125-m1u; the view's find box does the same). A MOVEd id resolves in the archive. No reader needs a map, so there is none.

**After the clean-up.** The header replaces the append-only rule with three sentences. A new ruling is appended as a row with a machine-suffixed id continuing from the highest number in either file (R-143-ui is next), its theme from the fixed list, and Wido's verbatim words in `context`. A ruling Wido amends is rewritten in place under its id, dated the day of his new word, after its old row is appended to the archive. A ruling he retires moves to the archive. The landing driver's bare-id refusal stays as it is (internal/landing/landpath/land.go:560-603: only a NEW bare `R-<n>` offends; a removed-then-added id is "a rewritten historical row", land.go:596); it never looks at the archive path, and need not.

**The parser** (internal/rulings): `Read` accepts six or seven columns (rulings.go:173 `len(fields) != 8` becomes 8 or 9; the defect text at :176 says "want 6 or 7"); the seventh fills `Row.Theme`; six columns leave it blank, which is what an adopted repository's register has (internal/landing/observe.go:1821 writes six). ## 4. The landing rule

`recordCarriageError`'s rulings case (observe.go:1207-1211) becomes two cases. `memory/rulings.md`: every ruling-row id in the base's register is in the candidate's register or the candidate's archive, and every candidate row is well-formed by `rulingRowID` (observe.go:1466-1475); a row may change, a row may leave for the archive, a row may never vanish. `memory/rulings-archive.md`: `appendOnly` (the existing helper) plus well-formed appended rows — today's `addRulingRowsOnly` with the path changed — and a base without the file accepts the candidate's archive whole, because it is the old register moved and its historical ids ("R-80-m2 note") would not pass `rulingRowID` (observe.go:48 allows one suffix). The refusal keeps the code `register-carriage-not-append-only` with a reason naming the id that vanished, so no refusal-register row is added. The rule binds chain landings with carried record paths (observe.go:600-608), `register-carriage` direct fixes (observe.go:1499) and carried landings (internal/landing/carried.go:241); the batch lane judges every member with the running engine (internal/landing/landpath/commit.go:589, `b.owners.Live()`), so the engine that judges the register member must already carry this rule. The build is therefore two members landed in order: first the code (parser, landing rule, their tests), then the register and the archive. A member judged by an older engine is refused `register-carriage-not-append-only` at observe.go:1209; that is the wrong order, not a defect. The change is two functions and one test file in internal/landing; the other seat's work there (lane D, integ-b8, 2026-10-01) is in lane and stop-loss code, and the build rebases onto whatever landed.

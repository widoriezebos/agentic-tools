## Step 1, in one paragraph

The file every critic and seat reads, `memory/rulings.md`, becomes a short register of standing law: one row per KEEP ruling, the table's rewrite with every approved absorption clause folded in (the exact text is in section 1), same id, with a theme. The file as it stands today moves to `memory/rulings-archive.md` with ten short rows padded to six cells and nothing else touched, so every id ever minted stays findable and Wido's original words stay where they were. No new resolver: the two engine readers that look an id up by its row do so only for a fresh `--approved-ref`, and nothing live holds one. The parser learns one trailing column and one second file; the landing rule changes from "append only" to "rows move, never vanish" and keeps its mode guard. Then the interface gives Rulings its own tab under Project, grouped by theme, and the Decisions page keeps only what waits on Wido. Nothing else.

## 4. The landing rule

`appendOnly` (observe.go:1405-1440) does four things: refuses a changed mode or a deleted file (:1414-1416), refuses an absent or unterminated candidate (:1427-1429), refuses an unterminated base (:1433-1435), and requires the base to be a byte prefix of the candidate (:1436-1438). The first three become `registerShape`, factored out and called by `appendOnly` first, so every append-only register behaves exactly as today. `recordCarriageError`'s rulings case (observe.go:1207-1211) becomes two cases. `memory/rulings.md`: `registerShape`, then every ruling-row id in the base's register is in the candidate's register or the candidate's archive, then every candidate row is well-formed by `rulingRowID` (observe.go:1466-1475); a row may change, a row may leave for the archive, a row may never vanish, and the file keeps its mode and its last newline. `memory/rulings-archive.md`: `appendOnly` plus well-formed appended rows — today's `addRulingRowsOnly` with the path changed — and a base without the file accepts the candidate's archive whole, because it is the old register moved and its historical ids ("R-80-m2 note") would not pass `rulingRowID` (observe.go:48 allows one suffix). The existing fixture that appends a valid row while changing the register to `100755` (observe_register_policy_test.go:214-230) stays and must still refuse. The refusal keeps the code `register-carriage-not-append-only` with a reason naming the id that vanished or the mode that changed, so no refusal-register row is added. The rule binds chain landings with carried record paths (observe.go:600-608), `register-carriage` direct fixes (observe.go:1499) and carried landings (internal/landing/carried.go:241); the batch lane judges every member with the running program's own `landing.Observe`, in process (cmd/metasystem/landing_path.go:228-230, `landpath.Judge{Observe: landingPathObserve}`; internal/landing/landpath/commit.go:589). Ordering two members inside one batch therefore changes nothing: the engine carrying this rule must have landed and be the running lane program before the register member is judged. A member judged by an older engine is refused `register-carriage-not-append-only` at observe.go:1209; that is the wrong order, not a defect. The hunk is two functions and one test file in internal/landing; it waits until the other seat's landing changes (lane D, integ-b8, 2026-10-01) settle on main, is then rebased onto them and verified, and is not started before.

## 6. Applying the table, and the order

The build lane (Opus, per R-133-ui) writes the register from table.md and section 1: the rewrite column verbatim, the thirteen final texts above as given, the theme from section 2, the fold list from the FOLD table's targets, nothing composed. Before the register member is pushed, the seat renders the 68 rows by theme as one page in the conversation and Wido reads it once; his corrections go onto the branch as ordinary edits and the member lands on his word. After the landing 7878 restarts onto it and he reads the same rows on the Rulings tab.

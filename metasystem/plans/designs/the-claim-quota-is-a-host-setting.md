## 1. Problem

Wido's rule since 2026-10-08: as many builders as the host CPU allows, about six at most (measured that day: ten builders drove load to 30 on 18 cores). The claim path allows one. The host carries two unit rounds at a time today, so the second waits behind a number in code. Wido's design rule: a value a person sets is configuration, never code.

Evidence, by line:

- The rule's live owner is `ClaimQuotaBlocker` (`metasystem/internal/goal/verbs.go:1458-1513`). It walks the live goals in alphabetical order (`sortedGoalIds`, `:1467`) and counts this machine's live claims as single goals, skipping the target, handed-over claims, fenced claims and members of the target's own arc (`:1467-1478`). A returned or landed claim refuses at once (`:1486-1491`). Two hand-ins waiting is the slot refusal (`:1504-1507`). Any held claim refuses with "machine %s already claims %s, and a machine holds one claim at a time" and the release command (`:1508-1511`).
- Agents only: `Claim`'s mutate calls `claimQuotaRefusal` under `if !person` (`verbs.go:1700-1703`); the arc claim the same (`verbs.go:4619-4626`). A person's reservation records the refusal as a warning only (`metasystem/internal/goal/reservation.go:64-66`).
- The rule's second copy is at rest. `ValidateTree` refuses any tree where one machine holds two agent claims unless all of them are in one arc: "the quota is one claim per machine (one arc counts once)" (`metasystem/internal/goal/validate.go:531-549`). Personal reservations, landing claims, fenced and handed-over claims are left out first (`:494-517`). Neither copy counts an arc as one unit beside independent goals; the blocker only skips the target's arc. Every publish validates its commit (`validate.go:740-760`, `:762`). Every fetch does too, on every engine: an older engine rejects the fetched tree and keeps its last accepted one (`metasystem/internal/goal/fetchadvance.go:79`). Landing's fresh gate projects through that fetch and returns its error (`metasystem/cmd/metasystem/landing_gate.go:60`). So a host setting alone cannot raise the quota.

## 2. Decisions

- **D1 The setting.** `host.claims`, a compiled row in `coreSettings` beside `host.builds` (`config/defaults.go:67`): default `1`, meaning "agent claims this machine holds at a time, counted in quota units, 1 to 6; a person's own act is never refused by it". The resolver is a new `config.ResolveClaimQuota(confPath string) (int, error)` in `metasystem/internal/config/claimquota.go`, with the key and `ClaimQuotaMax = 6` as constants and `ParseClaimQuota` as the one parser. It reads through `Get` as `CodexSandbox` does (`codexsandbox.go:37-44`) and `positiveBoardSetting` (`metasystem/internal/config/board.go:41-51`). A compiled key stays out of the generated reader registry (`metasystem/internal/config/declared_test.go:362`, `:382`); no regeneration.
- **D2 Bounds 1 to 6, checked where `host.load-max` is.** `SettingValueProblem` refuses anything but a whole number from 1 to 6: "host.claims must be a whole number from 1 to 6". The three `settings check` conditions at `config/validate.go:80`, `:89`, `:141` gain `|| key == config.ClaimQuotaKey`. Why 1: 0 would refuse every agent claim, a stop under another name. Why 6: Wido's measured cap of about six builders on this host; and the at-rest ceiling (D5) is a constant every engine can check without reading this host's file.
- **D3 Who sets it.** A person, at the enrolled terminal: `host.claims` joins `authoritySettings` (`intent_work.go:2962`), exactly as `host.load-max`. Example: `metasystem settings set host.claims 2`.
- **D4 One quota unit, counted one way in both owners.** A quota unit is an independent claimed goal, or one arc, however many members it has. A new `quotaUnits(claims []*GoalFile) []string` in `metasystem/internal/goal/verbs.go` gives each claim its unit key (its arc when it has one, else its id) and returns the distinct keys in program order (`OrderedOpenGoalIDs`, `metasystem/internal/goal/order.go:32`). The blocker and the at-rest rule both call it. Which claims each owner feeds it stays as today, and the page says so: the blocker counts every live claim on the machine that is not the target, not in the target's arc, not handed over, not fenced and not waiting to land (`verbs.go:1467-1478`); the at-rest rule leaves out personal reservations too (`validate.go:510-512`), so a person's reservation fills the machine for agents but never makes a tree invalid.
- **D5 The blocker takes the quota; the at-rest rule becomes a ceiling.** `ClaimQuotaBlocker(t, target, machine, tip string, quota int, laneState)`. `claimQuotaRefusal` (`verbs.go:1515`) resolves the quota from `filepath.Join(r.Endpoint.Root, "metasystem.conf")`, the path the handover's lock wait already reads (`verbs.go:1544`). An unreadable value refuses the agent's claim with the resolver's words. At quota 1 the code takes today's path byte for byte (the early returns at `:1486-1491`, the held text at `:1508-1511`, alphabetical order). Above 1 the blocker counts quota units (D4); returned, landed and held units count alike. When the count reaches the quota it refuses with "machine m1e already claims X and Y; it holds 2 claims at a time", units named in program order, an arc as "arc <name>". Then `run:` with the command of the first returned or landed unit in program order, else `metasystem goal release <first held> --reason TEXT`, with today's tails. `validate.go:531-549` refuses more than `config.ClaimQuotaMax` quota units per machine: "machine %s claims %s: a machine holds at most 6 claims (one arc counts once)". The host setting is applied where an agent puts a claim on a machine: the claim, the arc claim, the hand-back and an agent's budget lift (D8). The hand-back (`verbs.go:1599-1612`, on `returning`) calls the blocker for `targetMachine` with the quota resolved from `r.HandoverTargetRoot`'s `metasystem.conf`, and refuses with the block's first line and `run: <command>`.
- **D6 A person is bounded by the ceiling only.** A person's claim already skips the quota (`verbs.go:1700`, decision 124 (a)). A person's resume (`stop.go:440-441`) and take-over (person-only at `metasystem/cmd/metasystem/intent_planning.go:1450`) are not counted against `host.claims` either, under R-142-m1e. At quota 1 such an act beside a live claim, refused today by the at-rest rule, is admitted. The comment at `stop.go:487-488` already says so. This publishes a two-claim tree at default 1; section 7 treats it as a trigger.
- **D7 The steward names the holders.** `checkClaimQuotaWith` resolves the quota from `repoRoot`'s `metasystem.conf` beside the machine (`claim_quota.go:43-46`) and passes it to the blocker; unreadable is `CauseUnreadable`, as at `:31-33`. The block carries `Holders []string`; `RemedyFact` gains `Holders string` (`json:"holders,omitempty"`), the units' names already joined ("held-h and second-s"). A string keeps `RemedyFact` comparable, so the six comparisons above compile and keep their assertions as they are. At quota 1 the row and the ask keep today's words, and `Holders` stays empty. Above 1 the row reads "R (priority 1) is ready but X and Y hold this machine's claims (2 at a time); X has a running job; next: …". The ask goes to the named holder only, still once per (ready, held) pair: "Goal R is ready at priority 1 and waits for one of this machine's claims, which goals X and Y hold; yours is X. Next: <command>, then metasystem goal claim R."
- **D8 The budget lift follows the same rule.** `checkFenceLiftForRebudget` (`stop.go:404`) takes a quota. The set-budget caller (`verbs.go:1929`) passes none for a person (proof and name, `verbs.go:1883`): the other-claim check is skipped, under R-142-m1e. For an agent under a power of attorney (`verbs.go:1865`, `:1893-1907`) it passes `host.claims` from `r.Endpoint.Root` when the fenced claim is on this machine, else 1, since another host's file cannot be read here. The loop at `stop.go:417-431` is replaced by a call to the blocker with that quota (lane reader nil). The stop-batch check above it (`stop.go:413-416`) stays. At quota 1 an agent's words change to the blocker's held text with a `goal set-budget` tail instead of `goal claim`.
- **D9 Stop sees every held goal.** `idleBacklogContinuation` (`turnverdict.go:1351`) walks `work.Claimed` in order and continues the first held goal that does not wait on a person. Only when all wait does it answer "this machine's held goals wait on a human word". With one held goal the answer is today's.

- **D10 The load gate waits for an agent's launch.** Above `host.load-max`, an agent's launch inside a unit round (a build, a correction, a host-gated unit check) is admitted when the host's load allows, through the same host-gated start the checks use, inside the goal's budget clock.
  - Mechanism. The load refusal (`hostcapacity.go:123-125`) becomes a typed `launch.HostLoadWait{Load float64; Limit string; Reason error}` around today's coded error: same code, text and facts (`refusal.CodeOf` finds the code with `errors.As`, `metasystem/internal/refusal/coded.go:85-91`), so every caller that tests the code keeps its path (`read_sequence.go:114-116`, `intent_answer.go:212`) and the Manager-level callers outside a unit round keep today's refusal (`metasystem/cmd/metasystem/landing_merge.go:81`, `metasystem/cmd/metasystem/landing_agent.go:167`). `stepDriver.advanceStep` (`read_sequence.go:33-38`), when the driver has a `pause` (unit rounds only, wired in `UnitRunner.driver`, `unit_run.go:767-793`), tries the start again after `HostWaitPoll` (30 s, at most the time left) until it is admitted or the command's deadline (`unit_run.go:321`: `launch.wait.cap.seconds`, 240 by default, or `work wait --timeout`, `intent_work.go:2163-2170`). The pause runs inside `UnitRunner.CommandWait` (`metasystem/internal/launch/tree_reservation.go:431-484`), so the run's command locks are free while it waits, and on the manager's clock (`Manager.Now`, `Manager.Sleep`, `launch.go:87-88`). The step stays starting as today; no launch record exists until admission.
  - Budget. Each attempt runs the before-launch hook first (`read_sequence.go:107-111`), so a goal whose box ends while it waits stops with today's `BUDGET_REFUSED` and `goal budget` remedy. The wait has no clock of its own. When any attempt after the first ends in a refusal that is not a load wait, the step's `Waits` is cleared and saved while the command still owns the run, so status never shows "waits for the host" for a wait that ended on budget. After `UNIT_WAIT_RETRY` nothing is saved: another command owns the run.
  - Words. At each refused attempt the step records `Waits`, "waits for the host: load 9.2 of 8" (the reading to one decimal, the limit as set), saved with the run, and cleared before each new attempt, so the save that records an admitted start (`read_sequence.go:125-131`) persists it empty. `work status` and the situation show it as the stage instead of "running": both read `goalUnitStages` (`metasystem/cmd/metasystem/intent_selection.go:171`, `metasystem/cmd/metasystem/situation_sources.go:83`; the stage at `intent_selection.go:66-67`). `unitOutcome` answers a wait with exit 3, outcome in progress, "U1a waits for the host: load 9.2 of 8", next `work wait` for the same work, today's facts in the details. Never exit 1.
  - A person. A person's launch at the enrolled terminal is admitted as today, before the load is read (`hostcapacity.go:83-85`): a person is never queued behind the machine (R-142-m1e). A person's `work build run:<id>` starts a waiting round at once (`intent_work.go:784-800`). A person's command on the run while an agent waits is not blocked by the agent's command locks (the pause releases them). The agent's command then finds the run changed (`UNIT_WAIT_RETRY`, `tree_reservation.go:476-481`), which today falls to the default exit 1 (`intent_work.go:1631`); D10 answers it as `UNIT_RUN_BUSY` is answered, exit 3, "another command is advancing this work right now" (`intent_work.go:1618-1620`).
  - What stays. The threshold is `host.load-max`, set only by the person (`intent_work.go:2962`), compared with `>=` as today. These stay refusals with today's words and exit 1: an unknown capacity (`hostcapacity.go:120-122`), an invalid limit (`:117-119`), `host.builds=person` (`:114-116`), the `host.builds` cap (`:126-143`), and the lane-proof hold of a check's retry (`intent_work.go:548-551`). The listing of launch ids, the launch-store folder and the failed start belong to a-check-guards-its-own-inputs U1c1 (`agentic-tools-evidence/lane-test-20261009/briefs/a-check-guards-its-own-inputs-U1-brief.md:132-139`); D10 changes none of them and owns only the gate's behaviour: the retry inside the command, the recorded words, the exit code.
  - Rejected: keep the refusal and tell agents to retry. Every agent writes its own retry loop, and finding 471 shows the loop ends on exit 1. Rejected: raise the threshold. It hides the load (2026-10-08: ten builders drove load to 30 on 18 cores). Rejected: a queue owner that starts waiting launches by itself. It is a new owner, and the round's own `work wait` already drives it.

## 3. What does not change

- The default is 1. Until a person raises it, every agent claim, refusal text, row and ask is today's (D5, D7). The changes at 1 are D6 and D8 for a person, and D8's words for an agent.
- One landing slot per machine (`verbs.go:1504-1507`, `validate.go:520-524`). The lane proves one batch at a time (`proof.admission.top-level-max` defaults to one, `config/defaults.go:111`), so a second waiting hand-in from one machine only waits longer.
- `goal release`, `goal done` and `work land` as the remedies, with their tails.
- Build admission. `host.builds` and `host.load-max` still gate every build launch (`metasystem/internal/launch/hostcapacity.go:68-105`). A claim admitted is not a build started. D10 changes how an agent's unit round meets the load gate (it waits), not the gate or its threshold.
- The environment layer (`resolve.go:367-369`) overrides `host.claims` as it overrides `host.load-max`. Same exposure, not this page's.
- A new engine set to 1 accepts another machine's tree with two ordinary claims: the at-rest rule is the ceiling, not the local setting.
- Readers that take one claim, accepted at quota 2 as they are:
  - `SelectNext` continues the first held goal (`metasystem/internal/goal/project.go:769-777`); goal verbs without a goal ask for one when a session holds two (`intent_planning.go:1072-1088`).
  - `currentClaimOf` (`metasystem/internal/goal/goalverbs.go:935-951`) feeds the mission prompt's goal line (`metasystem/internal/mission/prompt.go:643`) and the turn verdict (`turnverdict.go:2005`): the first claim in program order.
  - The steward's situation keeps one block per selected holder (`metasystem/internal/steward/situation.go:612-616`).
  - `proof run` asks for `--authority` when two claims could authorize it (`metasystem/cmd/metasystem/proof_run.go:846-857`).
  - The seat ladder speaks per seat (`metasystem/internal/steward/seat_ladder.go:203-207`).
- Readers that already see every claim: `goal.Next` (`project.go:798-812`) and the board's claim check (`metasystem/internal/board/view.go:42`).

## 4. Questions answered

1. Where do the machine's settings reach the claim path? Through `r.Endpoint.Root`, already read for `metasystem.conf` in the same file (`verbs.go:1544`). No new field on `VerbRequest`.
2. Which value does a hand-back read? The seat's, through `r.HandoverTargetRoot`, required on a return (`verbs.go:1599-1601`). Limit, recorded: `Handover` has no caller outside tests at this SHA (`verbs.go:1531`), so this path is proved only by its tests. No adapter is added for it.
3. Does a person's resume or budget lift count? No (D6, D8). Rejected: count them to keep quota 1 exact; a person's claim already skips the quota, and R-142-m1e says the machine does not refuse him.
4. Which holder is asked? The one whose command the block names. Rejected: ask every holder; one freed unit admits the ready goal, and more asks mean more noise.
5. Why string `Holders` on `RemedyFact`? A slice makes the struct incomparable and breaks six comparisons at compile time. Rejected: `[]string` with six test edits.

6. Does a person's `work wait` wait for the host too? Yes: it is not a person's act today (`intent_work.go:501-503`), and D10 does not make it one. The person's way to start a waiting round now is `work build run:<id>` at the enrolled terminal. Rejected: make every person's `work wait` bypass the gate. `work wait` is not only a read: it calls `Continue` and can launch a pending step (`intent_work.go:2200`). Running it is an explicit choice to wait for the host; `work build run:<id>` orders an immediate start, and the bypass belongs to that act.

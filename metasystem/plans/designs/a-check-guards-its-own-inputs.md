## 1. Problem

A unit check runs for about 25 minutes. Any ref move in the repository during that window stops it as environment, and a person must Retry. With two goals active on one host the window is almost never free. And the check's engine is not held still: a deployment in the window changes the code its later process launches run.

Evidence, by line:

- One snapshot serves every guard: `repositorySnapshot{TreeID, Head, Refs, Index, Tree}` (`internal/launch/unit_run.go:1189-1195`). `Head` is the worktree's `HEAD`, the goal branch head (`:1256`). `Index` digests the worktree's own index (`:1271-1314`). `Tree` is the raw diff of the worktree against `HEAD` (`:1320`). `Refs` is `for-each-ref refs/heads refs/tags refs/notes refs/stash` of the shared `.git` (`:1260-1270`): main, every goal branch, every builder branch.
- `changed` compares head, refs, index and tree (`unit_run.go:1197-1213`).
- Five places stop on it:
  1. A step's own window. `startStep` takes `Before` for every proof and read step (`internal/launch/read_sequence.go:82-88`). `retryFailedStep` sets the step failed, environment, "the tree moved during the step" when `changed` names anything (`internal/launch/unit_step_failure.go:84-85`).
  2. Re-entry while the check runs. `savedRepositorySnapshot` compares the saved `proof-before.json` with a new snapshot by struct equality (`unit_run.go:1226`) and returns `UNIT_TREE_CHANGED` (`:1227`). `treeMoved` then fails the running step as "the worktree bytes changed across this step" (`internal/launch/tree_reservation.go:399-409`, words at `:404`), called from `unit_run.go:596-597` and `:629-630`.
  3. The proof window. `beforeProof != afterProof` adds "worktree" to `moved` (`unit_run.go:635-641`); the round is environment and `proof-wrote` (`:642-644`, `:672-677`).
  4. After the read: `afterRead != afterProof` calls `treeMoved` (`unit_run.go:710-716`).
  5. The base comparison's isolated directory (`internal/launch/unit_attribution.go:163-167`, `:222-224`).
- Measured, and confirmed by Astra: in run `20261101t133625-8715326d96` the retained `proof-before` and `proof-after` of launch `-r1-s2-retry` differ in `refs` only. `treeId`, `head`, `index` and `tree` are equal. The one moved ref is `refs/heads/main`, `1d58d986ec` to `1627fdbf03`: the pane's records commit at 15:36.
- Finding 472's first stop said "the worktree bytes changed" although the tree id matched afterwards. Path 2 compares the whole struct, refs included. Hypothesis: that stop was a ref move too (`goal/a-red-is-classified-once` has a commit at 15:10, inside the window). The snapshot taken at that re-entry was not kept.
- The names are lost after a machine retry. `retryFailedStep` clears the step's `Moved`, `Reason` and `Cause` before the retry (`unit_step_failure.go:120-121`). When the retry passes, the round still sees the move against its first baseline (`unit_run.go:635-644`), but the names go only to the skipped read (`:672-673`). `holdFailedStep` finds no failed step and keeps its generic class, "the failed step needs a person's decision" (`unit_step_failure.go:139-156`, reached from `finish`, `unit_run.go:1015-1016`).
- What the check reads. The proof is `metasystem test run --unit-run RUN --repo <installation>` in `<worktree>/metasystem` (`cmd/metasystem/intent_unit_check.go:72`; the folder at `cmd/metasystem/intent_work.go:1139-1145`). Its commands `proof.cheap`, `proof.audits` and `proof.deadline` are frozen from the goal branch's committed `metasystem.conf` (`intent_unit_check.go:239-279`), today `metasystem test impact` and `go test ./cmd/metasystem -run '^TestAudit'` (`metasystem.conf:17-19`). They run in the worktree folder (`internal/launch/unit_check.go:120-122`). `test impact` loads its contract from `--root .`, the worktree (`cmd/metasystem/test_impact.go:47`, `:56`; `internal/testrun/contract.go:53-68`). So `testing.json`, the ratchets, the floors, `metasystem.conf` and `proof/` come from the worktree, which `Tree` and `TreeID` cover. From `--repo` the check takes its layout, state root, run record and frozen `plan.json` (`intent_unit_check.go:94-97`, `cmd/metasystem/intent_process.go:950-969`), and the engine.
- The engine moves under the check. The step's program and the check's first `PATH` entry are `<installation>/bin/metasystem` (`intent_unit_check.go:31`, `:58`, `:72`; measured in the run's `proof-unit-check.json` and `plan.json`). Installation replaces that file by rename (`cmd/devgate/witness.go:390-409`, rename at `:405`). Inside `test impact` every group is supervised (`internal/proofrun/supervisor.go:232`): the custody engine is `os.Executable()` unless a context names one (`internal/proofrun/resource_custody.go:36-50`), and it is executed again for the watchdog (`:450-460`) and the worker wrapper (`:662-666`). So a deployment between groups runs new code under one check, while head, index and tree stay equal.
- The lane does not read the snapshot. The attestation's unit-check gate checks run id, subject tree, source tree, command digest and two zero exits (`internal/goal/branch/check.go:18-47`, called at `internal/goal/branch/attest.go:972-977`). The carry path guards its own workspace (`cmd/metasystem/intent_carry_check.go:153-164`). The hand-in reduces rounds to counts and proof names (`cmd/metasystem/landing_plain.go:466-480`). The committed read bundle carries no round observation (`cmd/metasystem/intent_unit_review.go:693-696`).

- Finding 473: a refused admission leaves a dangling launch id. `startStep` names the step's next launch, appends it to `LaunchIDs`, sets the step starting and saves (`internal/launch/read_sequence.go:59-77`) before anything is admitted. The admission comes after: the runner's hook writes the goal's pending job reservation (`cmd/metasystem/intent_work.go:540-563`, through `internal/dispatch/unit_launch.go:78-84`), then `Manager.Start` admits and refuses for load before any launch record exists (`internal/launch/launch.go:122-131`; `createAdmitted`, `internal/launch/hostcapacity.go:61-130`). A capacity refusal returns with the step still starting and the id on its list (`read_sequence.go:114-116`). A person's Retry takes `step.LaunchID` as `RetryLaunch` (`internal/launch/unit_step_failure.go:209`), so every `work wait` then failed on that id's missing `record.json`. Measured: the parked job record of `...-r1-s2-retry` is `pending` with operation `unit-launch:...-r1-s2-retry` (`agentic-tools-evidence/lane-test-20261009/u2b1a-snapshot-20261101-1530/job-r1-s2-retry.json.parked`).
- Finding 477: a reader that writes nothing stops the round with no verdict. A missing declared output fails the launch as `declared-output: ...` (`launch.go:569-570`), whatever the exit. `stopCause` gives it no cause (`launch.go:911-930`). In a unit, `endStep` then classifies it `unclassified` (`read_sequence.go:180-182`; `unit_step_failure.go:35-43`), so it is never retried (`unit_step_failure.go:95`); the `read-no-findings` cause at `read_sequence.go:191-192` applies only when the cause is still empty, which in a unit it never is. The read sequence returns `read-failed` (`read_sequence.go:276-281`), `finish` collects the reads (`internal/launch/unit_run.go:1008-1012`), finds none, and decides "unavailable-stop-inputs" (`internal/launch/unit_stop.go:91-128`).
- Finding 478: a retried read is told one path and collected from another. For a step's second launch `startStep` remaps every declared output to `<launch state>/declared/<name>` (`read_sequence.go:94-99`), and the launch records the remapped paths as `declaredOutputs` (`internal/launch/launch.go:239`), which the collection reads (`internal/launch/declared_outputs.go:18-40`). The reader's brief is the retained copy (`unit_step_failure.go:48-50`, `:56-73`), rendered at planning with the original path ("Write findings to: ", `cmd/metasystem/intent_work.go:1540-1541`). So a retried reader that writes where it is told is recorded as writing nothing. Premise corrected, measured in run `20261101t172658-638f6b9f88` round 2: the second read there was not a retry. It is a separate step, `read:fresh`, with one launch id (`...-r2-s4`); its `declaredOutputs` is the brief's path, its file was collected, and its launch record holds a counted read ("VERDICT: fix first (1 material finding)"). The run still shows that step running, with no reads on the round. Hypothesis: the round was decided before the fresh read's step was ended, which this page does not settle (OPEN). The remap defect is real and latent, and D9's machine retry would meet it every time.
- Finding 476: an excluded file the builder touched makes a green unit uncommittable. `ClassExcluded` is every workspace exclusion and `metasystem/records/reads` (`internal/goal/branch/range.go:231-246`); `metasystem/memory/receipts.log` is one. The result is frozen with it: `worktree.diff`, `result.patch` and the result tree at the build's end (`internal/launch/unit_build_outcome.go:18-37`). The review binds that result byte for byte (`cmd/metasystem/intent_unit_review.go:284-303`, `:337-344`), and the commit refuses any staged path that is not a unit file: "a build may not change ... (a excluded file)" (`internal/goal/branch/commit.go:669-673`; the range rule at `:299-301`). Restoring the file then fails the review's "the goal worktree changed after build round N" (`intent_unit_review.go:299-303`). The builder's instruction about the file is only in the brief's checklist; the engine's own preface to `checked-build.md` says nothing of it (`cmd/metasystem/intent_unit_check.go:74`).

## 2. Decisions

- **D1 The guard is what the check reads.** `changed` (`unit_run.go:1197-1213`) compares `head` (the goal branch head), `index` and `tree` (the worktree's bytes). The `refs` row goes. `Refs` stays in the snapshot as an observation, not a guard. No digest of `--repo` files is added (Q1). The engine is held still by D7, not guarded.
- **D2 One comparison everywhere.** The three struct comparisons become `changed`: `savedRepositorySnapshot` (`:1226`), the proof window (`:636`), and after the read (`:714`). On a refs-only difference `savedRepositorySnapshot` keeps the saved file and returns the saved snapshot, so the baseline stays the round's first one. The base comparison (`unit_attribution.go:223`) already calls `changed` and follows.
- **D3 The fact on the round, each window applied once.** `UnitRound` (`unit_run.go:75-97`) gains `RefMoves []RefMove` (`json:"refMoves,omitempty"`) and `ProofRefsNoted bool` (`json:"proofRefsNoted,omitempty"`). `RefMove{Ref, Before, After, Step string}`: `Before` empty for a created ref, `After` empty for a deleted one, `Step` the step whose window last set `After`. One entry per ref: the first `Before`, the `After` of the latest window applied. `noteRefMoves(round, step, before, after)` parses the two `Refs` texts and merges. Two callers:
  - A step's window, at `unit_step_failure.go:84`. It is consumed once: `Before` is cleared and saved right after (`:87-90`), and a retry takes a new `Before` under a new launch id (`read_sequence.go:59-69`, `:82-88`).
  - The proof window, at `unit_run.go:636`, only while `ProofRefsNoted` is false; it then sets it. Every continuation revisits `:595` and `:628` and returns the saved snapshots, so without the flag a replay of A to B would replace a later A to C. With it, the merge never replaces a later `After`. A person's Retry starts a new proof window: where `RetryFailedStep` renames `proof-before` and `proof-after` (`unit_step_failure.go:204-208`) it clears the flag.
- **D4 The readers are `run.json` and the read brief.** When `RefMoves` is not empty, the read brief gets one paragraph: "While the checks ran, these refs moved; the check reads none of them: refs/heads/main 1d58d986ec to 1627fdbf03." It is written where the read brief is prepared (`unit_run.go:684-699`), also on round one, when `warmRead` returns no packet (`internal/launch/unit_revise.go:379-392`): today the brief is rewritten only when a packet exists (`unit_run.go:688`). The hand-in and the committed read bundle do not carry it (section 1); no lane reader is added.
- **D5 The remaining failure names its input, through to the stop.** One sentence: "the check's inputs changed during the step: " and the names. A name is "the goal branch head (X to Y)", "the worktree's staged state", or "worktree file P" for each path whose raw entry in `Tree` differs, at most five, then "and N more". It is used at `unit_step_failure.go:85`, at `tree_reservation.go:404` (`treeMoved` takes the names) and in the `UNIT_TREE_CHANGED` error (`unit_run.go:1227`). The round keeps the proof window's names: `UnitRound.InputsChanged string` (`json:"inputsChanged,omitempty"`), set at `unit_run.go:636-644` and `:714`. The skipped read's reason at `:673` is `proof-wrote:` plus the same names. `holdFailedStep` (`unit_step_failure.go:139-156`) puts `InputsChanged` in the stop whether or not a step failed. With no failed step the class is "proof: the check's inputs changed during the checks: " and the names. With a failed step the class stays the step's name and reason (`:145-148`) and gains "; the check's inputs changed during the checks: " and the names. Today that branch shows only the failed retry's reason, because the machine retry cleared the first launch's (`:120-121`). So a one-time edit stops the round by name whether its machine retry passes or fails. The cause stays environment; the retry states stay as they are (`unit_step_failure.go:92-126`).
- **D6 The attestation keeps what it checks.** `validGateObservation` (`check.go:18-47`) and the carry workspace guard (`intent_carry_check.go:153-164`) do not change: subject tree, source tree, command digest and both exits. Neither reads refs.
- **D7 One engine for the whole step.** The owner is the step's retained inputs. `retainStep` already copies every input of a step into `step-N-inputs` once and reuses it on every retry and continuation ("Retained command and input bytes survive collection and a step retry", `unit_step_failure.go:45-76`; reuse at `:48-50`). For the declared unit-check step only, it also retains the engine. That step is named `proof:unit-check` (`unit_run.go:585` with the command name at `intent_unit_check.go:72`), and its plan carries a frozen `Check`. Every other proof command is untouched: a plan may name any program, `true` in the base fixture (`internal/launch/unit_test.go:229`), and validation asks only for a non-empty `Argv[0]` (`internal/launch/unit_plan.go:287-289`). Linking such a string as a path would fail before launch. For the unit-check step `retainStep` it reads the step's brief (`PlainBrief`, `internal/launch/plain.go:13-17`), hard-links `Argv[0]` to `step-N-inputs/bin/metasystem` (a copy when the link fails across devices), and writes the retained brief with that path. The launcher runs `Argv[0]` from the retained brief (`plain.go:19-34`). Installation never writes the old file in place: devgate stages and renames (`witness.go:400-405`), and the deploy store never rewrites an engine (`internal/enginedeploy/enginedeploy.go:1-6`). So the link keeps the step's bytes. In the check process, `runIntentUnitCheck` (`intent_unit_check.go:93-141`) puts its own executable's folder first on the check's `PATH` with `commandenv.EngineEnvironmentInDirectory` (`internal/commandenv/environment.go:26-49`) before `Check.Run` (`intent_unit_check.go:127`). `metasystem test impact` then starts from `step-N-inputs/bin`, and its `os.Executable()` names that file, so the watchdog and the worker wrapper run the same bytes for every group. A deployment during the step changes nothing under it; ref moves still pass (D1).

- **D8 A launch id is on the step only after the start returns.** Owner: `startStep` (`read_sequence.go:40-131`). It still names the candidate (`:60-67`) and saves it as `step.LaunchID` with the state starting, so a crash between the save and the start finds the record (`:78-80`). It appends the candidate to `LaunchIDs` only when `driver.start` returns a record (`:112`), or when `Store.Read` finds one (`:78`). A refusal for host load is a wait, as today (decision 136): the codes `LAUNCH_BUILD_CAPACITY` (the `host.load-max` gate, `internal/launch/hostcapacity.go:61-130`, and the hold beside a lane proof, `cmd/metasystem/intent_work.go:548-551`), `LAUNCH_BUILD_PERSON` and `UNIT_WAIT_RETRY` (`read_sequence.go:114-116`). From either site, the before hook (`:107-110`, which passes the capacity code through, `unit_run.go:782-783`) or the start (`:112`), `startStep` puts `step.LaunchID` back to the last listed id and the step back to pending, saves, and returns the code as today; the next `work wait`, an agent's or a person's, tries again. It is never an environment stop and never needs a person's Retry. Any other failed admission (a start error, a missing record, a refused reservation such as `BUDGET_REFUSED`) is one path to the hold: `startStep` restores `step.LaunchID`, sets the step failed, cause environment, reason the admission's words, and `Unadmitted` (a new `UnitStep` field, `json:"unadmitted,omitempty"`, `internal/launch/unit_run.go:99-132`) to the refused candidate; it saves and returns no error, so the runner reaches `finish` and its hold (`unit_run.go:1003-1019`). The machine retry skips such a step: its condition (`unit_step_failure.go:95`) gains `|| step.Unadmitted != ""`, so a refused candidate is never re-entered in the same call. Today's waiting tests keep their wait and change only what the list holds (`internal/launch/unit_admission_hold_test.go:30-39`, `internal/launch/unit_check_host_test.go:106-109`). The next attempt names the same candidate (the suffix counts `LaunchIDs`, `:62-66`) and joins its pending reservation (`unit_launch.go:54-61`, `:75-77`), so no reservation is left behind. A person's Retry then names a launch that has a record. The replay guard (`unit_step_failure.go:184-188`) answers a repeated identical Retry as a replay when the retry was recorded for the current launch. It gains `&& step.Unadmitted == ""`: a retry whose candidate was refused stays resumable by the same act, and a replay while an admitted retry runs stays a no-op. `RetryLaunch` keeps the previous admitted launch. A successful start clears `Unadmitted`. This is the rule for every step, build, proof and read, unit run and standalone read alike. The same rule holds for the candidate's folder under the launch store (finding 480): `startStep` creates nothing there, not the state folder and not the `declared/` remap, until the admission has passed, and `Store.List` (`internal/launch/record.go:224-247`) passes over an id-named folder that has no `record.json` instead of failing the whole listing, so a refused candidate can never block the host's launches again. Amended in revision 7: on a wait code the step stays starting and keeps its unlisted candidate in `step.LaunchID`, as before this design (brief revision 6, V1); the next call finds no record, starts the same candidate and joins its pending reservation, so no listed id dangles. An error the before hook returns, a budget refusal or an interruption, returns to the caller the same way (brief revision 6, V2 and P9): a raised budget admits the same command again, and an interrupted request fails instead of holding; the hold with `Unadmitted` is for a failed start, a missing record or a refused reservation of the launch itself.
- **D9 A reader that writes nothing is retried once, then stops by name.** Owner: `endStep` (`read_sequence.go:171-195`). For a unit read step whose launch failed with no declared output on disk (`readFindingsMissing`, `:197-212`), the cause is environment and the reason "the reader <launch> ended without writing its declared output <path>; transcript <path>", set before the unit's classification at `:180-182`. The transcript path comes from the launch's adapter when it offers one, through an optional interface beside `StopCause` (`launch.go:923-928`): `ClaudeHeadless` resolves `<sessionID>.jsonl` with the search it already uses (`internal/launch/claude.go:200-212`). Otherwise it is the launch's state folder. The environment cause gives the existing one machine retry (`unit_step_failure.go:92-126`). If the retry also writes nothing, `finish` (`unit_run.go:1003-1019`) holds a `read-failed` round whose cause is environment through `holdFailedStep` instead of collecting reads, so the stop's class is "read: " and that reason, naming the second launch. A standalone read keeps `read-no-findings` (`:191-192`). The path the reader is told and the path the collection reads are one value: the launch's outputs after any remap. Where `startStep` remaps a retried step's outputs (`read_sequence.go:94-99`), it also writes the launch's brief: the retained brief with each original output path replaced by its remapped one, saved under the launch's state, and `spec.Brief` set to it. The remap stays, so a retry never shares a path with an earlier writer (`declared_outputs.go:44-60`). With D8 the remap's test reads `len(step.LaunchIDs) > 0`, since the current candidate is no longer on the list when the start is prepared. The machine retry then reads the second attempt's file.

## 9. Rejected alternatives

- Digest the main checkout's testing files, ratchets, floors, settings and `proof/`. The check does not read them (Q1).
- Guard the engine, or take it from the steward's pins or the deploy store (Q2).
- Pass the engine through `WithResourceCustodyExecutable` (`resource_custody.go:36-40`). It is a context value inside one process; `test impact` is a separate process started by the shell, and the devgate caller (`cmd/devgate/gate.go:606`) is not on this path.
- Keep `refs` and leave out `refs/heads/main` only. Other goals' branches and builder branches still stop the check.
- Retry automatically on a refs-only stop. Each retry costs another 25-minute check.
- Hold ref-moving acts while a check runs (decision 126 as the rule). It blocks a person's records and goal verbs, against R-142-m1e.
- An event history of every window for the fact. One flag on the proof window is enough (D3).
- A renderer for `refMoves` in the lane or the board. Nothing acts on it; `run.json` and the read show it.
- A separate goal per finding (a-refused-launch-leaves-no-dangling-id, a-review-drops-an-excluded-file, a goal for the silent reader). Decisions 131 and 132: the round surviving its environment is one design problem, with one page and one critique.
- Drop the excluded path at the review's staging (Q8).
- A refused admission writes a failed launch record instead (finding 473's other option). A record for a launch that never ran is a false fact, and every reader of launch records would have to know it.

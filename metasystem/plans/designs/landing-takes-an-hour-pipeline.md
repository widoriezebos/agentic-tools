## Wido's words (binding)

- The lane is a merge queue: the entry condition for a hand-in is rebased on main and cheap-tier green on its own branch; the lane batches every qualifying goal (`landing.batch=auto`), ejects a goal whose fix came back and lands the rest; main moves once per batch (the brief, 21:35; the plan, "Decided 2026-10-08 21:35").
- The lane IS the seat of every goal in its batch: custody moves with the hand-in and comes back with a return; the lane fixes forward on the batch tree, which is its worktree, with the ordinary seat verbs, one fix unit per red package in parallel, each with a read, under the unit stop rule (one build, at most two corrections), and never loosens a test; records go on the goal the fix belongs to, never on a lane-owned goal; the landing loop stays the lane's; a decision the goal's person owns (a design change, a widened scope) is returned with the question and the goal is ejected (Wido 21:55: "the agent in the lane can do just fine acting like a proper seat"; 22:05: "Acting like a seat makes more sense to me"). The 21:35 line "the lane never edits code" is withdrawn.
- Elegant, robust, maintainable, future-proof, and the smallest thing that works (22:10, for this design: "we had so many issues with the lane"). Every verb idempotent: a repeat whose effect holds is a success (R-129-ui).
- A rebase goes through `work rebase`, never a merge commit: the lane refuses a goal-branch commit with two parents (`internal/goal/branch/range.go:279`); a person's branch is never rebased without that person; a conflict an agent cannot resolve goes back to the seat as a unit (the brief, 21:20 and P0).
- A person's act is never refused except to prevent damage; an agent never gets a person's power (R-142-m1e, R-143-m1e, R-75-m3).
- No caps beyond the vendor's (2026-09-20, reaffirmed 2026-10-06).
- Tests Scrooge as amended 2026-10-08: a unit runs its own new and changed tests plus the test packages of what it changed; the full suite runs once, when the goal lands.
- "Measure before claiming" (2026-09-19): this page claims no minutes; the measure is minutes from a push to the next goal's full proof start (the plan, "Landing measure from 2026-10-08 21:10"), recorded by U5's clock.
- Build the lane mechanism and land it itself, so the queued goals run through it as the test (2026-10-09 08:35); the smallest thing that works, not a nuclear power plant (2026-10-09, this morning): merge the goals onto main in a batch tree, cheap tier with reverse dependents, one sharded gate, one fix round by the lane as the batch's seat with plain commits, gate again, push under the existing push lock, record with U5's clock; on a red the fix round cannot clear, eject that goal and return it to its branch with its reds. Pipelining the next batch, rebuild and replay verbs, per-package custody worktrees, multi-fix chains and prepared records are deferred unless the minimum cannot work without them.
- Measured rules of 2026-10-09 (`plans/machinery-open-findings-plan-2026-10-06.md`): one fix round per gate, every red of the gate in one fix job, then the gate again; a red that also fails on main is main's red and is fixed on main first; the pre-commit guard admits the lane's merge and fix commits by a rule of its own, never by a bypass. The 21:55 and 22:05 words "one fix unit per red package, in parallel" are amended by the measured rule: one fix job per owning goal per gate, covering every red package of that goal; goals in parallel only where their fixes need no shared working tree (the minimum has one, the lane checkout, so the jobs run in series).
- One goal per batch for now (m1e for Wido, 2026-10-09 09:40, under his "smallest thing that works"; reversible): take the next handed-in goal, merge it onto main in the lane checkout, cheap tier from a verified commit base, one sharded gate, push under the existing push lock with the clock; on a red, return the goal to its branch with the complete red list; no lane commits but the merge; a red that also fails on main is main's red and holds the batch; the budget is the existing per-goal attempt limit.
- The lane never resolves a merge conflict (m1e for Wido, 2026-10-09 09:50, under his "smallest thing that works"; reversible): any conflict when merging a goal onto main returns the goal to its seat with the conflicting paths; the seat runs `work rebase G` and hands in again; the lane's merge proceeds only when it is clean.

## What the code says today, and where the brief's premises need correcting

1. **The batch check refuses a fix commit.** `checkBatchLocked` walks the candidate's first-parent chain from the batch's base and accepts only merges of selected members or commits already on main; a plain commit outside main is refused with "does not merge a selected member or main" (`internal/landing/plain/batch.go:554-593`, the refusal at `:582-593`). U3 admits there, after its round 5, a contiguous run of one-parent commits that `fixOwner` validates as one batch-owned goal's reviewed range (unit and read commits, every unit `read clean`, through `InspectStatus`); P3 generalizes the same site to one bounded subject per fix, because fixes serialized at commit and read afterwards interleave (fact 14).
2. **There is no custody move, and the claim check reads the ledger.** `goalBranchClaimCheckWithDeadline` passes only when the goal's `Claimed.Machine` is this machine and `Claimed.Lineage` is the lease holder's lineage (`cmd/metasystem/goal_branch.go:480-508`, the read at `:494-505`); the landing agent runs under lineage `landing-agent` in the lane checkout (`internal/launch/landing.go:27`, `:35-41`) and holds no claim. `work build` calls that check (`cmd/metasystem/intent_work.go:905-913`), then wants a worktree with `goal/G` checked out (`:1037`, `goalWorktree` `:1219-1252`; `prepareGoalWorktree`, `cmd/metasystem/intent_worktree.go:196-231`, which registers the worktree through `enterGoalWorktree`, `:434-457`), and the unit runner refuses a detached HEAD (`requireGoalBranch`, `internal/launch/unit_run.go:352-373`). So "the batch tree as the worktree" is small changes in existing owners, one per owner, not a new fix machinery; the custody fact is U3's `BatchOwned`.
3. **The branch commit owner already serializes parallel commits onto a moving tip.** `inspectCommitBranch` takes the branch's local tip as `baseTip` (`internal/goal/branch/commit.go:154-233`, `:231`); `buildCommitOnto` opens a commit worktree at that tip, applies the round's frozen patch there (`:388-431`, `Apply` at `:395`; a patch that does not apply is `ReplayConflictCode`), calls the review's `BeforeCommit`, commits with the goal's trailer and validates the range from the endpoint tip (`:424`); `installCommitOnto` checks the new tip out in the request's repository, attaches `goal/G` and publishes (`:483-513`, `Attach` at `:502`, `Publish` at `:506`). The review runs that commit under `conn.commitToken` (`cmd/metasystem/intent_unit_review.go:320`; the token at `cmd/metasystem/intent_worktree.go:95-98`), and its `BeforeCommit` reruns the round's check on the commit worktree whenever the parent is not the build's HEAD (`:333-352`, `runner.ProveRoundResult` at `:341`, `internal/launch/round_result.go:21`), so a unit committed after another unit moved the tip is checked on the combined tree before it is committed. Two fixes of different goals therefore need no cherry-pick and no replay: each commits onto the tip as it stands, in the order the token admits them. A patch that no longer applies is a person's decision today: "a person admits a correction of this retained round with its original plan" (`intent_unit_review.go:376-384`).
4. **A written handover exists and is the wrong tool here.** `goal.Handover` moves `Claimed.Machine/Lineage` and keeps `HandedOver{FromMachine, FromLineage, FromEpoch, Batch}` for the return (`internal/goal/verbs.go:1472-1569`; `internal/goal/file.go:333-342`, `:345-362`), but it refuses a person's act (`:1473-1475`), needs a live announced target session (`:1549-1552`) and publishes a ledger commit per move. A hand-in publishes nothing ("a hand-in never moves main", `cmd/metasystem/intent_delivery_owner_test.go:422`, kept by lane-lands Decision 5), and the lane's agent is not alive at every hand-in. Custody is therefore derived from the lane's own records (Decided 1), bound at every write (P3).
5. **Nothing prepares while a proof runs.** The keeper holds the agent's start while a proof runs (`cmd/metasystem/landing_agent.go:291-298` through `ProofHold`, `internal/landing/plain/wake.go:170-176`) and the skill ends the turn after `landing prove` (`skills/landing-agent/SKILL.md:14-16`). The keeper's `Prepare` runs every tick outside the home lock (`internal/landing/lane/agent.go:222-229`; `landing_agent.go:268-273`, `SelectBatch`). A preparation that takes minutes therefore needs a detached process, started the way `Start` starts the proof child (`internal/landing/plain/prove.go:447-516`: argv `landing prove --wait --attempt ID`, a pending record, the launch at `:482`, the process identity at `:490-511`).
6. **A gate's verdict is the command's exit status; a green is reused by tree.** `runCheck` runs the declared command and returns an error for a non-zero exit ("the proving command exited N", `prove.go:985-1041`, `:1036`); `proveInWorktree` is green when that error is nil (`:1122-1126`) and, under `--gate`, red when the report says `not-run` (`:1086-1089`). The report lines are read only for the failed units: `readReport` yields a complete report only when the last line is `LANDING-CHECKED` (`internal/landing/plain/report.go:44-85`, `:50`); U4's `test impact` prints `landing group ID STATUS MS` lines and exits 1 on any red (goal 8, U4 "The verb"), so a preparation that made a missing report red would stay red on every successful run (A4). `Start` and `Settled` with `--gate` read the newest line for HEAD's tree from `gates.jsonl` and report a reusable green at once (`prove.go:421-428`, `:544-549`; `checkBound` `:321-339`; `resultFor` `:924`; `resultsPath` `internal/landing/plain/gate.go:15-20`; `reusableGreen` `internal/landing/plain/scope.go:371-379` takes scope `gate` as plain green); `landing prove --gate` then says "already passed the cheap gate" (`cmd/metasystem/intent_landing_prove.go:259-276`). Gate lines are appended with `appendLine` (`internal/landing/plain/queue.go:135`), one JSON line per write. The agent merges with `git merge --no-ff SHA` (`SKILL.md:54`). So P1 writes a green as a gate line and P2 needs no consumer code.
7. **A gate red without a repeat allowance blocks the tree.** `checkBound` returns `NoRepeat` for a red line whose `Repeat` is not `allowed` when no person asks (`prove.go:321-339`), before any check starts. A speculative red appended to `gates.jsonl` would therefore refuse the ordinary gate when the real merge reaches the same tree (round 1, A3); a preparation's red belongs in its own record.
8. **The pending list includes the running batch.** `pending` (`queue.go:494-538`) returns every waiting, unlanded, unheld entry, the running batch's members first; the first entry is never "the next goal" while a batch proves (round 1, A2); `running.BatchMembers` names them (`prove.go:43-62`).
9. **The proof's cleanup empties `proof-trees`.** `proveInWorktree` removes every worktree under `proof-trees` at the start of every proof (`prove.go:1049-1060`, `removeProofTrees` `:1139-1164`, `proofTrees` `:1166`), the crashed ones included; a running preparation under that folder would lose its worktree (round 1, B1).
10. **The review path validates a goal-branch range, and publishes before the read is recorded.** After the commit, `resolveUnitCommit` calls `branch.ValidateRange(install, endpointTip, tip, goalID)` (`intent_unit_review.go:738-742`, called at `:389`), which walks `rev-list --first-parent` from the merge base (`range.go:245-299`, `:263`), refuses any two-parent commit (`:279`) and any commit whose trailer names another goal (`:176-177`); the review then carries (`:432`) and publishes (`conn.push`, `:449`) and only then records the read (`commitReviewChecked`, `:545`); the read owner requires the unit on a validated range from the endpoint (`RunBranchRead`, `internal/goal/branch/read.go:601-606`; `branchUnitWithRepository` `:308-309`; `branchReadBriefWithRepository` `:325`), and `commitRead` finds the unit commit the same way (`internal/goal/branch/attest.go:893`, `unitCommitInRangeWithReads` `:838`). On the batch tree the range from main holds the batch's merges and, after a parallel fix, another goal's commits, so a goal-branch range is the wrong subject there (round 1 A1; round 2 A1, A2, A3). The subject that is right is the fix's own commit on its own parent: the attestation's subject names exactly `Commit`, `Parent`, `Tree` and the patch digest (`attest.go:31-37`), its folds are the range from the endpoint tip to the commit (`foldRangeWithReads`, `:185`), and `validateAttestation` checks all of that for one commit (`:538-579`, the subject at `:550`); with the endpoint tip the commit's parent the folds are empty and the subject is bounded by that commit alone.
11. **Attribution is per batch today and per package under U3.** `classifyReplay` stops at the first failing prefix and names one `own` goal (`internal/landing/plain/replay.go:212-290`); U3 gives every failed unit an owner (`FailedUnit.Goal/SHA`, and `Commit`/`Fix` when a fix range first failed it) through prefix trees over merges and runs of one-parent commits alike (`fixOwner`, which ends a prefix at a range's read commit), and `ReturnProven` the return by owner (goal 8, "U3: reds are attributed per package"). P3 reads the owners; it attributes nothing; where runs interleave (fact 14) the prefix walk uses P3's per-fix answer from the same helper.
12. **The reprove after a fix is U3's.** U3's fix-round rule scopes the reprove to the failed packages plus what the fix can affect, selected through the adapter (`adapter.Impact`; the lane's `seams.Closure` default is `adapter.Detect` then `Closure`, `scope.go:157-167`; the seam `internal/testpolicy/adapter/adapter.go:71-83`), and `provenGreen` then refuses the scoped green until one full proof ran. A batch tree with fix commits, or rebuilt without a goal, holds a subset of the red's goals (`subsetGoals`, `replay.go:323-327`; `goalsInCommit`, `internal/landing/plain/cause.go:19-25`), so that rule applies to both without change. Nothing in the lane names a Go package or `goadapter.UnitImpact` (round 1, B5).
13. **`work land` has no entry condition.** The lane route reads the branch state, checks the land-once rule and the Units table, and hands in (`cmd/metasystem/intent_delivery.go:2008-2104`); nothing compares the tip with main (lane-lands Decision 2 removed the rebase, and a conflict with main returns the goal naming `work rebase`, `internal/landing/plain/resolve.go:238-246`), and `handLandingSubject` checks only that every unit is built and read (`:2393-2425`): a unit's check runs on that round's change from that round's base (U4), so a later unit's helper change that breaks an earlier unit's test the later selection omits is caught by nothing before the lane's gate (A5). `goalNextStep` prints build, review or land (`:2358-2389`). `work rebase` is the holder's act (`cmd/metasystem/intent_work_rebase.go:102`, `:123`), carries the reads of unchanged units by running their frozen check in a detached worktree (`internal/goal/branch/rebase.go:207`, `:345-357`; `read.go:212-237`; `cmd/metasystem/intent_carry_check.go:18-72`, which builds a `UnitCheck` from the tip's committed declaration and runs it) and runs a resolve round for a replay that stops (`intent_work_rebase.go:165-216`); a judgement conflict asks the person (`:268-320`). That is P0's rebase half and its "returned as a unit"; the carry's check is the shape of P0's cheap-tier half.
14. **The rebase owner replays a line onto a new tip and carries its reads, per unit.** `rebaseWith` (`rebase.go:96`) keeps the old tip under `refs/metasystem/goals/before/<goal>/<tip>` (`:184`; `keptTips` `:70-73`), replays `merge-base..tip` onto `EndpointTip` with `git rebase` and no `--onto` (`replayRebase`, `:411`, the rebase at `:426`: after an ejection that range would hold the ejected goal's merge and every member's branch commits, A2), runs `Resolve` for a replay that stops, then `carryReviewsWith` (`:281`) commits, for each unit whose change digest equals the reviewed one (`:334`), a carried read on the replayed commit after the frozen subject check passed on it (`:340-345`; `:364`, `Carry.FromCommit` the original, validated at `attest.go:575-579`, which requires the original commit to exist in the repository); an attestation is valid only for the exact commit it names (`:550`; `AttestationSubject`, `:31-37`). The read owner says whether a unit is read: `InspectStatus` (`internal/goal/branch/status.go:55-60`) validates a whole goal-branch range first (`:60`), so a run of two goals' fix commits cannot be inspected as one range (A3); `ValidateAttestationAt` (`attest.go:647`) answers for one commit against one endpoint tip, which is the question the admission asks (P3).

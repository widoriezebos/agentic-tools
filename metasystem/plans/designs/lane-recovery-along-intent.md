## Problem, measured

To get the lane going again with what was waiting, a person needed three verbs in the right order (restart, start, then the `landing run --goals A,B` the lane's own question named), because the barren hold lifts on an explicit start that finds a recorded selection or when the lane's own fingerprint changes, neither of which a restart alone produced; before that, a git merge in the lane checkout had to be aborted by hand so the engine could deploy; the status spoke the keeper's vocabulary ("held after 2 runs that left the lane unchanged; a person's recorded selection or a fresh proof of main is needed"). Returning a goal has two verbs (return, the unbuilt retract) chosen by the lane's internal state; landing despite a red main is spelled `--exception GOAL_LAND_TRUNK_RED`. Every one of these is available only to a person who knows the mechanism.

## Decisions

- D1 `landing resume` is the one act for "make the lane work again with what is waiting". It aborts the pending merge only when that merge is abandoned: the abandonment is bound to the merge actually pending by both coordinates the resolver uses (HEAD equals the abandoned record's checkpoint commit AND MERGE_HEAD equals its tip; a record abandoned for an older merge of the same tip against another main says nothing about the newer one), no job owns the lane checkout (the resolution job's record is not running), and the checkout's writers have settled — all three on every abort path; never on "main moved" alone. The stale case of 2026-10-12 12:06 is a merge still pending (HEAD = the record's checkpoint, MERGE_HEAD = its tip, record `resolving`) whose resolution job has ended (its launch record is terminal) while main advanced by code: resume owns that transition — it marks the record abandoned with the reason "superseded by main's code move; rebuild", aborts the merge, and the lane rebuilds on the current main; the same identity and settled-writer checks apply, and a job still running keeps its merge; lifts a barren hold, or a selection hold (`landing.batch=person`: the lane waits for a person's selection), by recording the selection of every admissible waiting goal (oldest first) as the person's, reopens or restarts the batch on the current main when the sealed batch is behind main by code, proves main when it is owed (open incidents and no proof of the current main, or a barren hold with no selectable goal: the keeper's own remedy for that hold is a fresh trunk proof, which resume requests), and starts the agent. Each step runs only when its condition holds; a resume on a healthy running lane changes nothing and says so (R-129). It never ends a proof a person started and never touches a merge the lane still calls current.
- D2 `landing give-back G --reason TEXT` takes a goal out of the lane for its seat whatever the lane's state: waiting, admitted, merged, proving, returned-pending. It is the person's return where a return applies and the retract (lane-recovers D4) where the goal is mid-flight; the lane records its disagreement when its last check attributed the red elsewhere (lane-recovers U3). Never refused (R-142/143); the only outcome besides done is "nothing to give back: G is not in the lane".
- D3 `landing land-anyway G --reason TEXT` is the person's exception: it admits G's hand-in despite main's open incidents and records the decision with the reason and the person; the lane's question for a trunk red names this verb. The old spelling (`work land G --exception GOAL_LAND_TRUNK_RED`) stays as an alias for scripts.
- D4 `landing deploy` deploys the lane's engine from origin's main for the lane install: it refuses nothing a person asks, waits for a running proof unless `--now`, aborts a merge the lane calls stale and refuses while one is current, builds and activates the install's own engine (the binary the health fact stamps), restarts the supervisor, and leaves the lane's run state exactly as it found it (a paused lane stays paused: finding 185). The person's terminal is proven as for every lane act (one enrollment per install today; one per machine when shared-state-in-the-ledger lands).
- D5 `landing stop` ends the landing agent's session through the settle path as well as pausing admission (finding 135, LS-04), and revokes any standing continuation a person recorded through a pause (`StandingPause`, the permission `landing run --goals` leaves for a paused lane), so the next keeper cycle launches nothing: "stop" means stop; `landing restart` records the person's selection AND performs the keeper's explicit continuation (the step `landing run` takes), so a restart alone lifts a barren hold and starts execution (finding 200; the keeper clears the hold only on an explicit run with a recorded selection).
- D6 Every status headline, question and refusal names the intent verb that resolves it and nothing else: resume, give-back, land-anyway, deploy, stop, start — and `landing prove` with its flags where a person's proof or classification is the act (the agent's own skill requires it; LR-03). The mechanism words (barren runs, recorded selection, sealed window, fingerprint, admission, exception code) move to `landing health`, where the steward reads them. A test walks every headline, question and remedy string in the lane's packages and fails on a mechanism word or a verb outside the six intent verbs and `landing prove`.

## Step 1 and what is deferred (R-121)
Step 1 is U1 (`landing resume`, `landing stop` ending the session, `landing restart` recording the selection): after it a person resumes a stopped, held or stale lane with one verb and stops it with one. Deferred, in order: U2 give-back and land-anyway, U3 deploy, U4 the wording rule. The steward's acts (lane-steward U2) switch to these verbs in a later correction, so the machine and the person recover the lane the same way. Not in this design: a terminal enrolled per machine (shared-state-in-the-ledger), partitioning the proof.

## Threat model
(1) A resume that acts when the lane is healthy: every step is conditional and idempotent; a test asserts byte-identical records after a resume of a running lane. (2) A resume that discards work: it aborts only a merge the lane itself calls stale and never a proof a person started. (3) Give-back used to take a goal the person does not own: the lane records who gave it back; the seat sees it; R-142 stands. (4) Land-anyway hiding a real main red: the decision, reason and person are recorded on the push and in the incident. (5) Deploy during a proof: waits by default; `--now` is the person's explicit choice and the running proof is restarted by the lane as after any engine change. (6) The wording rule rotting: the test over every remedy string.

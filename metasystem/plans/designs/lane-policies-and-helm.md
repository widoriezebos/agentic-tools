## What this goal delivers

1. The lane's batch size, proofs, response to red and response to red main are declared, settable and readable settings with provenance. Their consumption, including `person` preparing and asking for an action, belongs to `lane-reads-its-policies`.
2. `helm take` makes the scope's policies `person`; take, return and status support `--all` for this computer.
3. Claims carry their design's edit areas. Automatic claims with overlapping declared areas wait until the earlier work lands or is dropped; unknown areas on either side publish with an “areas unknown” warning.

**Step 1 is U1.** After it lands, a person can set, inspect and validate every decision policy and its provenance; agents can read policies but cannot write them, and `settings.apply` is read-only. The display names which consumers are still pending. U4 applies the helm override and U5 adds area checks to existing claim admission. Build order: U1, U4, U5. The lane consumes U1's four landing keys only in the follow-up `lane-reads-its-policies`.

The threat is mistakes, stale state and interrupted processes on a trusted host. Scope is the three remaining units. No new dependency, records branch, generic scheduling service, file lock over edit areas, or implementation is authorized by this design acceptance.

## Decision 1: one settings owner, with effective value and provenance (U1; mechanism 1)

**Keys and scope.** All values are one token. `auto` is the built-in policy default. The batch policy is named `landing.batch`, as mechanism 1 specifies; settings show describes its batch-selection meaning beside the checkout-path meaning of `landing.batch-root`. Numeric caps are decimal integers: batch N is at least 1; review corrections N may be 0. No arbitrary upper limit is introduced. `settings.apply` defaults to `boundary` and is a timing declaration, not a decision policy; the helm never writes the invalid value `person` to it.

| Key | Values | Owner checkout | Consumer or deferred owner |
| --- | --- | --- | --- |
| `landing.batch` | `auto`, N, `person` | registered lane | Declared/settable here; batch selection in `lane-reads-its-policies` |
| `landing.proof` | `auto`, `person` | registered lane | Declared/settable here; full-proof decisions in `lane-reads-its-policies` |
| `landing.on-red` | `auto`, `person` | registered lane | Declared/settable here; red decisions in `lane-reads-its-policies` |
| `landing.trunk-red` | `auto`, `person` | registered lane | Declared/settable here; hand-in, admission and push in `lane-reads-its-policies` |
| `seat.driver` | `auto`, `person` | seat | U4 display/override; driver consumption deferred |
| `review.stop` | `auto`, N, `person` | seat | U4 display/override; unit-review consumption deferred |
| `goal.raise` | `auto`, `person` | seat | U4 display/override; budget consumption deferred |
| `question.route` | `auto`, `person` | coordinator | U4 display/override; routing consumption deferred |
| `settings.apply` | `boundary`, `now` | committed repository declaration | displayed; boundary consumption deferred |

**Resolution.** New `config.ResolvePolicy` is the single typed reader used by `Get`, `KeyOrigin`, settings show, helm views and board composition. The follow-up wires lane decisions to this same reader. It takes a canonical checkout and explicit readers for the lane/coordinator registration and helm. Inject the policy registry reader into config from the command/composition layer: the lane already imports config (`internal/landing/plain/scope.go:15`, `wake.go:16`), so config must not import the lane. It resolves: that checkout's helm override; that checkout's configured value; the coordinator checkout's configured default; built-in `auto`. Inside either configured layer, preserve `Get`'s flag/environment/local/committed precedence. An environment override belongs only to the calling checkout; a seat's process environment cannot override a lane or coordinator it reads. The compiled default is applied after the coordinator lookup, not before it. An `Undeclared` coordinator skips that layer and resolves to built-in `auto` when the checkout supplies no value; only `Corrupt` or an unreadable file holds an agent at that layer (`cmd/metasystem/intent_operations.go:494–511`; `internal/brain/brain.go:148–181`). Unrelated keys keep today's resolution.

New `policy` metadata is stored per canonical checkout, beside the existing helm state, keyed by name: `name`, `checkout`, `value`, `set-by`, `at`, `previous`. `previous` carries the underlying value and source to display under a helm. Configuration remains the value authority; the record supplies authorship, not a second competing setting. `set-by` records the name from the successful proof/enrollment, or `author unknown` if that enrollment has no name; a supplied name alone is never proof. For manual file/environment changes without matching metadata, report “set outside settings; author unknown”; never reuse an old author's name for new bytes. Built-in values say “built-in”. Missing metadata is legitimate legacy state.

Add all eight decision-policy keys to `authoritySettings` (`cmd/metasystem/intent_work.go:2429`): `landing.batch`, `landing.proof`, `landing.on-red`, `landing.trunk-red`, `seat.driver`, `review.stop`, `goal.raise` and `question.route`. The existing check at `:2305–2308` requires `directPersonProof` before any policy value or provenance write, including a write routed to the lane or coordinator. For settings writes, first accept direct-person proof at the calling checkout, discovered from the working directory independently of `--repo`; failing that, accept direct-person proof at the resolved destination. Each attempt requires `Proof.Helm == nil` and `EnrolledTerminalFor` for that attempt's root (`intent_work.go:2472`). Refuse for lack of direct-person authority only when neither root proves it. When no checkout contains the working directory, use the resolved destination as the proof root; an explicit `--repo <lane>` therefore works from outside every checkout. Enrollment is per checkout (`internal/humanauthority/authority.go:659`); carry the successful proof and its root to the exact write target. Resolve `set-by` from that successful proof/enrollment, recording `author unknown` when the enrollment has no name, never from an unproved `--by`. Keep the existing `directPersonProof` roster caller unchanged (`cmd/metasystem/intent_roster.go:65`): roster set continues proving at its resolved `--repo` root; the settings-specific fallback and name result must not change that caller's contract. A helm, grant or supplied name never substitutes for that proof. `settings.apply` stays committed-only and read-only through these verbs. `settings set` then writes through the existing configuration owner and records provenance under a per-checkout settings lock. A crash between writes leaves a usable setting with unknown provenance, never a fabricated author. A repeat does not rewrite an identical value's original attribution. `settings show KEY` displays effective value, canonical checkout, source, setter and time, plus underlying value and helm holder when overridden. Both APIs use the same resolution result. `settings check` validates grammar and scope structurally, without needing the lane to be alive or a session to exist.

Scope comes from the registry, not from a setting naming its own owner. For the four lane policy keys, an agent's `settings set` refuses without changing the value; its remedy names `metasystem settings set KEY VALUE --repo <lane>` to run at the person's terminal enrolled at either the calling checkout or the destination lane. The remedy permits either proof root and never implies the agent can retry into authority. A person's request from a seat targets that registered lane immediately and reports its path. This applies the brief's wrong-checkout restriction to agents while honoring its stronger No HAL rule. Only the four new policy keys use this restriction; existing `landing.*` configuration is not reclassified by prefix. Fleet `question.route` similarly targets the coordinator. For a `question.route` write with no declared coordinator, the destination is unknown, so the write holds and names `metasystem settings coordinator --declare --by NAME --repo PATH`, filled where known; a read-only `settings coordinator` is only diagnostic. A person may make that declaration from the intended checkout and then set the key. An unknown destination cannot be guessed without risking a write to the wrong checkout.

`settings.apply` follows mechanism 5's committed declaration rule and is read-only in U1: read, show and validate its committed value, with no new `settings set` writer. A person edits the committed declaration through the existing repository workflow. Do not change 1a's `proof.*` writer contract here. Until the boundary consumer exists, both values are displayed as “applies at the next verb; unit-boundary application is not implemented yet.” In-flight commands keep their already admitted inputs. A helm override is visible immediately at the next policy read regardless of that declaration; lane action consumption remains deferred.

## Decision 4: the helm is the person's policy override (U4; mechanism 1)

`helm return` becomes person-only, and its help text and the hook message at `internal/hooks/runtime_hook_stop.go:145` must change with it to direct return to the person's enrolled terminal.

**Sites.** Extend `helm.Record`, `Write`, `Remove` (`internal/helm/helm.go:22`, `:143`, `:168`) and the existing take/return/status commands (`cmd/metasystem/intent_helm.go:144`, `:172`, `:388`). Reuse `machine stop --all`'s host discovery (`cmd/metasystem/intent_machine.go:870`) and coordinator declaration (`cmd/metasystem/intent_operations.go:457`). The agent/person boundary is existing terminal proof, not `helmAdmitter`'s permissive fallback (`cmd/metasystem/helm_admits.go:97`).

A seat take overrides `seat.driver`, `review.stop`, `goal.raise`; the lane take additionally overrides its four landing policies; the coordinator additionally overrides `question.route`. All become `person` in one atomic signature write. New policy entries on the helm record carry mechanism 1's fields, including their underlying values and provenance. The configuration values themselves are not overwritten: an unreadable previous setting cannot stop a person taking or returning the helm. The absence of a snapshot on a legacy signature still means all applicable policies are `person`.

Return removes the override and exposes the configured values again. A `settings set` while held changes the underlying configured value and updates the displayed `previous` value, explicitly saying it will apply on return. It does not drop the helm. Thus a later person's setting is not lost when the earlier take is returned. Repeated take preserves the original take's identity/snapshots unless a person deliberately replaces its holder; repeated return is unchanged. No stack of nested helms.

A lane take only writes its policy override signature. Return only removes that override; a manually recorded immediate pause survives return. Return never rewrites malformed settings from a guessed previous value. Signature write/removal failure reports an incomplete act; retry uses the same idempotent owner.

Lane execution changes are deferred to `lane-reads-its-policies`; U4 changes no keeper preparation or start guard. Existing steward holds and periodic trunk-timer suppression remain in place while the helm is held.

`--all` enumerates the current computer's registered/discovered primary checkouts, includes the registered lane and local coordinator, canonicalizes and deduplicates shared Git common directories. Prove the person once at the calling terminal, carry that proof to each exact target; do not demand that terminal be separately enrolled in every target checkout. Remote computers are outside the act. Take, return and status share this enumeration. Take/return run sequentially and report each success/failure; there is no fleet transaction or rollback of successful takes. A retry is idempotent. An unreadable registry yields a partial result for known targets plus the direct `helm take --reason TEXT --repo PATH` or `helm return --repo PATH` command for a missing target, retaining the take's supplied reason; never “all done” when enumeration failed.

**Five answers.** Production callers are the three helm verbs and their `--all` wrappers; policy readers consume the signature and status/board consume the same effective records. Targets, actor proof and underlying settings are read at the act, and each write rechecks its target identity under the appropriate lock. Take and return are person-only, including removal of corrupt signatures; an agent cannot return someone else's helm to escape `person`. A person's direct `--repo` act works independently of fleet enumeration and session state. Corrupt policy metadata or signatures cannot veto a proved person's take/return; preserve diagnostic bytes where readable, report partial I/O failures, and retain a hold after an unconfirmed take. An agent encountering corrupt authority cannot become a person by asserting a name.

## Decision 5: a claim records areas; overlap sequences work (U5)

**Sites.** `DeclaredUnits` reads the table by column name (`internal/launch/admit.go:457`; table parsing at `:210`). `ClaimRecord` has no areas (`internal/goal/file.go:337`); parsing and rendering are at `:1440`, `:1862`. `claimRequest` mutates against the fetched ledger (`internal/goal/verbs.go:1553`), with 1a's claim/queue adapter at `cmd/metasystem/landing_plain.go:38`. At-rest quota validation is `internal/goal/validate.go:399`; it has no host queue and must not acquire one.

New `launch.DeclaredAreas` reads a page-level `Areas:` list and/or an `areas` column in the accepted design's Units table. Union both when present; deduplicate. Paths are relative to the application repository root, with `/` separators, including `metasystem/` in this repository. A literal directory ending in `/` means its subtree; literals name exact files; globs support `*`, `?`, character classes and full-segment `**`. Normalize `./` and separators, reject escapes outside the repository. Multiple values use a JSON string array on `Areas:` or in a cell, avoiding ambiguity for spaces/commas in filenames. Ordinary single path/glob cells remain valid. The existing unit-name/size parser continues accepting tables with additional columns.

New claim fields are `areas`, `areas-source` (design id and content digest), and `areas-known`. They are one snapshot on the claim, not a permanent reservation register. The command resolves the same accepted design used for unit admission, pins the page bytes, and passes them into the claim transaction. At publication it verifies the accepted design binding still stands; a changed binding is reread, not silently claimed with older areas. A missing declaration is **unknown**, not the empty set. An explicit `Areas: []` declares that this goal edits no files. For legacy claims, first read their accepted design at the fetched ledger tip; if it supplies no areas, retain unknown. No bulk migration commit.

New `goal.AreasOverlap` conservatively compares declared patterns, not just files that currently exist, so two goals adding the same new file conflict. Take each normalized pattern's literal prefix up to its first wildcard (`*`, `?` or `[`); a pattern without a wildcard uses its whole literal. Two patterns overlap when either literal prefix is a prefix of the other. An empty prefix overlaps every known pattern. This deliberately sequences patterns with different suffixes under the same prefix; it does not compute exact glob intersection. Return the declared pattern pair and prefixes as the reason, without inventing a matching path. Malformed input is unknown. Unit tests include different suffixes under one prefix, disjoint prefixes, nested directories, an absent future file, `**`, and classes.

New `goal.ClaimAreas` combines the candidate's snapshot with all other claims in the fetched ledger, including other machines and arc members, and 1a's newest queue state. A claimed goal continues excluding its areas while waiting, incident-held, returned or being corrected. Landing containment against the seat's current local main releases areas even before `goal done` (`cmd/metasystem/landing_plain.go:3–6`). U5 adds no main fetch: existing repository synchronization advances that ref; a stale main only holds areas longer and cannot establish new containment. Reread the local main tip for each publication retry, separately from the fetched goal ledger; drop/abandon releases them. Ordinary release/park ends active ownership only if no waiting hand-in remains. A waiting entry retains its areas even if its claim was released; copy the claim's area snapshot onto the hand-in for this case. A returned goal whose claim remains live still excludes its areas. Records-only entries inherit their goal's areas. No file writes are intercepted.

Automatic claims are refused when overlap is established, naming the blocking goal and conflicting area. The next step is `metasystem goal claim` **after that goal lands or is dropped**. Until then the seat may wait or claim another genuinely disjoint ready goal; next-goal selection filters with this same predicate instead of offering the blocker again. With all candidates excluded it reports the dependency, not “no approved work”. For an otherwise admissible claim, unknown areas on either side publish with a recorded “areas unknown” warning naming the affected goal, design or unreadable queue path; unknown is never reported as proven disjointness. `ClaimAreas` and `AreasOverlap` take no actor input and have no person-warning branch. `goal.Claim` refuses humans (`internal/goal/verbs.go:1384–1385`); `lane-drain-and-fresh-claims` adds actor-aware advice with person claims. No ninth decision-policy key is introduced; a helm does not turn an agent's claim into a person's claim.

Unknown areas on either side never block an automatic claim: sequencing applies only when both sides declare known areas. No accepted design declares `Areas` today, so legacy claims must remain usable. Record “areas unknown” on the published claim/history and show it in the claim view; missing, malformed or unreadable area declarations follow this warning path. An unreadable queue also counts as unknown areas: an otherwise admissible claim publishes with the recorded “areas unknown” warning naming the queue path, never a hold caused by that read failure. A computer with no configured lane reads as an empty queue, matching `cmd/metasystem/landing_plain.go:40`; it does not generate an unreadable-queue warning. A known overlap with another declared claim still holds even if a different claim has unknown areas. Overlap is checked again inside every publication retry; concurrent claimers cannot both publish from the same old ledger. Queue transitions can only release an exclusion or retain an existing claim's exclusion; re-hand-in of an unclaimed/released goal must recheck areas before restoring it. This prevents a queue-only admission racing another claim from bypassing the rule. No queue lock is held across a network publication.

**Five answers.** `DeclaredAreas` serves claim admission and the hand-in snapshot; `AreasOverlap` serves `ClaimAreas`; frontier selection and the claim transaction call `ClaimAreas`. Use the existing fetched claim-publication transaction and reread per retry; selection's existing projection is advisory until that transaction checks it; the queue and the separately observed local main tip are reread for that attempt, with queue-read failures carried as unknown-area warnings naming the queue path rather than swallowed or used as holds. Stale main retains exclusions until containment becomes visible. These predicates serve agent claims only; person overrides are deferred with person-claim admission. Once local main shows the blocker's landing, or the blocker is dropped, its area exclusion clears on the next read; the printed claim command can then succeed subject to ordinary admission; declaration failures let otherwise admissible claims publish with the recorded “areas unknown” warning. Unreadable ledger is not safe to overwrite, but unreadable areas warn and do not hold automatic admission; an unreadable queue follows the same warning path and never holds automatic admission; no configured lane means an empty queue. Area advice does not grant claim or session authority; person-claim admission and its end-to-end proof belong to `lane-drain-and-fresh-claims`. Existing claims without areas are readable and never invalidate the entire ledger.

The “more than one goal of a seat waiting in the lane” bound deferred from 1a belongs to goal 4, `runs-advance-on-their-own` (“runs advance”). Lifting it requires changing claim quota and at-rest validation together, beyond U5's claim view; goal 4 consumes this goal's claim/queue snapshots. This goal retains the current quota and does not promise additional capacity merely because two areas are disjoint.

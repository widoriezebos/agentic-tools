## What it delivers

The first goal measures recorded unit work, makes settings and per-unit check selections accountable, stops further automatic process changes when cost drifts or an intervention class repeats, and reports observed process cost separately from external delay. It does not stop useful work merely because elapsed time exceeded an estimate.

**Step 1 is U1.** After that unit, `work status GOAL --work UNIT` and the goal status route show recorded build, check, read, correction and waiting time, reported tokens, and the design estimate. They derive the practice measures from evidence instead of a person typing numbers. This is useful without any process-change gate. The brief's “unit status” means the existing `work status GOAL --work UNIT`; no `unit` command family is added.

Build order remains **U1, U2, U3, U5, U4**. U2 supplies settings/check acts, their consumption identities and executable person questions without depending on U3. U3 compares measurements with bands. U5 presents the result. U4 stops repeated settings/check interventions through U2's admission points. Each is an independently usable increment.

### 2. Settings and unit checks are recorded process acts (U2)

**Read sites.** `internal/config/policy.go:49` defines `PolicyRecord`; `:285` overwrites one key's provenance, so it is not change history. `:97` owns policy precedence and `:269` owns the settings lock. `cmd/metasystem/intent_work.go:2280` owns settings writes; `:2287` refuses committed-only keys. `cmd/metasystem/intent_policy.go:302` owns routed policy writes and `:324` rechecks destination under lock. Direct-person proof is checked at `:243–247`, at calling checkout with destination fallback. `internal/config/defaults.go:18` owns setting declarations. Current policies are person-only in `cmd/metasystem/intent_work.go:2439`; `process.change=auto` must not remove that restriction.

Introduce `process.change=auto|person`, default **person**, scoped to the canonical checkout where the setting takes effect, under existing coordinator fallback and helm precedence. This is an explicit exception to the generic built-in `auto`. It instantiates **“NO HAL 9000 … never rewrites its own rules without [a person]”**, as proposed by brief U2. It is itself person-only, is included in helm take/return, and is recorded when changed. Agents cannot change the policy that admits their changes.

For non-committed, non-protected keys under `proof.*`, `review.*`, `landing.*` or `launch.*` accepted by `settings set` (for example mutable `launch.*` settings), the changed value passes through new `processchange.ApplySetting`. Reuse existing direct-person validation for `landing.batch`, `landing.proof`, `landing.on-red`, `landing.trunk-red`, `review.stop` and `process.change`; successful person changes get provenance through the same writer but need no new agent proposal route. `proof.cheap`/`proof.full` remain committed-only and outside this settings adapter. Prefix membership selects accountability; it does not grant authority or make an ordinary setting a decision policy. Existing setting validation, destination routing and write mechanics remain owners of their respective behaviors.

Extend `settings set KEY VALUE` with `--goal G --rule FILE#ANCHOR --measure NAME --reason TEXT` for a proposal, and `--act ID` to execute a retained proposal. A rule reference resolves to repository bytes and an exact section at a recorded source revision; the act retains the cited text/digest and why this delta instantiates it. A design stage is cited by design id, section and revision in the same field. Automated validation proves identity and existence, not semantic agreement with English. Under `person`, the question presents the delta and the citation for the person's judgment. Under `auto`, an agent needs a readable citation and measure, and every pre-existing authority gate still applies. The machinery never claims a random citation proves the change wise. A person may explicitly supply a reason without a citation; record “person-directed”, not a fabricated rule.

Record `ProcessAct` in `<target-state-root>/process/acts/<id>.json`, beside the canonical checkout's settings state: id; requesting goal/episode and actual actor lineage; proven authority **including `Proof.Helm` and its grant identity**; target checkout/key/layer or goal/unit check target; before and after values/argv including unset (for a first changed check, before argv is the resolved applicable declaration); citation/digest and explanation; expected measure/direction; class; proposed/applied timestamps; effect status; predecessor and optional reverted-act id. Store each operation separately, using existing atomic-file and lock utilities. U2 supplies the act read/replay path and target process lock; U3 extends that same reader as `ReadState` with stop files, so U2 depends on no later unit. Never copy a whole settings file, which may contain secrets. Process attribution distinguishes `direct-person` from `agent` even when authority succeeds through a grant. `internal/humanauthority/authority.go:916` creates helm-shaped proof and `:937` admits helm/attorney fallback; `Proof.Helm != nil` is agent-owned for U4 and U5. Under `process.change=person`, both plain-agent and grant-backed acts are held unless execution independently carries direct-person proof. Reuse `directPersonProof` rather than checking only OutcomeProven or the granting person's name. The existing `policy` record remains the effective-value attribution; an act references it and never competes with configuration as value authority.

Under the settings lock, read current target bytes and effective `process.change`, prepare the act, execute the existing write, then mark it applied. Retry reconciles target bytes: before means still pending, after means effect recorded, any third value is a superseded/conflicting proposal. No repeated write or duplicate intervention. A person can replace an explicit value despite unreadable act/policy metadata; preserve unknown bytes and report history unavailable. Actual inability to preserve or write configuration is an I/O failure, not a policy veto.

Agent under `person`: persist the proposal and one question; do not change the setting. Its `needs` is the exact `metasystem settings set KEY VALUE --repo CHECKOUT --act ID` command at the person's terminal, with all known values filled. Authority is proved again at execution; `--act` and `--by` are not proof. A failed/no-op unrelated write or a text answer cannot close the question. Successful application of that exact operation does.

**The recorded unit check is in scope now.** `cmd/metasystem/intent_work.go:806` reads the agent-selected `work build --check`; `:901` writes it to `UnitPlan.Proof`. U2 adds `processchange.AdmitCheck` at this composition/admission boundary before any launch, reusing the act, citation, policy and question owner. `work build` accepts the proposal citation/measure/reason and retained `--act ID` fields already defined above. Persist the resolved committed cheap/full argv, selected argv and prior admitted goal-unit check identity. Compare argv arrays exactly, including argument order, without shell-equivalence guesses. Compare with the goal's previous admitted unit check when present and with the resolved declaration for the check's rung (`proof.cheap` for a unit, `proof.full` for full integration); either difference is a process change. A normal cheap check is not changed merely because it differs from the other, full rung. The two declaration snapshots also support U1's independent full-suite equality test. A missing required comparison is unknown and holds agent admission, not silent equality.

A differing first selection with no previous check is `added-check`; replacement of a previous nonempty check by different argv is `widened-check`. These are conservative intervention classes from argv difference, not claims that arbitrary shell commands have a semantic subset relation. Record both comparisons and class on `ProcessAct`. Under person policy hold before launch and print the exact original `work build G --work U --brief FILE --act ID --check ...` with frozen argv and impact for execution at the person's terminal. Under auto require the citation and existing build authority. Revalidate the previous check under the target process lock; successful plan admission and consumed act id reconcile by operation id after interruption, never launching twice. A later unrelated policy change cannot steal attribution. With no last in-band observation, use the run's initial frozen baseline and mark attribution provisional. Attach other matching acts and external load/provider evidence to that process-change cause; external evidence never demotes it to unclassified or changes the first remedy. With no matching consumed act, choose evidenced load/provider/design or unclassified. Overlapping elapsed time is reported once with multiple evidence links, not wholly charged to each cause.

The first act printed for `process-change` is U3's exact reverse command, with the impact and before/after shown. The default policy makes it a person's remedy. Undoing the process change resolves that episode's intervention hold; it does not erase sunk hours or declare the cumulative measure in band. Keep that episode as “resolved by removal”, and require new affected executions to open a new episode. This prevents an irreversible elapsed total from immediately reblocking its own remedy. Other causes ask for a reasoned, scoped continuation through the existing `work revise` person act when a revision is actually pending; otherwise the question requests the pending settings/check act with a reason. No phantom revision is created just to clear a process stop. Successful explicit continuation acknowledges only the named episode, not later drift.

The unset branch reuses the settings parser/writer and authority checks; it does not remove an entire file. Reversion is a new act, never deletion of history. If a later act changed that key, an agent cannot overwrite it using old before-bytes; prepare a fresh question showing the intervening value. A person's explicit value wins after the impact is printed. A successful reverse is exempt from the process-drift/repeat hold it remedies, but not from identity, destination or data-preservation checks. No remedy asks anyone to set `process.change=auto` or to return the helm.

For a check act, U3 prints the same admitted `work build` selection with `--undo ID --check BEFORE_ARGV...`, its known goal/unit/brief and impact. The build owner handles `--undo` as selection restoration only: record an inverse selection act for the next execution and return without launching. It neither reruns nor rewrites a completed or active plan. U2 admission consumes the restored selection on the next ordinary build; its original full argv comparisons and authority still apply. A superseding selection requires an explicit person decision, as with a changed setting. No automatic extra check is launched to prove removal. U3 resolves only the stop tied to the successfully restored selection.

Unknown measurements cannot authorize another automatic process intervention. They do not block ordinary status, useful work under its already admitted plan, or a person's explicit act. An unreadable process record is shown ahead of any stale green summary. A corrupt history is never interpreted as “no changes”.

### 4. The same detector covers settings/check interventions by the steward (U4)

The production seams are U2's `ApplySetting` and `AdmitCheck`, reached by a steward or coordinating agent using settings verbs and `work build --check` as well as any other caller. Do not instrument only a proposed steward helper that nothing calls. Current `UnitRunner.Revise` at `internal/launch/unit_revise.go:67` and budget owners are outside this seam and explicitly in the follow-up.

Add `processchange.RepeatedClass` at proposal admission under the target process lock and the same actor/episode observation. Classes here are `added-check`, `widened-check`, `changed-policy`, with `changed-process` for changes whose direction cannot be determined. Known checks use retained before/after command/check identities; labels from a requester cannot turn a repeat into a new class. Arbitrary command equivalence is not inferred. `added-round` and `changed-budget` arrive only with their real producers in the follow-up.

The window is keyed by **canonical target checkout and actual actor lineage**, with the goal execution episode resolved from that lineage's current work, not from optional `--goal`. Share history across the episode's units, sessions and resumes; the lineage is the stable seat/actor identity, not a fresh invocation id. Require an agent proposal to name the resolved goal (positional G for `work build`, `--goal G` for settings), and hold a missing or mismatching goal before effect; omitting it never opens a fresh window. A genuinely new recorded goal episode may begin a new window, never a requester-supplied goal string. Direct-person acts remain explicit and recorded when no goal is available. The second intervention of one class stops **before** applying it and asks a person. Source: the plan's stop-table phrase “the same intervention twice” and the brief's U4 “a class repeating within the goal's window”. The brief's third-added-check example would be caught already at the second; no third-attempt default is invented. Attempts/proposals replaying one operation id are one intervention. Rejected proposals do not inflate applied-cost totals. Helm/attorney grant acts count as the agent's interventions, with granting authority attached, and never as person bypasses. Direct-person acts are recorded but never refused by this detector; undo acts are linked reversals, not new attempts to improve the process.

The progress measure is U1's named expected measure moving in the declared direction since the preceding applied intervention. With no completed observation it is unknown, not improvement. A repeat stops whatever that measure says; any drift stop already standing is reused, not replaced by a later clean observation. Stop identity includes target checkout, actor lineage, resolved goal episode, class and proposed act id. This is a process loop with an intervention-class reason, using U3's stop/question path. ### 5. Report own process cost without inventing causal savings (U5)

A current drift stop is first, then changes and their measured cost, then external delays and unknown coverage. Example: “Automatic process changes are held: this unit used 300 minutes against an estimate of 70; 150 recorded minutes were checks under the widened setting.”

“Own process cost” means measured work executed under a matching applied process act, with act id and actual actor shown. In particular, a helm/attorney-backed act is the agent's own process cost: display its lineage and grant provenance, never reclassify it as a person's external decision. Direct-person acts are labelled separately. It is **not** a claim that all those minutes were avoidable or that removing the act would save them. Added independent check executions can be charged in full; a widened check has observed cost and an unknown counterfactual unless an actual comparable earlier execution exists. Baseline product work, external load/provider delay, main-red work and unclassified time are separate. Never relabel all unclassified time external. Do not double-charge overlapping steps or a full integration suite across units. Tokens have the same observed/unknown distinction.

Use a report watermark of included operation ids and observation revisions, stored with the existing successful channel report state. It advances only after successful delivery. Failed delivery retries the retained message and watermark; a new act appearing meanwhile is included next time. Status/fleet reads do not advance it. With no readable watermark, include all retained acts and say the report boundary is unknown. Include additional cost accrued since the last report for an older still-active act; filtering only by act creation time would hide that cost. Remote seat evidence is displayed with observation time and missing-seat warnings, never treated as a current local authorization snapshot.

## 1. Problem

A unit round is finished only by the process that launched its last step. A step that outlives that process is never booked.

The case (finding 484). a-red U1a2a round 4. The first read ended without usable stop inputs (the class of finding 477), so the round stopped "unavailable-stop-inputs". At 02:57 `work review` took the unknown-read path. `RetryUnknownRead` renamed the old read steps `unknown:read...`, appended `read:fresh`, launched it and waited in `advanceStep` up to `DefaultWaitTimeout` (`unit_stop.go:350-382`). At 03:02 it returned "the work is still running". The read finished at 03:18: completed, exit 0, both outputs, AGREE, zero material. Nothing ran the tail of `RetryUnknownRead` (`unit_stop.go:382-389`: `finish`, then the stop note in `unknown-retry.json`). The step stayed "running", `round.Reads` nil, the stop "stopped unavailable-stop-inputs". the-steward-decides U2b1c round 2 ended the same way the evening before. Both were resolved by a correction round that changed nothing.

What the code does:

- The retry keeps the record state "awaiting-judgement". `finish` set it on the first decision (`unit_run.go:1003-1004`), and `RetryUnknownRead` saves the new step without changing it (`unit_stop.go:369-371`).
- `Advance` returns at once for that state (`unit_run.go:314-316`). `work wait` (`metasystem/cmd/metasystem/intent_work.go:2163-2201`), `work build run:ID` (`:799`), `work revise` (`:1853`) and the channel answer (`metasystem/cmd/metasystem/intent_answer.go:201`) all reach `Advance` through `Continue` (`metasystem/internal/launch/unit_named.go:90-134`). None of them looks at the running step.
- A named revision does not go through `Advance`. `work revise G --work W` (`metasystem/cmd/metasystem/intent_selection.go:947`) and the person-authorized run form (`metasystem/cmd/metasystem/intent_work.go:1838`) call `Revise`, whose `reviseLocked` (`metasystem/internal/launch/unit_revise.go:115-295`) takes the run lock, checks correction admission (`:180`, `:279`) and advances directly (`:289-295`). A person can start another round while the previous fresh read is unbooked.
- `work review` reads the run without advancing it (`metasystem/cmd/metasystem/intent_unit_review.go:46`). With `UnknownRetries` at 1 and the stop still "stopped ...", it refuses: "the fresh examination still has unknown inputs" (`intent_unit_review.go:99-110`).
- The driver books a step only while it waits: `waitStep` ends it with the launch's outcome (`metasystem/internal/launch/read_sequence.go:134-169`, `endStep` at `:171-195`). A read that ends after the wait is booked by nobody.
- `finish` already does everything a late read needs: it collects the reads by the `read` prefix, so the renamed `unknown:read` steps are left out (`unit_stop.go:91-129`, prefix at `:96`), decides the stop (`unit_stop.go:131-208`), saves once and publishes the judgement (`unit_run.go:1003-1026`).
- Reading a launch with `Store.Read` (as `collectLaunches` does, `metasystem/internal/launch/unit_accounting.go:16`) never notices a dead supervisor. The death reconciliation is `Manager.Status`: a running launch whose supervisor and child are both proved dead is failed "supervisor-lost" (`metasystem/internal/launch/launch.go:734-743`).
- The supervisor of the read is the one process that is there when it ends (`metasystem/internal/launch/launch.go:368-606`, run by `metasystem launch supervise`, `metasystem/cmd/metasystem/launch_verbs.go:112-125`). It writes the launch record and exits. The launch record does not say which unit run it belongs to, nor which installation started it (`metasystem/internal/launch/record.go:75-108`). The reservation is written under the invoking installation (`intent_work.go:769`); the candidate's working directory can resolve another one (`metasystem/internal/stateroot/stateroot.go:235-247`), where collection would write an "unaccounted" duplicate (`metasystem/internal/dispatch/unit_launch.go:96-104`) and leave the real reservation pending.
- The job reservation of a unit launch is written "pending" at start (`metasystem/internal/dispatch/unit_launch.go:15-86`) and terminal only when a driver collects the launch. Between the two, three readers count it as a running job by its own status alone: `work status` (`intent_process.go:1132-1143`), the job inventory behind `system status` and `system stop` (`families.go:199-201`) and the helm report (`metasystem/cmd/metasystem/intent_helm.go:516-521`). That is the completed r4-s4 shown "pending" at 03:44, and finding 469's record that changes only at its end.

### 1.1 A round interrupted after its work is done (finding 492)

the-steward-acts U3a. Round 1's builder wrote the whole candidate (123 production lines, 449 in all), then was killed by a credential switch (finding 490); the round ended build-failed. Round 2's correction builder inherited the candidate, passed the brief's tests and mutations, then reported `RESULT: BLOCKED` after 20 admission checks found no host test slot. It changed nothing. The engine counted a gap and never ran its own check. The candidate stands unproven, and no engine route reaches the check: another correction with no change is a gap again, and a new work name starts with the candidate already in its starting diff.

What the code does:

- Each round's starting diff is written before its first build: `build-before/worktree.diff`, the worktree against the unit's base (`metasystem/internal/launch/unit_run.go:528-532`). A correction inherits the worktree as it is, so its starting diff holds the inherited candidate.
- After the builds pass, `freezeBuildOutcome` (`metasystem/internal/launch/unit_build_outcome.go:18-80`) writes the round's `worktree.diff` against the base (`:19-24`), freezes the result (`:25-38`) and counts the change with `countBuildLines` (`:40-45`). `countBuildLines` (`:85-101`) diffs the round's `worktree.diff` against its `build-before` diff through `diffSince`, which applies both onto the base (`metasystem/internal/launch/unit_revise.go:421-461`), and calls an empty difference a gap (`unit_build_outcome.go:100`). A gap stops the round "stopped (gap)" before any check (`:60-79`); the proof steps are added only after the freeze (`unit_run.go:583-590`).
- A failed build never freezes: it skips its proof steps (`unit_run.go:547-558`) and counts its change only for the person's question (`countFailedBuild`, `unit_build_outcome.go:107-120`). So round 1's candidate was never checked.
- The builder's result block is parsed by `buildResultLine`, which knows DONE, PARTIAL and FAILED only (`unit_run.go:914`, `parseBuildResult` `:961-992`). `RESULT: BLOCKED` is no result block: the step stays passed with the reason "no-result-block" (`judgeBuildResult`, `unit_run.go:951-957`), and the round reaches `freezeBuildOutcome`. The block is not the defect; the gap count is.
- The declared size of every build is set by `buildSize` (`metasystem/internal/launch/admit.go:169-186`, recorded on the launch at `metasystem/internal/launch/launch.go:259`); the size hold compares it with the counted change (`unit_build_outcome.go:46`).
- A proof step's launch id is saved before its admission (`metasystem/internal/launch/read_sequence.go:59-76`), and a refused start can fail the step with no launch record at all (`:117-121`). A retry appends a new id to the step's `LaunchIDs` (`:62-68`) and clears the step's execution start (`:72`). An execution started only when its launch record has a child: `Supervise` records it when the process starts (`metasystem/internal/launch/launch.go:480-486`).
- The unit's base is the goal branch's commit when the unit started (`metasystem/cmd/metasystem/intent_work.go:1204-1208`). Uncommitted work already in the worktree is not part of it; each round's `build-before` diff carries it, which is why `TestIntentBuildSizeExcludesRecordsAndPreexistingChanges` (`metasystem/cmd/metasystem/intent_build_outcome_test.go:587-614`) counts 2 lines with 40 unrelated lines present.
- A build's declared size is read from the units page when the spec names one (`metasystem/internal/launch/admit.go:169-173`); every build of the run, corrections included, is given the retained plan's units page (`metasystem/internal/launch/unit_run.go:536`).
- The gap rule after a checked round is pinned by `TestIntentBuildUnchangedCorrectionIsGap` (`metasystem/cmd/metasystem/intent_build_outcome_test.go:564-586`).

## 2. Decisions

- D1 The launch store is the truth of a late fresh read. In a run awaiting judgement, a `read:fresh` step of the last round that is starting or running in the record, and whose launch is terminal, is ended with the launch's outcome by the driver's own `endStep` (`read_sequence.go:171-195`). The new `bookEndedRead` does it. It reads the launch through `Manager.Status` (`launch.go:734-743`), never `Store.Read`, so a launch whose supervisor and child are proved dead is failed "supervisor-lost" first and then booked; no dead pair leaves the step running. Two callers: `Advance`, for every resume, after the collection loop and the named check (`unit_run.go:258-270`), so the early return (`:314-316`) and an unnamed revise (`:291-313`) see the booked round; and `reviseLocked`, under its locks right after the named check and before any admission (`unit_revise.go:129-134`, admission at `:180`), so `work revise G --work W` and the person-authorized form decide on the booked round. A launch with no record (a refused start, finding 473) or still running is left as it is.
  Rejected: run `advanceRunning` again for the finished round. It retakes the proof snapshots and judges the build again (`unit_run.go:479-717`).
- D2 One path finishes the round. The tail of `RetryUnknownRead` (`unit_stop.go:382-389`) becomes `finishFreshRead`: `finish(record, round, "green")`, then, if the stop is still "stopped ...", the decision "stop" and the handoff written into the round's `unknown-retry.json`. `RetryUnknownRead` and `bookEndedRead` both call it. A fresh read is booked the same way whoever sees it end. The `unknown:read` steps stay excluded by name (`unit_stop.go:96`). The ended step is set in memory only; it reaches `run.json` in the same save as the stop decision (`saveDecision`, `unit_stop.go:212-215`), so a second call finds the step terminal and does nothing.
  Rejected: a second booking path for late reads. It would drift from the first.
- D3 Nothing is retried, started or stopped here. Booking reads step records and launches; it changes only a `read:fresh` step record. A step whose launch still runs stays running. A terminal step record is never reopened, even when its launch still runs: the moved-tree case marks a running proof step failed and finishes the round without cancelling its launch (`unit_run.go:595-597`, `:1215-1227`, `metasystem/internal/launch/tree_reservation.go:399-408`), so a run awaiting judgement can hold a live proof process. That existing case is deferred (section 3); booking does not widen to it. Retries, listings and the candidate's folder belong to the umbrella a-check-guards-its-own-inputs.
  Rejected: a longer wait cap. It hides the defect until the next long read.
- D4 The launch's supervisor books its own end, best-effort. A unit launch records its run and its installation: `StartSpec.UnitRun` and `StartSpec.UnitInstallation` (`launch.go:53-62`) are set by the unit driver's start (`unit_run.go:768-772`) from the run's id and the runner's `ExaminationRoot`, the caller's installation (`unit_run.go:168-169`, set at `intent_work.go:512` from the same layout that writes the reservation at `:769`), and written as `adapterData.unitRun` and `adapterData.unitInstallation` beside `unitStopInputs` (`launch.go:219-221`). When `Supervise` returns, `runLaunchSupervise` (`launch_verbs.go:117-125`) composes the unit runner the way `work wait` does (`intent_work.go:477-614`) from that installation, never from the launch's working directory, and calls the new exported `BookEndedRead(run)`. Empty parsed input is safe for that composition (`metasystem/cmd/metasystem/intent.go:344-351`). `BookEndedRead` takes the tree lock and the run lock with try-locks (`tree_reservation.go:79-84`, `unit_run.go:1409-1427`) and does nothing when they are busy. Under the locks it runs `collectLaunches` for every round, then `bookEndedRead`. The booking is best-effort: a holder may have read the step running just before the end and return without booking (`unit_run.go:314-316`). The fallback is the next verb that resumes, revises or reviews (D1). `work review` calls `BookEndedRead` before it reads the run (`intent_unit_review.go:46`).
  Rejected: a new daemon that polls runs; the supervisor already exists and is there at the end. Rejected for this page: a steward tick duty that scans every run on every tick. The tick costs about a minute already (finding 470), and the supervisor is the event. The verbs are the fallback for a busy lock or a supervisor that died. Rejected: `work status run:ID` books too. It uses a bare runner with no repository composition (`intent_process.go:1279`); booking with it would decide the stop without the review policy and the inherited findings.
- D5 A waiter follows a run another observer booked. `RetryUnknownRead`'s wait releases the run and tree locks and returns UNIT_WAIT_RETRY when `run.json` changed meanwhile (`tree_reservation.go:433-483`). With D4 the supervisor can book the read while `work review` still waits. On UNIT_WAIT_RETRY from `RetryUnknownRead`, `reviewUnit` reads the run once more and goes on to the stop check and the review (`intent_unit_review.go:101-106`). One reread, no loop.
  Rejected: keep the run lock during the wait. `work stop` and the cancel paths then wait behind every read.
- D6 The job projection reads the store. A unit-launch reservation (`unitRun` set and `operationId` "unit-launch:" plus its id, the test `metasystem/internal/dispatch/stop.go:542` already uses) that is not terminal, while its launch record is terminal, is no running job. One helper in `metasystem/internal/dispatch` decides it, reading the launch's state as `engineHost.UnitLaunchStatus` does (`metasystem/cmd/metasystem/delegate_host.go:26-33`). `listJobs` (`intent_process.go:1139-1141`), the job inventory (`families.go:199-201`, the reader given through `LocalConfig`, `families.go:27-38`, from `metasystem/cmd/metasystem/process_verbs.go:134-137`) and the helm count (`intent_helm.go:518`) skip it. The same inventory feeds stopping (`metasystem/internal/stoptransition/transition.go:590`): a reservation whose launch ended has nothing to stop, and a reservation whose launch runs is unchanged, so `system stop` still cancels it.
  Rejected: rewrite the reservation from the projection. A status read would then write.

- D7 A correction after rounds that never ran the check counts against round 1's starting point. The test, read literally: an earlier round "reached the check" when one of its `proof:` steps has, among all its `LaunchIDs` (earlier retry attempts included), a launch whose record exists and has a child, so its execution started (`read_sequence.go:59-76`, `:117-121`, `launch.go:480-486`). An id with no record, or a record with no child (a start refused or failed before execution), is no check. When no earlier round reached the check, `countBuildLines` measures the round's `worktree.diff` against round 1's retained `build-before` diff, instead of the round's own `build-before` (`unit_build_outcome.go:85-101`). Inherited work from round 1 on is counted, and uncommitted work that was already there before round 1 stays excluded, as today. An inherited complete candidate is then a result, not a gap, and the round goes to the engine's own check. When an earlier round reached the check, the rule is today's: a correction with no change is a gap. The declared size is unchanged: every build reads the retained units page (`admit.go:169-173`, `unit_run.go:536`), whatever round 1's failed-build counts say. A builder that ends `RESULT: BLOCKED` exits as passed with "no-result-block" (`unit_run.go:951-957`), so D7 sends its candidate to the check: intact, changed or partial alike, under the gap and size rules. No completeness gate is added; a red check is the right outcome for a broken candidate. The check is the proof; the builder's blocked verification is not a gap. `BLOCKED` is named in `parseBuildResult`'s comment and pinned by T9, so it is never read as FAILED.
  Rejected: a new verb to run the check without a builder. The engine already runs it after a counted build. Rejected: loosening the gap rule for every round. A real no-op correction after a checked round must still stop. Rejected: reading `BLOCKED` as FAILED. The round would end build-failed, and the candidate would again never reach the check. Rejected: measuring against the unit's base. It counts work that was there before the unit (Astra's fold 2). Rejected: a launch id as the evidence of a check. It is saved before admission (Astra's fold 1).

- Finding 469's "pending, no startedAt" while the launch runs. D4 makes the reservation terminal at the end; the running display stays the reservation's.

Deferred defects, named and not built here:

- Finding 469's health reading. The claimed-goal-delivery role requires `capDeadline` on every non-terminal job record (`metasystem/internal/steward/delivery.go:231-245`), and `ReserveUnitLaunch` writes none (`metasystem/internal/dispatch/unit_launch.go:78-80`). A running unit launch therefore counts as a delivery failure. D6 changes none of this.
- The stale round cause. `finish` keeps a non-empty cause (`unit_run.go:1005-1007`), and a clean fresh read does not clear the "environment" the first decision set (`unit_stop.go:194-200`). Review readiness reads the outcome, so the clean round is reviewed. But the hand-in counts the round as machinery, not as a counted round (`metasystem/cmd/metasystem/landing_plain.go:466-475`). The retry path does this today; this page keeps it.
- A live proof process in a run awaiting judgement after the moved-tree case (D3).

## 4. Questions answered

1. Which observers book? Every verb that resumes or revises a run (D1), `work review` and the supervisor (D4). `work status` and the steward tick do not (D4's rejected alternatives). Wido's request named both; I answered in his name. He overrules.
2. Does the supervisor become a driver? No. A launch that ends in a running round is only accounted (`collectLaunches`); the next `work wait` starts the next step.
3. Is the race with a live review real? Yes. The supervisor's end and the review's next poll both follow the store write, and the supervisor's try-lock usually wins because the waiter released its locks. D5 makes the review follow the booked run.
4. What if the supervisor is killed before its end? The next verb that resumes, revises or reviews reads the launch through `Manager.Status`, which fails it "supervisor-lost" once supervisor and child are proved dead, and books the round (D1).

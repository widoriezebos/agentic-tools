## 2. The item: five rosters, four kinds of work, one folder

A roster is one file, `rosters/<id>.conf`, beside `metasystem.conf` (the directory every reader already resolves from: `RosterParams.ConfPath`, `ResolveSettings(confPath)`, `UIPartner(confPath)`). Its id says what it serves, and there are five: `tier-1`, `tier-2`, `tier-3` (work on a goal of that risk tier), `landing` (the landing agent) and `partner` (the Project Partner). Its lines are `kind=runtime:model:effort` in the conf grammar (`internal/config/conf.go:20`: comments, blanks, last key wins), the pair form `model.tier.N` already uses with the effort as a third field; the effort may be left off, and then today's effort key answers. The `partner` line is `runtime:model` only: the Partner's session takes a model option and nothing for effort (`internal/ui/partner/host.go:537-556`), so a third field there is refused rather than shown. The `landing` roster is the one file that is not beside the seat's conf: it is beside the registered landing installation's (§3). A tier roster's kinds are `design`, `design-critique`, `build` and `code-critique`; the landing roster's one kind is `landing`; the partner roster's is `partner`. Example, this seat's roster as `rosters/tier-3.conf`:

    # tier-3: the most careful work (R-133-ui).
    design=claude:claude-fable-5-1:xhigh
    design-critique=codex:gpt-6-astra:xhigh
    build=claude:claude-opus-5-5:xhigh
    code-critique=codex:gpt-6-sol:xhigh

The folder is seat-local and git-ignored, as `metasystem.conf.local` is (the repository's `.gitignore:1`): each seat names its own agents today (`metasystem.conf.local:9`), and a page edit must never dirty the tree. A roster that does not exist, or a kind it does not name, is answered by today's keys and compiled defaults, so a seat with no `rosters/` folder behaves exactly as it does now; the compiled defaults are the roster nobody wrote. One reader, `config.ReadRoster(confPath, id)` and `config.RosterPair(confPath, id, kind)` in `internal/config/roster.go` (no new package, no new floor), answers the runtime, the model and the effort (empty when the line names none), or "not named", with the source (`rosters/tier-3.conf`); `config.SetRosterEntry` writes one line with `SetConfKeys` semantics, creating the folder and file on first use. The engine's table names kinds and ids only, never a runtime (R-140-m1e): the runtimes a roster may name are `metasystem.runtimes` (`roster.go:167-182`).

## 3. How work finds its roster

The landing agent uses `landing`; the Partner uses `partner`.
- Kinds map onto both readers: `design` is the implementer in mode design and the design lane; `design-critique` the design critic and the critique lane; `build` the implementer in any other mode and the build lane; `code-critique` the code critic and the read lane.

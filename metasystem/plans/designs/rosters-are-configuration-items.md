## 2. The item: five rosters, four kinds of work, one folder

A roster is one file, `rosters/<id>.conf`, beside `metasystem.conf` (the directory every reader already resolves from: `RosterParams.ConfPath`, `ResolveSettings(confPath)`, `UIPartner(confPath)`). Its id says what it serves, and there are five: `tier-1`, `tier-2`, `tier-3` (work on a goal of that risk tier), `landing` (the landing agent) and `partner` (the Project Partner). Its lines are `kind=runtime:model:effort` in the conf grammar (`internal/config/conf.go:20`: comments, blanks, last key wins), the pair form `model.tier.N` already uses with the effort as a third field; the effort may be left off, and then today's effort key answers. A tier roster's kinds are `design`, `design-critique`, `build` and `code-critique`; the landing roster's one kind is `landing`; the partner roster's is `partner`. Example, this seat's roster as `rosters/tier-3.conf`:

    # tier-3: the most careful work (R-133-ui).
    design=claude:claude-fable-5-1:xhigh
    design-critique=codex:gpt-6-astra:xhigh
    build=claude:claude-opus-5-5:xhigh
    code-critique=codex:gpt-6-sol:xhigh

The folder is seat-local and git-ignored, as `metasystem.conf.local` is (the repository's `.gitignore:1`): each seat names its own agents today (`metasystem.conf.local:9`), and a page edit must never dirty the tree. A roster that does not exist, or a kind it does not name, is answered by today's keys and compiled defaults, so a seat with no `rosters/` folder behaves exactly as it does now; the compiled defaults are the roster nobody wrote. One reader, `config.ReadRoster(confPath, id)` and `config.RosterPair(confPath, id, kind)` in `internal/config/roster.go` (no new package, no new floor), answers the runtime, the model and the effort (empty when the line names none), or "not named", with the source (`rosters/tier-3.conf`); `config.SetRosterEntry` writes one line with `SetConfKeys` semantics, creating the folder and file on first use. The engine's table names kinds and ids only, never a runtime (R-140-m1e): the runtimes a roster may name are `metasystem.runtimes` (`roster.go:167-182`).

## 3. How work finds its roster

- Work on a goal uses `tier-<goal tier>`; work with no goal, or whose tier the reader cannot learn, uses `tier-3`, the engine's own precedent for an unknown tier (`admission.go:407-409`) and the most careful roster, so no path ever lowers quality by accident (R-34-m2). The landing agent uses `landing`; the Partner uses `partner`.
- Kinds map onto both readers: `design` is the implementer in mode design and the design lane; `design-critique` the design critic and the critique lane; `build` the implementer in any other mode and the build lane; `code-critique` the code critic and the read lane. Verifier and investigator run on main (`defaults.go:312-315`), the steward continuation and the seat lane are not kinds: they keep their keys.
- Dispatcher: `RosterParams` gains `Tier uint8` (0 = unknown). `ResolveRoster` asks `RosterPair` first and, when the kind is named, takes that pair as `rosterRuntime`/`rosterModel` before `:148`; the `main` refusal, the runtimes check, the alias step and the escalation ranking run on it unchanged, and `RosterPair` (`:253`) names it so an override still escalates against it. The requested model under a `--runtime` override keeps reading `role.<role>.model.<runtime>` (`:210-218`): a roster names one runtime. `dispatch_phase.go` hoists the `Binding` read (`:333`) above the roster (`:245`) and passes `binding.Tier`; its checks stay where they are. The four goal-less callers pass nothing and get `tier-3`, so no off-limits file changes.
- Launch: `ResolveSettings` (`settings.go:139`) also reads the five rosters into `Settings`, and `launchRuntime`/`launchValues` (`:315`, `:334`) take a tier; `Manager` gains one port, `Tier func(goal string) uint8`, set beside its settings (`intent_work.go:100`) from the ledger the work verbs already read, nil or unreadable answering 0. `Start` (`launch.go:105-106`, `:124`, `:130`) and the unit runner's two choices (`unit_run.go:294`, `:316`) read through them, or the roster never reaches a build. `launchValues` answers the entry's effort when the line names one and today's effort key when it does not (`settings.go:337-349`); it reaches the adapters as the lane's effort does now (`launch.go:106`, `:116-117`; `claude.go:44-45`, `codex.go:78-81`, `devin.go:38-39`). For `landing`, the claude-only refusal and the unbound-model refusal stand in their words (`launch.go:134-138`; `landing_gate.go:21`, `:30`); `internal/launch/landing.go` and `cmd/metasystem/landing_agent.go` are not on this path and stay untouched.

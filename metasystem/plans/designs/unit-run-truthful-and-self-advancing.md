# Design: a unit run judges its build truthfully and advances on its own events

- Status: accepted

## Problem

A `work build` run (internal/launch/unit_run.go) is a chain build → proof → read → judgement. On 2026-10-14 it failed the person four times in one unit, each time on the machinery and not on the code:

1. The build launch ended at 10:09 (exit 0) and nothing advanced the run for 25 minutes. Under the helm, `internal/steward/tick.go` returns `helmTick` ("nothing decided") and no tick touches unit runs; the only advance is a typed verb (`work wait`, `work build run:ID`, `work review`). A person who started a run then has to poll it.
2. The build step was marked passed on the launch's exit code although the builder's last message started with `RESULT: PARTIAL` and listed three red tests. `advanceStep` (unit_run.go, build loop at ~500) never reads the result block; `measurement.verdict` stays empty.
3. The proof step ran the frozen cheap check (`metasystem test impact`, 18 groups of cmd/metasystem) and was cut at `proof.deadline=15` ("cheap timed out after 15m0s") while four groups had already reported red. The builder's result block had reported the same cut. (A follow-up round re-admits the declaration from HEAD, so a longer committed deadline would reach the next round; nothing told the person that, and the proof was spent first.)
4. After the proof step was recorded failed, `work wait` still answered "round 1 is still running step proof:unit-check" and the round's outcome stayed empty; only the person's `work stop run:ID` closed it. Astra round 1 traced the likely cause: the attribution of the red (`attributeProof`, a comparison with the base that waits) was still pending, and the status line did not say so.

## Decisions

D1. A run advances on its own events, helm or not. The launch supervisor (the detached process that owns a launch, `internal/launch` record `supervisor`) ends a launch by writing its record; at that moment it continues the owning run (`UnitRunner.Continue{Resume: run}`) in the same process, exactly as `work wait` would. The steward's tick stays out of it: under the helm "the machinery decides nothing" still holds, because continuing a run executes the person's `work build` decision and decides nothing new. If the continuation fails, the launch record carries `advance: <error>` and `work status` shows the run as "needs work wait", never as silently running.

D2. The build step reads the builder's result block, after the launch itself completed. A launch that the launcher recorded failed or cancelled (exit non-zero, or exit zero with a failed collection of a declared output: `internal/launch/launch.go:566`) stays failed whatever its text says; result parsing only downgrades a completed launch, never promotes one (Astra round 2, UTR-1). For a completed launch, `advanceStep` parses the last message for the first `RESULT:` line: `DONE` → passed; `PARTIAL` or `FAILED` → the step fails with reason `build-partial` / `build-failed`, the round's outcome is that reason, the proof and read steps are skipped as on `build-failed` today, the run awaits judgement, and the builder's `OPEN:` text is retained as `round-N/open.md` so `work revise run:ID` can carry it into the next brief. No `RESULT:` line → passed on exit code, with reason `no-result-block` recorded (today's behaviour, now visible). `measurement.verdict` carries the parsed word.

D3. The deadline is checked before it is spent. When the admitted declaration's deadline is shorter than the last recorded duration of the same cheap check for this goal (the run keeps each round's check result under `round-N/check-*/result.json` with `minutes`; the proof log carries per-group milliseconds), the proof step is not launched: the run stops with the plain reason "its check needs longer than the declared 15 minutes (last run 19 min)" and the one remedy of D6. The duration is taken only from executions of the goal's own check (`check-*` results of candidate proofs), never from base comparisons written into the same round (`intent_unit_check.go:97`), and a timed-out execution counts as a lower bound ("at least 15 min"), so the same inadequate deadline is never re-admitted from its own timeout (Astra round 2, UTR-3). The remedy verb `work check G --work NAME --minutes N` (D6) does two things in one admitted transition: it declares the longer deadline on the goal branch (the person's declaration admission) and continues the awaiting run by re-admitting its plan from HEAD and launching the proof step with the new deadline; committing the declaration alone changes nothing for a run awaiting judgement (`unit_run.go:313`, `:684`), and the verb says so if used without a waiting run (Astra round 2, UTR-4). When the deadline is re-admitted inside a round, the round's retained proof snapshots are reconciled with the changed HEAD the way the existing retry path archives them (`savedRepositorySnapshot` rejects a changed HEAD, `unit_run.go:1101`): the superseded proof observations are archived under the round and the new proof starts from the admitted declaration (Astra round 3, UTR-5). Corrected after Astra round 1 (N1): a follow-up round already re-admits the declaration from the worktree HEAD (`unit_run.go:684–693` reuses a plan only inside its round; a new round calls `FreezeCheck`), so a longer deadline committed on the goal branch takes effect in the next round today; the design adds no cross-round change there.

D4. `Continue` finishes what is recorded, after its attribution. A failed proof step is not the round's end by itself: `advanceStep` is followed by `attributeProof` (`unit_run.go:581`), which compares the red with the base and may wait on that comparison (`unit_attribution.go:182–189`). `Continue` on a run whose step is recorded failed first resumes any pending attribution or retry work and runs it to completion (an expired comparison wait is re-run, not skipped), and only then finishes the round with the step's reason (`proof-red`, `build-partial`, …) and the attribution's classification (goal red, base red, flake). While attribution runs, status says so in plain words ("comparing the red with the base, 3 min") instead of "still running step proof:unit-check". Folded from Astra round 1 (F1).

D5. Configuration on main: `proof.deadline` 15 → 30 in `metasystem/metasystem.conf`, landed as a unit of this goal, because `metasystem test impact` over a cmd/metasystem-wide impact set takes 15–20 minutes on this host; D3 keeps a short deadline from costing a proof even when it is set too low again.

D6. The person meets intent, never the run's structure (Wido, 2026-10-14 11:06: "verbs along the lines of intent, not internal state/structure/process"). Names below are proposals; Wido names verbs.
- `work status` for a goal's work says, in one plain sentence per work item, what it waits for and the one thing to type: "F-1-fix: the builder reported a partial result (three red tests); correct it: metasystem work revise G --work F-1-fix --brief FILE", "F-1-fix: its check needs longer than the declared 15 minutes (last run 19 min); give it time: metasystem work check G --work F-1-fix --minutes 30", "F-1-fix: proving (12 of 18 groups done, 9 min)". No round numbers, step names, launch ids or record states (`awaiting-judgement`, `proof-red`) in the summary; `--verbose` keeps them for diagnosis.
- Remedies are intent verbs on the goal and its work name, and every remedy line is executable as printed: it passes the stop the run itself recorded. A failed build creates a stopped `unit-build` decision (`unit_run.go:878`, `unit_step_failure.go:84`) that today's revision admission passes only with the person's `--by NAME --reason TEXT`; the printed remedy therefore carries them (`work revise G --work NAME --brief FILE --by NAME --reason "…"`) or the admission is changed so the builder's partial result needs no override; a remedy that cannot run is a defect (Astra round 2, UTR-2). `work revise G --work NAME --brief FILE` (exists) corrects the work; a new `work check G --work NAME --minutes N` (proposal) declares the longer deadline on the goal branch as the person's act, the same declaration admission as a committed `proof.deadline` change; `run:ID` forms stay as the verbose, scriptable alternative and never appear in a remedy line.
- The builder's `OPEN:` text is shown to the person as the work's open question ("the caller must decide: file scope, deadline") at the moment the run stops on a partial result, not buried in a launch directory.
- One message shape for every stop of a run: line 1 the situational reason in plain words, line 2 the one remedy; the same words in `work status`, in the channel report and in the verb's own output (one truth, finding 305).

- U1 (D2 + D4): result-block judgement only on a completed launch; a green flake retry keeps continuing normally (Astra round 3); (a failed or cancelled launch is never promoted; tests for exit-zero with failed output collection, with and without `RESULT: DONE`); `Continue` resumes pending attribution before finishing a recorded failure; tests in `internal/launch` for the three verdict words, the missing block, a Continue over a recorded failed proof with an expired comparison wait (attribution completes before judgement), and the plain-words attribution status. ≤180 lines.
- U2 (D1): the launch supervisor continues its run at launch end; test that a run with an ended build launch has its proof launched without any verb; the helm test keeps "nothing decided" (no new launches of other goals). ≤150 lines.
- U3 (D3 + D5 + D6 deadline remedy): deadline check before the proof against the last goal-check execution (timeouts as lower bounds, base comparisons excluded), `work check G --work NAME --minutes N` declaring and resuming in one transition with the round's proof snapshots archived (UTR-5); `proof.deadline=30`. ≤200 lines.
- U4 (D6 status and stop messages): plain-words `work status` lines and one stop-message shape across status, channel and verb output; every printed remedy is executed in a test and passes the stop it answers; a test that no summary line carries a run id, step name or record state. ≤150 lines.

## What it delivers

A seat's own verified engine re-arm preserves the authorization needed to continue its work. A genuinely active dependent job prevents an idle decision even after the goal's elapsed allowance passes. A person can revive one existing seat without changing policy, and a provider recovery that leaves a seat down produces one request for that exact act. The host view and board expose the usage actually measured, its missing coverage, without inferring account limits.

**Step 1 is R1:** re-arm a seat with an authorized continuation and retain that continuation's authority, without giving an unrelated enrollment or agent the same permission. Its public scenario also protects an active dependent job. This is useful before the new recovery request exists. R2 supplies the remedy; R3 consumes its record; R4 supplies usage observations. Neither observations nor requests select new work.

## Decisions with code sites read

### R1 — Preserve continuing authority and recognize dependent work

At `internal/steward/stage.go:129` and `:184`, bind new continuation intents to the existing human enrollment witness as well as their original installation generation; at `internal/steward/dispatch_authorization.go:45`, permit a generation change only when the same repository's verified machine re-arm preserved that witness and the staged role, brief, permissions and return digests still match. `internal/steward/runner.go:738` already carries the witness through `machine-rebuild`; serialize its identity publication at `:1129` with existing revival arbitration, retaining the lock order arm lock then arbitration and allowing no publication between authorization validation and launch. A new human enrollment changes the witness; a worker enrollment still changes the independent enrollment fence checked by `internal/steward/revive.go:135`; neither is silently accepted. Old intents lacking the witness retain exact-generation validation. Reuse P5's stable-seat restart history unchanged, including consumed-but-unstamped recovery: re-arm is never a new allowance. In the same continuation admission path, make `internal/steward/seat_idle.go:57` count Starting reservations and live dependent launches regardless of elapsed goal budget, joining the held goal's unit/step or recorded job ancestry to actual process identity; include dependent jobs beyond the existing `code-critic-*` inventory. `SeatBusy`, `SeatAtUnitBoundary` and the tick/revival decision consume that same observation before declaring idle; unreadable relevant custody is unknown and prevents an automatic idle action, and a terminal or reused-pid job is not active. Waiting on a live job is a busy reason, not a fabricated work-progress mark that resets P5. No new killer is added: today's idle verdict at `internal/steward/verdict.go:129` notifies, while seat reap at `seat_start.go:260` closes already-ended launches. Estimate: 240 production lines (145 authority/arbitration, 75 dependency readers, 20 diagnostics).

### R2 — Give a person one recorded act to revive an existing seat

Add `metasystem machine revive MACHINE [--after LAUNCH]` to the existing command owner beside `cmd/metasystem/intent_process.go:294`, resolving MACHINE through the existing registered machine inventory in `cmd/metasystem/intent_machine.go:256`, and pass independently validated person authority into `internal/steward/seat_start.go:496`/`:536`; `--after` names the failed seat launch whose work is being continued, not a caller-selected provider or goal. This is needed because today's `machine start` clones a machine and `session start` prepares the calling agent; neither is an existing-seat recovery act. Reuse the seat's enrolled engine/runner repair and existing selection, launch record and arbitration; add only invocation-scoped person override of the automatic outage, restart, helm and seat-policy holds, explaining that one session will start while standing policy and P5 history remain unchanged. Do not inherit that override into later ticks or successors, reopen a process-creation stop fence, claim another goal or alter its approval. An intentional system stop is reported with the existing person's `system start --repo CHECKOUT` repair; it is not a provider-recovery target. Extend `SeatRecord` (`internal/steward/seat_start.go:79`–`:94`, which currently has no recovery field) with `RecoveryOf`, naming the failed launch and its provider episode. R2 makes the shared `StartSeat` owner write this link before launch for both the person command and an automatic start whose seat's last launch ended in that episode; automatic admission predicates and P5 history stay unchanged. Derive the link from the retained failed launch and episode under the same arbitration, then join the launch manager's actual Starting/Running outcome before reporting success; a reservation alone never proves revival. Re-entry reconciles the same launch: an already-live matching successor succeeds without another launch, a live unrelated session is left alone, and an unknown launch result cannot cause a duplicate. Missing identity, enrollment or work evidence is reported precisely without claiming success or requiring an advisory setting change; an agent cannot use this person route, and automatic starts keep their current predicate. R2 owns P5's person remedy `machine revive SEAT`; P5 displays it as unavailable until R2 lands. The recovery request supplies `--after LAUNCH`; when omitted, the command resolves and binds the seat's current failed launch under arbitration. Estimate: 250 lines (65 parser/authority, 120 existing start/reconciliation changes, 15 automatic recovery-link production, 50 record/help/result).

### R3 — Ask once for the exact seat that missed recovery

Add a recovery-request reconciliation to the registered host steward's existing loop at `internal/steward/runner.go:325`, after automatic seat/revival results (`:382`, `:422`) and before channel delivery (`:428`), reading the registered seats and P2/P3's provider episode plus each dependent `SeatRecord`/actual launch, and use `internal/channel/question.go:243` (`AskOrFind`) and `:580` (`Close`) as the only question store and delivery owner. The old `runner.go:491` citation is inside `runnerWait`, not the steward pass. Declare `provider.recovery-alert-after=6m` through the existing configuration/default/help owner, expose the effective interval and due time in `machine list`, and bind the chosen interval when an episode is first observed: six minutes is a draft grace period for seat recovery after provider success, not a measured provider promise. Start the due clock only at the first genuine provider success (probe or launch) after the episode's evidenced reset, and set due time to that success timestamp plus the bound interval. When reset is unknown, use the episode's first genuine provider success; never invent a reset. Failed post-reset probes do not start the clock: while the provider mark stands, issue no recovery ask and leave stale-mark reporting to P3. A timer, person clear or stale expiry is never success, and cannot start the clock; expose due time as pending success until that evidence exists. After that due time, a seat whose last provider-dependent launch ended for this episode and still has approved held work but no live/starting successor gets one subject `(host registration, seat, failed launch, provider episode)` request containing R2's fully populated command. Intentional stops, a person-held seat, completed/released work and an active dependent job are reported as such instead of being requested to revive; they do not change provider evidence. Extend the channel's existing command-request recognition (`question.go:479`) narrowly for this typed recovery subject, including terminal answers, channel replies and question display, so text cannot close it; reconciliation closes it only on R2's matching successful `RecoveryOf` plus observed launch identity, including a matching automatic recovery recorded by the same start owner. Persist subject/due/closure reference in that question's facts, retain closed questions for deduplication, and recheck under the seat's existing arbitration before publication/closure; changed host registration makes the old request stale and non-executable, never a request for its replacement. Delivery retries reuse the question, failed persistence remains visible, and the exact launch may be reconciled after a crash without starting it again. P3's once-per-mark stale alert stays separate; this pass launches no probes or seats and grants no extra attempts. Estimate: 250 lines (120 reconciliation, 60 command-request/closure adapters, 35 declaration, 35 visible output).

### R4 — Display measured usage with honest account coverage

Extend P1's host snapshot (a source-design dependency, not yet on this main revision) with a read-time usage projection over the existing global launch store (`internal/launch/record.go:129`, `:217`), reusing `Measurement` at `:42` and adapter `TranscriptUsage` at `internal/launch/claude.go:120` for completed, failed, cancelled and active sessions. Active or crossing-window sessions contribute every evidenced in-window call, regardless of session start/end; missing or invalid timestamps, unavailable transcripts, conflicting attribution or unavailable session identity produce explicit incomplete/unknown coverage, never prorated session totals or fabricated zeroes. Estimate: 250 lines (75 measurement/timestamp-window reuse, 95 grouping/coverage, 80 terminal/board/Fleet rendering).

## Four recurring defect classes

| Class | Required evidence in this design |
| --- | --- |
| The remedy fails or removes policy | Follow the exact recovery command under the hold, prove its actual launch, and show policy/restart history unchanged; system-stopped seats are not given the wrong remedy. |
| An agent gains a person's power | Agent copies the exact command and supplies no lineage: still no person override. A different enrollment cannot reuse the continuation's witness. |
| Old state hides current state | Re-arm retains history; active dependency uses custody, not an old status word; recovery is bound to an episode/launch; failed reset probes never look recovered, and partial usage never looks complete. |
| A test seam hides production behavior | Public parsers reach actual authority, persistence, launch and question closure; both presentation routes consume real records. Only OS/time/provider/transport boundaries are controlled. |

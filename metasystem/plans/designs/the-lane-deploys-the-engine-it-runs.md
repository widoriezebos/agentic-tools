## Problem

The lane's engine is three things that nobody compares: the binary on disk (`bin/metasystem`, whose build stamp `landing status`, `landing health` and `DeployEngine` read: `internal/landing/plain/status.go:322`, `health.go:401-412`, `deploy.go:39-49, 85-98`), the steward runner's pin (`artifacts/agents/steward/identity.json`: generation and digest, `internal/steward/install.go:12-14`) and the supervisor's generation (`artifacts/agents/supervision/state.json` with its fingerprint over the binary, `internal/supervise/arming.go:236-238`, `internal/census/fingerprint.go`). Consequences, all observed:

1. `DeployEngine` decides "nothing to deploy" when the disk binary's stamp equals origin/main, whatever runs (`deploy.go:85-98`); the lane's own rebuild path updates that binary, so a hand deploy after a landing never restarts the supervisor.
2. The rebuild path (`internal/steward/runner.go:773`, mintedBy "machine-rebuild", via `rearm_resolver.go`) re-arms the steward runner with the new pin and leaves the supervisor owner and components on the old one. Two paths produce the split: the recover-only supervisor arming returns "not-needed" without a generation check (`internal/supervise/arming.go:1213-1221`), and the detached test-run rebuild replaces enrollment and the runner BEFORE identifying the session (`internal/up/up.go:806`); when identification fails (`up.go:852`) it never reaches the supervisor arming (`up.go:925`), and the rebuild caller accepts that partial result because enrollment advanced (`rearm.go`). `RepairEnrolledRunner` reports any live runner CURRENT without comparing the pin it executes (`internal/steward/runner.go:961-964`).
3. A deploy or a seat restart during a proof arms what it can (the "arming half", `cmd/metasystem/intent_landing_deploy.go:35-44`) and nothing completes the swap when the proof ends; `landing status` shows the stamp of the disk binary and says "stale false" while two engines run.
4. The rebuild runs from a records-only move (c0487ef65 differs from 8a079027a by one design page), inside the lane's own check.

## Decisions

D1. **The engine the lane runs is what its live processes execute, and that is what is compared.** The running engine is read from each live owner, component and runner through its owning package: the engine digest of the identity-checked pinned executable the process executes (the `engine-pins/generation-N-<digest>` path verified against the pin's bytes, `internal/steward/identity.go:305-409`), never from enrollment records or the supervision configuration fingerprint (`identity.json` describes enrollment, `internal/steward/install.go:12-14`; the fingerprint hashes the binary with configuration, runtime signatures and repository scope, `internal/census/fingerprint.go:227`; the supervisor's generation counter advances on component relaunches, `internal/supervise/owner.go:412`; all three stay separate and are reported as what they are). Execution evidence that cannot be read (a dead or uninspectable process) is reported UNKNOWN and never yields "nothing to deploy". The lane runs one generation when every live process executes the same digest. `landing deploy` compares that running digest with the digest of the engine built from origin/main: equal on every live process → "nothing to deploy: the lane runs main's engine (generation N, main <sha>)"; otherwise it builds (when the disk binary is not already that engine) and restarts the supervisor and the runner together, whatever the disk stamp or the checkout say. `landing status` and `landing health` show the running digests with their generation and main commit; health evaluates each running engine against main with the COMPLETE engine-input comparison deploy uses (today `health.go:405` compares only landing code, the gate runner and the landing command files, excluding `internal/steward`, `internal/supervise` and `internal/up`), so `stale-engine` fires on the running engine, never on the disk binary, and fires when main changes only the supervision machinery.

D2. **A re-arm replaces the whole generation or reports that it could not.** Every arm of the lane (deploy, the arming half, `system restart`, the detached test-run rebuild) arms the steward runner AND reconciles the supervisor with a generation check (`EnsureArmed` compares and replaces, `arming.go:1228-1244`; never recover-only for a changed engine); the detached rebuild path reconciles supervision after an authorised enrollment change WITHOUT requiring an agent-session identity, preserves the existing creation fences, and propagates an incomplete reconciliation as its result instead of treating enrollment advancement alone as success. Both `EnsureRunner` (the ordinary `up` path, `internal/up/up.go:646`, which today returns verified for any healthy live runner, `runner.go:835`) and `RepairEnrolledRunner` check the live runner's executable digest before accepting it; `RepairEnrolledRunner` keeps ENROLLMENT_CHANGED for its existing meaning (enrollment changed while repair held its lock, `runner.go:945`); a live runner that executes an obsolete pin under stable enrollment reaches the shared guarded stop-and-launch replacement and the repair returns RESTORED only after the replacement started; a repeated arm or repair then returns verified/CURRENT unchanged. With an open creation fence and working components, the detached reconciliation returns CONFIRMED success without an agent-session identity and the rebuild continues (sessionlessness is the normal detached case; today `up` fails at `up.go:852` and the caller maps every non-confirmed envelope to an error, `internal/testrun/rearm.go:443`); a genuine reconciliation failure propagates as an incomplete result despite advanced enrollment. After every arm the lane verifies one generation and records the result as a `generation` event in the landing events (owner, components and runner digests); two generations are a health row ("the lane runs two engines: owner generation 147, runner generation 148; run: metasystem landing deploy"), never silent.

D3. **A swap started during a proof is finished by the lane.** When an arm happens while a proof runs (deploy `--now`, the rebuild path, a seat restart), the lane records a PENDING SWAP distinct from the existing proof-cancellation request (`RestartAttempt`, whose consumer records a cancellation, ends the proof and may start another trunk proof, `deploy.go:211`, called by the keeper before moved-main recovery, `cmd/metasystem/landing_agent.go:341`); the keeper completes the pending swap when the proof ends and BEFORE every automatic proof-start path (moved-main recovery, the cadence, the observation's request): it stops the old owner and components, arms the new generation and verifies D2. `landing status` says so meanwhile: "engine: generation 147 (main 8a079027a); generation 148 (main c0487ef65) waits for the proof to end".

D4. **A records-only move rebuilds nothing.** The rebuild path rebuilds and re-arms only when the code tree that builds the engine changed (the code-moved predicate records-scope U1 uses, `trunk_recovery.go` `codeMoved` through the pathclass classifier); a records-only move leaves the engine, its generation and its stamp alone. Because a build embeds main's commit stamp in the binary (`cmd/devgate/build.go:98`), source-engine equivalence with main (the code tree the running engine was built from equals main's code tree) is compared SEPARATELY from the agreement among the running processes' digests (D1): a records-only advance keeps the existing binary and stamp and is "nothing to deploy"; a code advance is not. U2 reuses the existing engine-input projection comparison from the running build's source to main (`internal/testrun/rearm.go:605`, `rearm_resolver.go:717`); `codeMoved` (`trunk_recovery.go:69`, "anything other than records or ledgers") remains the proof-selection predicate only; the records-only rebuild observed at 07:03 is traced before rebuild eligibility changes.

## Units

- U1 (D1, D2): the running-engine reader (per live process, through the pinned executable's verified digest; unknown when unreadable); the comparison in `DeployEngine` against the engine built from main; the supervisor reconciliation with a generation check on every lane arm, the detached test-run rebuild path included (no agent-session identity required, fences preserved, incomplete propagated); the stale-runner replacement in `RepairEnrolledRunner` (RESTORED after the replacement starts; ENROLLMENT_CHANGED kept for the race); the post-arm verification with its `generation` event and the two-engines health row; `landing status`/`health` reading the running engine. Tests through the production deploy, restart, `up` and rebuild wiring on fixture installations with pinned fake engines, production record formats: enrollment current while a live runner executes an older pin → deploy restarts and verifies one generation; dead or uninspectable processes → unknown, never "nothing to deploy"; two generations planted → the health row fires with both numbers and `deploy` resolves it; a live runner on an obsolete pin under stable enrollment, through BOTH the ordinary `up` arm and recovery → the old process stops, the replacement executes the enrolled pin, a repeated arm/repair returns verified/CURRENT unchanged (the separate enrollment-race fixture retained); the detached rebuild driven through production `up` composition without an agent-session identity, fence open, components working → confirmed success and the rebuild continues; a separate fixture injecting reconciliation failure → an incomplete result despite advanced enrollment; all processes on the same old engine while main changes only `internal/supervise` → `stale-engine` fires (retaining health's restricted path list fails it); mutations: compare the disk stamp instead of the running digests (the first fixture fails); return verified/CURRENT for any live runner in either path (the obsolete-pin fixtures fail); treat "enrollment advanced" as success (the failure-injection fixture fails); require a session identity for the detached reconciliation (the sessionless fixture fails); keep health's restricted path list (the supervise-only fixture fails); skip the post-arm verification (the explicit post-arm result and `generation` event assertions fail). Production bound provisional: before dispatch the U1 brief inventories every changed owner and caller (execution-identity reads, orchestration, outcome changes, production-wiring fixtures) and supplies a changed-line allocation including tests; the page's 150-line estimate never limits required behaviour or proof.
- U2 (D3, D4), builds after U1: the pending-swap record, distinct from the cancellation request, and its completion by the keeper before every automatic proof-start path; the code-moved predicate and the source-equivalence comparison in the rebuild path; tests: an arm during a running proof fixture → the swap waits, the status says so, and the keeper's observation shows completion before moved-main recovery, the cadence and the observation's request; a records-only move → no rebuild, no new generation, "nothing to deploy" despite the new stamp main would embed; a code move → rebuild and one generation; mutations: complete the swap during the proof (the waiting fixture fails); start a proof before the swap completes (the ordering fixture fails); rebuild on a records-only move (that fixture fails). Production bound provisional (estimate ≤120 lines).

## Problem

Every delegate worktree writes its git objects into `<gitdir>/objects-quarantine`, which `createJobWorktree` registers in the repository's `objects/info/alternates` (`internal/delegation/dispatch_phase.go:741-793`; the delegate's git is routed there by `internal/adapter/supervisor/env.go:144-155`), so the repository reads the delegate's commits through the alternate. The absorb that publishes those objects into the repository, content-verified, and drops the alternates line exists (`internal/diskstore/quarantine.go:157-265`, `AbsorbQuarantine`; `RemoveAlternate` at `:106`), but it runs only as the last step of a workspace release (`internal/dispatch/delegate_workspace.go:133-134`, `BeforeRemoval: p.absorb`), and a release needs every clause of `observe` (`delegate_workspace.go:54-117`): readable job records, a closed chain, durable evidence, every round's custody proven dead, and no uncommitted or unarchived content. A workspace kept for any of those reasons keeps its alternate for as long as it is kept. A job worktree whose chain's records are gone is kept forever, with the instruction "a person decides: git -C … status, then git worktree remove it once nothing is needed" (`internal/steward/disk_delegates.go:76-78`): the machinery sends the person to the one act that destroys the borrowed objects. So the repository depends on its own kept worktrees, and its own guidance leads to the loss.

## Decisions

D1. **Objects are absorbed when they are final, not when the workspace goes.** Observation stays read-only (`OwnerProof.Observe` creates nothing, `internal/diskstore/owner.go:73-76`; planning calls it before the pass mode is known, `stores.go:75`, `sweep.go:253,284`): the delegate observation reports a retained workspace whose chain is closed and whose every round's custody is proven dead as "absorbable" in its verdict, and an APPLY pass (the steward's applying disk pass and `disk clean` without `--preview`) runs the absorb for such retained workspaces under the store's critical section before the removal evaluation, in every pass that reaches that point, after revalidating identity and eligibility inside the section and taking a complete, refreshed use census with no holder of the workspace or its quarantine (custody death covers recorded identities, group membership and tagged survivors, `custody_death.go:171`, not every process; an untagged writer could add objects after the inventory and before the alternate disappears): a holder or an incomplete census leaves objects and alternates untouched and reports Pending naming it; preview and report-only passes report the eligibility and change neither objects nor alternates (`cmd/metasystem/intent_disk.go:159`). The absorb is the existing `AbsorbQuarantine` (content-verified; a repeat re-inventories and re-verifies, published objects are retained; `internal/diskstore/quarantine.go:188-263`) followed by the drop of the alternates line; a failing absorb reports Pending with its reason and leaves the line in place; an open chain or a live round leaves the quarantine and its alternate untouched (the next round writes there and the repository reads through the alternate). A kept workspace therefore holds nothing the repository depends on once absorbed. The release keeps its own absorb before removal, so no removal path loses its guard.

D2. **The machinery never sends a person to `git worktree remove`.** A job worktree whose chain's records are gone, whether it is a registered delegate store (observation today returns Pending at `internal/dispatch/delegate_workspace.go:68-74`, before any absorb) or an unregistered legacy worktree adopted by the scanner (`internal/steward/disk_delegates.go:50-78`), is absorbed by the apply pass when the use census (`diskstore.UseCensus`) finds no live user of it (records are not needed for an absorb; a live user makes it Pending naming the user), and its verdict names the machinery's route: `metasystem disk clean --discard <path> --reason <why>`. That route, for a records-gone delegate, resolves and validates the worktree's identity, registers it when it is not, keeps any worktree that contains a nested repository, submodule history or an independently registered descendant (the outer discard never authorises deleting those stores; `plans/disk-hygiene-design.md:323`: unsupported nested repositories stay report-only; today `judgeContent` returns at once for a discard, `workspace_release.go:300`, and removal is forced, `:616`), and uses the EXISTING locked release sequence (`internal/diskstore/workspace_release.go:99-171`: identity revalidation, complete use proof, tip archival including detached and reflog-only history, absorption, removal journaling), waiving only the chain-evidence checks that cannot be made without records and the uncommitted content the person explicitly discards; a failed archival prevents the removal (`plans/disk-hygiene-design.md:264-274, 303-310`), and the shared archive helper PROPAGATES an error enumerating an existing HEAD or branch reflog (today `workspace_release.go:507, :511` drop both errors): a confirmed absence is allowed, an enumeration failure makes the discard Pending before removal. `metasystem disk show` says of every worktree whose quarantine is still borrowed "the repository borrows its objects; remove it only through metasystem disk clean", and of an absorbed one "its objects are in the repository". Git offers no hook on `git worktree remove`, so the guard is D1 (a closed workspace has nothing to lose) and this guidance.

## Problem, measured

Between 2026-10-11 22:12 and 2026-10-12 08:40 the lane landed nothing. Everything that went wrong was noticed by a person (m1e, through hand-written watchers polling `landing status`, the incident register, the queue and the host load) and corrected by a person's act in Wido's name: three false main reds from timing-sensitive tests under build load (153, 168, 174), a stale exception question that held the lane idle for an hour after main had moved (158), a keeper that re-asked instead of proving the moved main (159), a person's return refused twice (171, 178), an agent with no recorded step for 55 minutes and nothing that explained the wait (134), a verb run with a stale engine (162), a batch of one while a second goal waited ten hours (150), proofs of 72 minutes under load (139), a resolution check of 95 minutes (133), a proof wedged on a lost response (early 10-11). The lane runs a seat steward (the same process every install runs) which does seat bookkeeping; the fleet view printed "stalled since 13:19" for the lane's goals all night and nobody acted on it. The lane is not a regular seat and its steward is instructed as one.

## Decisions

- D1 The lane steward is a role of its own on the landing install. It reads the lane's health facts on every keeper tick, judges them against the noticing table (D3), acts with the lane's verbs under the lane's own authority (the lane acts as the seat, Wido 2026-10-10), records every act as an intervention (what, why, how — the shape of the human steward's log), and asks the person once and plainly only when no verb resolves the situation (D5). It replaces nothing the agent does inside a batch; it watches the lane from outside the batch.
- D2 Health facts, one source (every fact says measured or unmeasured; a missing record is never read as a quiet host, a current premise or a green main; reading health writes nothing — where the status reader persists what it observes, such as an abandoned resolution through `RefreshMerge`, health observes through a read-only path and a test asserts the records unchanged after a read) (`landing status --json` gains a `health` object; `landing health` prints it): per waiting goal its age since hand-in and the reason it waits; batch state and age; the agent's step and idle-since (U8 of lane-housekeeping-2); paused/stopped with reason and since; every open question with its age and its premise: current, gone or unknown — gone only on evidence the question carries (the agent's "main is at commit X" fact with main moved past X; the checkout-not-on-main fact with the checkout on main; a policy request whose recorded effect satisfies it), unknown otherwise; every incident with the recorded attribution and the repeat evidence that exists (a named repeat green, a repeat red, no repeat yet) and the load at the time where a result recorded it; the host load now, and at each proof's start and end once the lane records them (from this design on every result carries its load samples; older results say unmeasured); the lane engine's commit against main; the last three proof durations against the median; the last push time; each goal's time in the lane against the one-hour target (Wido 2026-10-11 08:00: a green batch lands in about an hour; a red goal returns with no human touch).
- D3 The noticing table is the specification. Each row is one observation from the log, the signal in the health facts, the judgement, and the act or the question. The first table is written from the 2026-10-09..12 log (below); the steward appends a row whenever a person intervenes in the lane again (the intervention log is the queue of rules not yet coded).
- D4 Acting. The steward may: prove main (`landing prove --trunk`, D8 of lane-batching repeats its reds first); withdraw its own stale question and re-ask after a fresh proof; start and stop the lane; end a silent agent session through the settle path (`settleLandingAgent`; `landing stop` only pauses admission), and wake the agent; return a goal as the lane with its disagreement recorded; redeploy the lane engine when main moved with lane code (the queued goal landing-deploys-the-engine is this act); restart a young proof for a newcomer (lane-batching D2); hold the host's builds while a proof attributes, or defer the attribution (the capacity guard of S63 as machinery: proofs and builds on one host are metered by one rule); open the fix goal of a load-fragile test the register names twice (a broken machine cannot heal itself, Wido 2026-10-12 08:30: the fix is not left to a person's notice; the goal is built and landed as any goal). Metering other installs' builds is not an act of this design (see Step 1); the steward reports the load. Every act is one record in artifacts/agents/landing/interventions.jsonl and one line in status and in the fleet view. Bounded: one act per situation per hour; never a person's process ended; never a code push without its gate; never a person's verb refused (R-142/143).
- D5 Asking. One question per situation; line one is the situation in plain words, then the verbs that would resolve it; the question is withdrawn by the steward when its premise changes (main moved, incidents cleared, the goal returned) and re-asked only if the situation returns. The person is told what was tried.
- D6 Instructions. The lane steward is Go code on the keeper's tick (no model, no session, no tokens): the table is its checklist, the interventions file its memory, and the hourly report the judgement Wido asked for on 2026-10-03 (quality: reds and their causes; speed: cycle time per goal against the hour; tokens: the agent's and the critics' spend per landing, or unmeasured and which record is missing). The landing agent's skill gains a section about the steward: what it watches, what it does, that a withdrawn question is not re-asked without a fresh proof, that `landing health` is read before any question to a person.
- D7 Fleet. The fleet view's "stalled since" line for the lane becomes the lane steward's line: what it noticed, what it did, what it asks. m1e stops watching the lane by hand the day U2 lands.

## Threat model

(1) The steward acts wrongly under load: one act per situation per hour, every act logged and visible, no act ends a person's process or pushes code without its gate. (2) Question churn: one question per situation, premise-based withdrawal. (3) HAL9000: the steward never refuses or reverses a person's act; it records disagreement (R-142/143). (4) The steward and the agent act at once: the steward acts only outside the agent's turn (agent idle) or on facts the agent cannot see (host load, engine version, question premises). (5) The table rots: every human intervention appends a row; the hourly report names rows that fired and rows that never did.

## Step 1 and what is deferred (R-121)

Step 1 is U1 alone. After it the lane steward exists as a reader: `landing health` (and the `health` object of `landing status --json`) prints the health facts of D2 and, under them, every row of the noticing table whose signal is present now, with the act or question the row prescribes — but nothing acts. The fleet view's line for the lane is that output's first line. A person reading the fleet view sees what m1e had to poll for over three days. Deferred after step 1, in order: U2 adds the acts whose verbs exist today, each bounded; U3 the skill and the hourly report; U4 the load-fragile test landing; U5 the refusal defects. Never in this design: metering other installs' builds (the host has no build verb; the capacity guard stays a script of the person who launches builds), ending a person's process, pushing code without its gate.

## Units (each ≤ 250 production lines, independent files; built in this order, each hand-landed under the broken-machine rule)

- U1 (step 1) Health facts and the rows that fire: `internal/landing/plain/health.go` (new) builds `Health` from the records `readStatus` already reads (queue entries with their hand-in times, the running proof and its `since`, `last_proof`/`trunk_proof` with durations, the agent step record of `agent_step.go`, paused/stop, the lane questions in the channel with the main commit at ask time, the trunk incidents, `hostload.Read`, the lane install's engine identity read from its binary stamp (`internal/enginebuild`'s stamp reader, never the observing process's own build info: finding 162 was exactly two engines on one host) against `origin/main`) and `Rows() []Fired` evaluates the table; `status.go` adds `Health *Health json:"health,omitempty"`; `cmd/metasystem/intent_landing.go` adds `landing health` (summary lines; `--json`); the fleet view's lane line reads the first line. Tests use fixture records shaped like 2026-10-11/12 (a stale trunk-red question after a code commit; incidents with main moved; an agent silent 55 min; a batch of one with a newcomer inside the window; a proof at 1.6× median under load 33); no act, no network.
- U2 The loop: `internal/landing/plain/steward.go` (new), run from the keeper's existing tick when the agent is idle: for the rows with verbs today — stale question → `WithdrawStaleLaneQuestion` then a trunk proof; moved main with incidents → trunk proof before any question; stale engine → the engine redeploy; silent agent → the stop path's session end and a wake; flake under load → the named repeat (replay.go, `continueRed`) — one act per row per hour, each appended to `artifacts/agents/landing/interventions.jsonl` (what, why, how, row) and shown in status. - U3 The skill and the hourly report: `skills/lane-steward/SKILL.md` replaces the seat steward text on the landing install; the report (quality: reds and causes; speed: minutes in lane per goal against 60; tokens per landing) is written from the health facts and the interventions file once an hour to the lane's record and the fleet line.

- U5 Person-refusal defects: every refusal of a person's verb is an intervention record and a row; the steward reports the count until it is zero.

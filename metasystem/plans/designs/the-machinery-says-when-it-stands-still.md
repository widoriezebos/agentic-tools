## 4. Decisions

- **D1 A steward duty that fails is a health row of its own (G9).** Each per-tick duty (disk sweep, tick timing, question replies, unit boundary, seat recovery requests, notifications pending, channel pending, cache trim, the breach-stop notice) writes its latest outcome, empty on success, to `duties.json` under the runner directory (`runner.go:236`), through one helper called at the stderr sites above; the startup ledger examine is not a duty here (its recovery has its own component record). **One health role per duty**, `steward-duty:<name>`, generated from the duty list into `healthRoleOrder`, so the per-role consecutive count and cause (`health.go:200-206`) are per duty and a flapping duty cannot mask a steadily failing one. A duty role has **no** automatic remedy (a role with one never resets on a changed cause and never becomes standing: `health.go:895`, `:958-960`, `health_standing_test.go:61`), so the same-cause count resets on a changed cause and `Standing` is set at five (`:960`); what changes for duty roles is notification eligibility alone: a duty role's dead observation does not notify until it is standing (one predicate beside `NoLawfulRemedy`, `health.go:959-985`), so one transient timeout is a row and nothing more, and a steadily failing duty fires the existing `health-standing-red` pattern at five, per duty; the sibling page's G7 routes that defect to an owner. On a helm seat the duties still run (`runner.go:371` settles replies before the helm branch) but the tick skips health (`tick.go:291-297`); G9's report-only helm path observes the duty roles and files their standing defects, on top of G10's helm pass, so the observed seat (m1e, the helm) counts its own failing duties. **A partial observation files only what it observed**: the standing-defect filer today iterates every role in `healthRoleOrder` and clears any role absent from the supplied set (`health.go:996-1020`, `ObsClear` with `ClearTicks: 1`, resolved at once by `pattern_episode.go:337`); with the helm's partial pass, an unobserved role produces no clearing observation, so a standing defect of a role the helm never checked stays open until a full observation or a repair, while an observed duty's success still clears its own. The row lags one tick (health runs before the duties); accepted. The landing lane's keeper is unchanged: its agent failures are the lane steward's rows. Rejected: one shared role (one count, one cause: a noisy duty hides another); a new alert kind; escalating on the first failure; an automatic "retry" remedy (it would keep the duty from ever standing).
- **D2 A ready priority-1 goal behind the one-claim rule is a row at once, and its holder is told (G10).** `goal/verbs.go` exports a read-only quota query, `ClaimQuotaBlocker(tree, target, actor, laneState)`, which `claimQuotaRefusal` itself calls, so the exceptions (same arc, fenced, waiting to land, handed over; a person's incoming claim exempt at `:1678-1680`, which is not `ValidateTree`'s reservation exemption at `validate.go:509-513`) live once. It returns the blocking claim, **its outcome and the command that outcome needs** (a returned claim: `work land <held>` to inspect its return, `verbs.go:1473`; a landed claim: `goal done <held>`; an excess landing slot: `work land <slot>` to inspect its landing state, `:1490`, never a release (release would drop its claim and landing marker, `:2331`, `:664`); an ordinary held claim: `goal release <held> --reason …`, `:1494`), and **the waiting claims that still need their landing markers** (`:1478`, `:1497`), which only `claimQuotaRefusal` records into the claim transaction (`:1700`, so the claim still validates, `validate.go:501-513`); health reads the result and records nothing. A `claim-quota` check runs it from the cached projection with the production lane-state reader (`landing_plain.go:39-63`) for each goal in `Next.Ready` with `Priority == 1`, pinned to this machine or unpinned. The row names the ready goal, the holding claim, whether that claim has a running job or an open question, and the query's own command for that claim's outcome (land, done or release), then `metasystem goal claim <ready>`. It has no automatic remedy, so it alerts at once (`NoLawfulRemedy`, `health.go:959-961`, `ShouldAlert`, `:985`). Because the standing-defect pattern G7 routes forms only after five failures and three ticks, G10 carries its own handoff: one `agent ask --goal <held>` to the holding claim's holder (the ready goal is unclaimed and names nobody), deduplicated per (ready, held) pair, through the same ask writer G7 will generalize. On a helm seat `helmTick` runs this one check and its ask (report only, no decision; `tick.go:291-297`), since the observed seat was the helm. The one-claim rule itself is unchanged (section 9).
- **D3 A records-only move of main keeps main's full green (G11).** For a **trunk** proof only (`running.Trunk`), a scoped records-only result and the full green it inherits from are not hour-bound: `decideScope`'s records-only branch accepts the newest ancestor full green whose tree differs from the current tree by record paths only (`recordsOnlyPaths` over `git diff --name-only <FullTree> <tree>`, as `trunk_recovery.go:219-222` already does) at both age checks (`scope.go:136-139` and `:148-156`, keeping the unreadable-time and future-time refusals), `fullCurrent` treats such a scoped trunk result like an inherited one (`scope.go:476`), and the **keeper** does not count it as debt. That exemption is a keeper-specific debt calculation, `keeperProofDebt`, used by both `WakeReasons` (`wake.go:95`, which today returns the shared debt before the clock helper runs) and `KeeperClock` (`keeper_clock.go:83`, which reads `scopedProofDue` directly and reaches the fresh trunk proof at `:176`); the shared `scopedProofDue` is unchanged and still reports the debt to batch admission's `overdueBatch` (`depth.go:47`, `proof_admission.go:205`), so an executable batch after an exempt trunk result still gets full depth when it is overdue, and the four-hour clock stands. `keeper_clock.go` is in G11's scope; G11 lands before the sibling page's G3 changes the keeper's wake order (push before the clock), and G3's brief is cut on G11's tip. Goal-batch proofs keep every rule they have (the hour limit, batch depth, the push's coverage test, `proof_admission.go:199-219`, `push.go:346-383`); a standing-red scoped result with `OwedSince` or unproved groups is never exempt. One addition for the push, from finding 439 (21:1x today): when `landing push` merges record-only commits of main into a proven batch, the merged tree whose diff from the proven tree is records only (`recordsOnlyPaths`) inherits the batch's green, recorded as trunk recovery records its inheritance (`trunk_recovery.go:245-246`), instead of refusing "HEAD's tree was never proven" and proving the whole batch again (45 minutes today); an executable difference still refuses as today. Goal-page moves keep today's inheritance (no checks); every other records move runs the five record checks and inherits the rest. A full proof of main then has three triggers: the four-hour clock (`proof.trunk-every`), an executable change (`scope.go:180-189`), a fresh request (`--fresh`, a resume, a deploy restart). Rejected: inheriting green with no checks for non-goal records (a malformed record would wait for the clock); routing goal-page moves through the checks (unchanged behaviour, not today's defect; named in section 7); relaxing batch proofs (not this page's authority).

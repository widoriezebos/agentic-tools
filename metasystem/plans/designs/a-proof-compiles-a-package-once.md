# Design: a proof compiles a package once, then fans out

- Id: 01M4ZA0000000000000000MEM1
- Kind: design
- Status: accepted
- Goals: a-proof-compiles-a-package-once
- Evidence: lane test finding 336 (2026-10-15 17:36: twelve Go compiles of 3.2–3.6 GB each during the proof of 6226d4a32, swap 94 %, 61 GB of pages in the compressor); finding 324 (the morning's memory wipe-out); analysis/memory-hogs-and-root-causes-2026-10-15.md H1; Astra rounds 1 (analysis) and 2 (pages) folded.

## Problem

A proof partitions `cmd/metasystem` into up to 3 × Workers shards (`internal/proofrun/test_go.go:917`), Workers = GOMAXPROCS = 18 on this host unless the environment lowers it (`test_go.go:133`), and `runGoPartitions` (`internal/proofrun/test_build.go:1393`) starts a goroutine per partition that acquires a worker and launches its `go test -trimpath -json -count=1 -timeout 0 -p=1 -parallel=1 -run ^(…)$ <packages>` (`:1455-1485`); the worker pool bounds how many run, not when they start, so 18 shards of one package launch in the same second. A partition may name several packages: `partitionGoTests` groups packages that share test names (`test_go.go:818`, kept by `TestGoPartitionsKeepDuplicateNamesAndBuildOnlyPackagesComplete`), and build-only packages (no tests, or `TestMain` only) are scheduled on purpose (`test_go.go:850`) and end with a package-level `skip` or `pass` terminal and no test `run` event (`test_go.go:1014`). The build cache is shared (`internal/testenv/testenv.go:684`), but a cache entry helps only a shard that starts after the entry exists: 18 simultaneous misses of the same build action compile the test binary of `cmd/metasystem` 18 times cold, about 3.5 GB each. When the binaries run, each shard's `TestMain` builds its own engine candidate (`cmd/metasystem/ambient_controls_test.go:59, :89-101`: `go build -trimpath -o <namespace TMPDIR>/metasystem-wait-candidate-*/metasystem .`), again up to 18 cold compiles of the main package. App fixtures build a third variant through `testenv.Engine` (`internal/testenv/toolchain.go:124-129`: `-buildvcs=false`, `-o` into the binary's namespace, no `-trimpath`), serialised only within one test binary by the toolchain slot (`toolchain.go:20`), so across 18 shards it compiles cold up to 18 times as well. Bursts of 18 × 3.5 GB on a 64 GB host: the kernel compresses and swaps everything else, the compiles stall in swap, and every process on the host thrashes.

## Decisions

D1. **Shards start one at a time per package.** Readiness is tracked per (partition, package). A partition is launched only when, for every package it names, the previous partition naming that package has resolved that package: by the first `go test -json` event with `"Action":"run"` for it (the test binary and the vet result are then in the shared cache and that shard's `TestMain` has finished its own engine build, so the next shard compiles nothing and only links), or by that package's terminal event (`pass`, `skip` or `fail`: a build-only package resolves on its successful terminal; a failed package resolves too, see D2). The `start` event never resolves anything: Go emits it before it knows whether the build failed. The wait happens before the partition acquires a worker, so a waiting partition holds no worker and partitions of other packages keep launching. Nothing about the worker count, `-p`, GOMAXPROCS, the partitioning, the grouping of packages into partitions or the shard arguments changes; the order among the partitions naming one package is the partition order.

D2. **A producer that ends resolves its waiters; nothing is suppressed, nothing is retried concurrently.** When a partition's command exits, every package it names is resolved for its successors, whatever the outcome: a successor of a failed package is launched in its turn, compiles the package again as today, fails the same way, and the proof reports the failure as it does today (`goGateNativeFailure`; no test of another package in the same partition is lost, no build is retried in parallel with another). A partition that could not be launched (setup error) resolves its packages the same way. If the proof is cancelled (`shardCtx`, `test_build.go:1420-1424`: cancel and join), every waiter ends with the cancellation like the launched shards do; a waiter never waits on a timer and never waits past its producer's exit.

D3. **In-test engine builds take one lock per build variant across processes.** Two build variants are named explicitly: the wait candidate (`go build -trimpath` of `cmd/metasystem`, `ambient_controls_test.go:94`) and the fixture engine (`testenv.Engine`, `toolchain.go:124-129`). Each holds, for the life of its `go build`, an advisory `flock` on a file named by that variant's identity (the go subcommand, its build flags in order WITHOUT `-o` and without any path under a namespace or temp root, the package path and the module path) in the directory of the shared Go build cache the command runs with (the pair `sharedGoCacheEnvironment` resolves, `testenv.go:684`), so every test binary on the host building the same variant agrees on the lock. The lock is taken after the per-binary toolchain slot and released before it (slot, lock, build; release in reverse); `HoldToolchain` stays as it is. The first holder compiles cold; every later holder of the same variant finds the compile cached and links. The lock orders builds only: no build is skipped, no flag, directory, custody, tag or output path changes, and a lock that cannot be created or taken fails the build with the error named (no fall-through to an unlocked build). The acquisition honours the command's context (`GoContext`): a cancelled waiter returns the cancellation without starting the command, and the slot and the lock's descriptor are released on every exit.

D4. **The effect is measured, not asserted.** Each partition's log begins with how long it waited and for what ("waited 71 s for shard 1 of cmd/metasystem to begin running"; "no wait"). The claim is "no two cold compiles of one build variant at once", not a host-wide compile count: the watcher's HEALTH line carries the number of concurrent Go compiles and the next proof's peak is compared with today's twelve.

## Units

- U1 (D1, D2, D4 logging): the per-(partition, package) readiness in `runGoPartitions` (`internal/proofrun/test_build.go`): a resolution per package of a partition raised by that package's first `run` event or its terminal event in the partition's output stream, or by the command's exit or launch failure; the next partition naming the package waits on it before `acquireTestWorkers`; cancellation joins the waiters; the wait is logged. Tests on the snapshot harness of `internal/proofrun/test_go_workers_test.go` (`TestReal`; the `goShardLifecycleHooks` output hook at `test_build.go:1303`; the readiness/release barriers the worker tests already use, `test_go_workers_test.go:426`): a package with three partitions on a two-worker pool, the producer held before its first `run` event by a barrier, proves the successor is blocked at command entry until the release, that one worker stays available and a shard of an unrelated package launches while the producer is held, and that the third partition waits on the second, not on the first; a partition naming two packages that overlap another partition's packages proves it waits for both predecessors; a build-only package (no tests) and a `TestMain`-only package resolve their successors on their terminal and the proof passes; a package that does not compile resolves its successor on exit and the proof reports the build failure for each partition as today; a cancelled context ends a waiter promptly. Mutations: release on `start` (the compile-failure fixture emits `start` and then fails: the successor must still be blocked); resolve per partition instead of per package (the overlapping-partitions test fails); hold the worker while waiting (on the two-worker pool the unrelated shard cannot launch while the producer is held). ≤140 production lines.
- U2 (D3): the per-variant cross-process build lock in `internal/testenv` (`toolchain.go`): a `buildLock(ctx, variant)` taken by `Engine` and offered to the wait-candidate build through the `GoCmd` run path for `build` commands, keyed as D3 says, placed beside the shared build cache, honouring the context. Tests: two test processes (the package's fork/child pattern) building the same variant from different namespaces and output paths: the second's `go build` enters only after the first's ends (barriers at command entry, holder record read while held); two different variants do not wait on each other; a build that fails under the lock releases it and reports its own error; a cancelled waiter returns the cancellation while another process holds the lock and leaves no descriptor; the lock directory is the shared cache's, not the namespace TMPDIR; the order is proven: with this binary's toolchain slot held, a build of this binary is acknowledged waiting for the slot while another process acquires the same variant's lock and builds, and after the slot is released exclusion proceeds as usual; `TestWaitCandidateIsBuiltInsideTheNamespace` keeps executing. Mutations: key the lock by output path (the two-process test fails); take the lock before the slot (the ordering test fails: the other process cannot acquire the lock while this binary waits for its slot); fall through on a lock error (the unwritable-directory test fails). ≤100 production lines.

## Not in scope

The worker count and host-load admission (`metasystem-test-proof-host-load`), the hand gate script (one `go test` process per package; its in-process workers inherit the parent's candidate), the engine candidate's location (disk-lifetimes A9), the memory of one compile of `cmd/metasystem`, and a host-wide limit on concurrent compiles.

## Critique record

- Round 1 on the analysis (Astra, gpt-6-astra, 17:51, scratchpad/codex-crit-memory-1.log; 9 material, 2 minor): the shared candidate built by the runner and its fallback withdrawn (fail-open; it also skipped the namespace assertion); the gate waits for the first `run` event, not `start`; producer failure and cancellation paths added; the third build variant named and the per-variant lock added (D3, U2); the claim bounded to "no two cold compiles of one variant" (D4); shard count 3 × Workers.
- Round 3, second on the pages (Astra, 18:10, scratchpad/codex-crit-memdesigns-2.log; page A: 0 material, 2 minor, folded): the worker test uses two workers so unrelated progress is observable while the producer is held (R2-A1, U1); the slot-then-lock order has an explicit oracle (R2-A2, U2). Converged: 4 → 0; accepted.
- Round 2, first on the pages (Astra, 18:01, scratchpad/codex-crit-memdesigns-1.log; page A: 4 material, 1 minor): readiness per (partition, package) because partitions group packages and a failed package must not suppress a partition's other work (A1, D1/D2); an exit without a `run` event is not a failure, build-only packages resolve on their terminal, and failure propagation is tested through three partitions (A2, D1/D2/U1); the lock key excludes `-o` and namespace paths, the variants are named, `HoldToolchain` is untouched, exclusion proven at command entry across two processes (A3, D3/U2); the lock acquisition honours the command's context (A4, D3/U2); barrier-based tests instead of a timing oracle (A5, U1).

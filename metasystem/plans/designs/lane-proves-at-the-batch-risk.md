## Problem (measured, finding 57/58 of the lane test)

Landing fleet-provider-and-session-recovery took two hours: the skill runs a cheap gate proof after every merge (`landing prove --gate --wait`, scope impact) and then the full proof before the push. The gate selected 107 of about 110 unit packages (the goal changes core packages) and ran 63 minutes, longer than the full proof's 55 minutes on the same tree (the impact runner shards like the full, groups.go:163; the cost is the selection's size and its per-shard process overhead on a near-full selection). The full proof is the whole suite (231 packages, 402 CPU-minutes, floor 22 minutes = the longest shard; 35 minutes wall on a quiet host, 55 under contention) and does not grow with the batch, so batching amortises it; the per-merge gates grow with the batch and duplicate it.

## Decisions

D1. **One proof per batch, at the batch's depth** (ruling R-149-m1e, Wido 2026-10-10, amending R-3: the change decides the depth, the batch's riskiest tier is the floor). After its merges the agent runs `metasystem landing prove` once. The engine chooses the depth: `full` when the riskiest member's tier is at or above `landing.full-from-tier` (default 3), else `impact`. The attempt records depth and reason (member tiers, share); `landing status` prints them (`proving at impact depth: tiers 2,2; 41% of the tree`). The push admits a green at the chosen depth.

D1a. **Impact depth is its own scope, with its own provenance** (critique F1: the existing `scoped` scope inherits a prior full proof's timestamp and identity, scope.go:98/407, and the cheap runner emits no environment fingerprint, prove.go:1166 re-runs full on an empty one). A new scope value `impact` records: the batch base (the fetched main the merge started from), the tree, the plan hash (`test impact --plan` output), and the proof environment fingerprint, which the impact runner prints with the same `landing environment` line the full reporter prints. An impact result is valid for exactly that base and tree; it inherits nothing from any full proof and needs no earlier full green. Fixture: a first low-tier landing with no prior full proof of its tree proves at impact depth and pushes.

D1b. **Impact depth runs the static and build checks first** (critique F2: `test impact` excludes groups whose inputs cover cmd/**, so `fast-static-build` never runs at impact depth, test_impact.go:86-96; the reporter runs its static phase only when full, full.go:149-160). The impact proof runs the `fast-static-build` group (build, vet, static) before its selected tests, and that group's red is the proof's red. Fixture: impact tests pass while static fails; the proof is red.

D2. **Impact only when it is cheaper.** Before an impact proof the engine computes the plan (`metasystem test impact --plan`) and, when the selected whole packages reach `landing.impact-max-share` percent of the full plan (default 50) or include cmd/metasystem whole, it runs the full instead and records the reason (`impact would cover 97%: full`). Same cost, more coverage.

D2a. **The measure counts change-driven selections only.** The share counts every test-bearing package with any selected test, whole or named, against the full plan's packages; groups the contract always selects (its canaries) are left out on both sides, since they say nothing about the change; a change-driven selection naming any cmd/metasystem test is never cheap (unit U5, after the first live measure: a "cheap" check that ran 48 minutes, finding 87, and a measure that read every plan as not cheap because of the canaries, finding 89).

D2b. **The resolution check follows the same rule.** The conflict-resolution job's check (`--check 'metasystem test impact'`, skill case 4) and the fix round's check compute the plan first; when impact is not cheap the check is the proof's fast-static-build group only (build, vet, static) and the batch proof carries the tests. Measured: pcc's resolution check ran impact for over an hour on three one-hunk conflicts because the goal touches cmd/metasystem. The collection step of a resolution or fix job (the repeated `work build`) reuses the job's recorded check result when the staged tree and base are unchanged (same tree hash), instead of running the check again (measured: pcc's collection re-ran a 55-minute impact check the job had just run).

D3. **A gate runs only when cheap, every gate runs the static group, and a skipped gate is a recorded state.** `landing prove --gate` keeps its place in the skill after each merge. Every gate, cheap or skipped, first runs the `fast-static-build` group (build, vet, static; today's cheap runner excludes it, test_impact.go:86) and records that group's result on the gate record; its red is a gate red. When D2's rule says the impact is not cheap the gate records state `skipped` with the reason (`impact covers 97%; the batch proof follows`) after the static group. Every gate record carries the merge it was REQUESTED for (`Requested` = the merge commit, HEAD at the request) and, separately, the commit the check ran or failed on (`Attributed`: the merge, or its first parent when the baseline check failed, gate.go:80 / prove.go:1126). `landing status` exposes `last_gate` by `Requested == HEAD` (critique round 1b F5 and round 3 F2: an absent or stale gate must never read as the current outcome, and a baseline failure on the parent must stay visible as the current gate's red with the parent named): states `green`, `red` (with `Attributed` and the cause), `skipped`, or `none` for this HEAD. Skill cases 1, 2 and 5: `skipped` continues like `green` (merge the next member or run the batch proof); `none` means the gate has not run for this merge. Attribution of a red in a multi-member batch stays the fix round's job (the lane is the batch's seat); the agent may still run an explicit `--gate` per member when it needs the culprit. Fixtures: an absent gate record and a stale red gate from an earlier HEAD both read as `none`.

D4. **A green on the same tree, from the same base, with its static group green, is not repeated.** `landing prove` at depth impact reuses the last gate attempt only when it is green on the same tree, at the same depth, with the same proof environment fingerprint, with the `fast-static-build` group recorded green on it (critique round 3 F1: a gate without the static group is not an impact proof), AND the same comparison base as the batch proof (the batch base) (critique F3: a per-merge gate compares against the merge's first parent, gate.go:54-68, so after merging A then B the last gate selected A->A+B while the batch proof selects main->A+B; a one-member batch's gate base equals the batch base, a later member's does not). It then records `proven by attempt X` and proceeds to the push; otherwise the batch proof runs. The full after a green impact on the same tree still runs (the complement-only run, per-package reuse, is a follow-up goal). Fixtures: a two-member batch whose last gate is green is NOT reused; a one-member batch's is; a one-member gate with tests green and the static group red is not reused and the push is refused.

D5. **Batches split by depth class, never across ancestry** (`landing.batch=auto`). Waiting goals group into the cheap class (tier below `landing.full-from-tier`) and the full class, in queue order. A waiting line whose branch contains another waiting member's tip, or is contained by one, stays in the same batch as that member at the higher of their depths (critique round 2 F1: selecting a cheap B whose branch contains full-tier A would merge A unselected and admission refuses it, batch.go:710); the split only separates lines with no shared ancestry. The cheap batch is selected first; the full batch follows and absorbs main's move through the existing refresh merge. One class present means one batch, as today. Status names the class; `after` records and conflict handling are unchanged. Splitting per tier value is rejected: it shrinks batches and multiplies full proofs. Fixture: full-tier A queued, cheap B containing A: one batch of A and B at full depth.

D6. **An overdue full proof rides the next batch.** When the keeper has raised `full-due` (wake.go:82-87), the next batch proves at `full` depth whatever its tiers, and its green after the push resets the full-proof clock (critique F4: today the skill runs the trunk proof only when nothing mergeable waits, SKILL.md:168-169, so a busy queue of cheap batches could defer the full proof indefinitely). With nothing waiting, the trunk proof runs as today. Detection of an impact-missed regression is therefore bounded by one cadence period plus one batch. Its red is the batch's or main's by the existing replay attribution. Fixture: `full-due` set and a low-tier batch waiting proves full and resets the clock.

Settings (config/defaults.go with help text): `landing.full-from-tier=3`, `landing.impact-max-share=50`.

## Follow-up (own goal, makes impact trustworthy beyond low tiers)

Per-test coverage map: the cadence full proof runs instrumented once and records which packages each test executes; impact then selects tests by executed packages (exact), not inferred symbols. Also: per-package green reuse keyed by tree, and sharding in the impact runner.

## Threats and nets

- Impact misses a dependency: a red lands on main at impact depth. Nets: D2 (core changes prove full), D6 (an overdue full proof rides the next batch), tiers (only low-risk batches), the lane's hot-fix path. Bound: one cadence period plus one batch.
- A tier is set too low: same nets; a person sets tiers.
- Reuse of a green whose environment differs: D4 keys on tree, depth and the proof environment fingerprint prove.go already records.
- Skipped gate hides which member broke a multi-member batch: the fix round fixes the batch; `--gate` per member stays available.

U4 (D5, D6): selector by depth class keeping ancestry together at the higher depth; `full-due` forces the next batch to full depth and its green resets the clock; status class and reason lines. Tests: mixed tiers, one class, empty; cheap B containing full A -> one full batch; full-due with a low-tier batch.

## Acceptance

The next batch after deployment lands with one proof at its depth; a low-tier batch's proof under 25 minutes; a core-change batch proves full once with no 63-minute gate. Stop rule for the design: Astra critique to material zero, at most three rounds; build one unit at a time, Opus read each.

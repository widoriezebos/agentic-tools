## 1. What is typed, and where the binary is

`metasystem` is on nobody's PATH: an interactive zsh answers `metasystem not found`, and `~/.local/bin` holds no link. The binary is `<installation>/bin/metasystem`, an untracked build artifact of `go run ./cmd/devgate build` (README.md:179; docs/architecture.md:11-13), one per checkout. Wido's history (`~/.zsh_history`) shows how it is reached: 50 lines `./bin/metasystem goal approve`, 13 `bin/metasystem goal approve`, 20 `./bin/metasystem goal set-budget`, 12 `goal set-pin`, 11 `goal unapprove`, 12 `goal enroll-terminal`, 12 `session stop`, and from the repository top `metasystem/bin/metasystem status --repo .`; nearly every line carries `--id G --by Wido`. Never a bare `metasystem`. Two consequences: the completion must be registered for the basename and answer for any path spelling, and each call back must run the binary the person typed, so the checkout they sit in answers with its own tables (tmux `human:11` sits in `agentic-tools-ui/metasystem`, the other windows in `agentic-tools-m1e`). Both shells do the basename lookup: zsh's `_set_command` sets `_comp_command2="${command:t}"` (`/usr/share/zsh/5.9/functions/_set_command:21-26`), `_normal` dispatches on the full word, then that tail, then `-default-` (`_normal:37-40`; `_dispatch:46-56`); bash tries the full pathname, then "the portion following the final slash" (bash(1), Programmable Completion). Wido's zsh loads oh-my-zsh and then runs `compinit` itself (`~/.zshrc:75`, `:113-114`); bash on this Mac is 3.2.57, which has `complete -F`, `COMP_WORDS` and `compgen` but no `compopt`.

The router has no framework to hook: `dispatchWithFamiliesAndRepositoryTop` (cmd/metasystem/main.go:250-292) routes `help`, `internal`, `status`, then an object to `dispatchObject` (:299-327), then a one-word entrypoint or family to `dispatchInternal` (:345-383). Its tables are `intentCommands()` (cmd/metasystem/intent.go:114-142; one `intentCommand` per (object, action), :52-88, with `usage`, `flags`, `maxArgs`, `hidden`), `intentObjects()` (:1029-1039), `registeredFamilies()` (main.go:100-226) and `registeredTopLevelEntries()` (:63-87). Flags are one table too: `allFlags()` adds `--repo` and `--json` to every row (intent.go:287-289), `lookupFlag` resolves aliases (:291-303), `parseIntentArgs` refuses what `lookupFlag` does not know (:340-361). No row sets `passthrough` today, so every public row's options are in the table. The ledger's open goals are one file each, `plans/goals/<id>.md` (internal/goal/file.go:4; `stateroot.RelativeRoot(Goals)` is `plans/goals`, internal/stateroot/stateroot.go:271-290): line 1 is `# <id>`, line 3 `- State: <state>` (the writer, file.go:1716-1717; the parser takes the id from the `# ` line, :559-564; the id is also the file stem, `goalIDFromPath`, internal/goal/reconcilepub.go:241-248). Done and abandoned goals live in `records/goals/` (434 files); `plans/goals/backlog.md` is the ledger's root record, not a goal (approval.go:178, :473), and has no State line. Today: 170 files, 125 queued, 34 parked, 8 approved, 2 claimed.

## 2. Slice 1: what exists after it

**D-words.** Two words. `metasystem __complete -- WORD...` is a one-word process entrypoint in `registeredTopLevelEntries()` (launcher `cmd/metasystem/completion.go`, evidence `__complete`): the shell glue starts it, nobody types it, and `metasystem internal` lists it as it lists `up` (main.go:453-470). `metasystem system completion SHELL` is a public row beside `system enroll` (cmd/metasystem/intent_process.go:123-131): audience human, `maxArgs` 1, SHELL one of `zsh` and `bash` (spelled `zsh|bash` in its usage line), any other word refused with exit 2 naming both; it prints the glue script for that shell and reads nothing. `system` is an administration object, so its help scope is administration by itself (`helpScope`, cmd/metasystem/intent_help.go:137-145). `intentObjectSummaries["system"]` (intent.go:1006) gains "completion". Wido adds one line after `compinit` in `~/.zshrc` (after line 114): `[ -x ~/LocalStorage/GitHub/agentic-tools-ui/metasystem/bin/metasystem ] && eval "$(~/LocalStorage/GitHub/agentic-tools-ui/metasystem/bin/metasystem system completion zsh)"`. The script embeds no table, so any checkout's binary prints the same one.

**D-protocol.** WORD... are the shell words after the command name up to and including the word under the cursor, which may be empty. The `--` is not optional: `helpAware` turns a lone `--help` into help (cmd/metasystem/helpers.go:140-152), and the entry itself answers `--help` with `usage: metasystem internal __complete -- WORD...` and exit 0, an unknown first word with `does not take X; nothing was done` and exit 2, no words with that usage on stderr and exit 2, as every entrypoint must (section 5). After `--` it prints one candidate per line, `WORD<TAB>DESCRIPTION` (the tab and description optional), already filtered by the current word's prefix, or the single line `:files`, which tells the shell to complete file names. Exit 0 in every case after `--`, and nothing on stderr; the glue discards stderr as well, so no error ever lands in the command line.

**D-derive: every position is answered from the router's own tables.** Word 1: `intentObjects()`, `status`, `help`, `internal`, with `intentObjectSummaries` as descriptions. After an object: `objectActions(object)` (intent.go:1060-1068), public rows only, summaries as descriptions. After `help`: the objects, then that object's actions (`runIntentHelp`, intent_help.go:243-300). After `internal`: every family name and every one-word entrypoint (`__complete` included; it is a routed word and `metasystem internal` lists it); after `internal FAMILY`: its verbs with their summaries (main.go:100-226). After `OBJECT ACTION`, or after `status` (the row with the empty action, cmd/metasystem/intent_table.go:551-568), the row `findIntentAction` returns (intent.go:276-279) decides: a current word starting with `-` offers every `allFlags()` name that is not `hidden` (intent.go:43), as `--name`, its `usage` as description, aliases accepted but not offered; a previous word that is a flag taking a value (`value != ""`, joined `--name=` handled the same) offers that value's kind; otherwise the k-th positional is offered by the k-th placeholder after the action across the row's usage lines. Value kinds, from the placeholder text alone: `G`, `[G]`, `G...`, `G2` are goal ids (13 flags and 36 usage lines spell it so, `status G` at intent_table.go:554 among them); `FILE`, `PATH`, `DIR`, `ROOT` answer `:files`; a lowercase `a|b|c` offers those words (`human|main`, `yes|no|unknown`); anything else offers nothing. `--` ends the flags as it does for the parser (:344-347). Hidden rows (`hiddenIntentEntries`, intent_table.go:532-550: `goal fetch`, `goal next`, ...) are never offered under their object; they are reached under `internal goal`. A typo earlier on the line finds no row and offers nothing.

**D-goals: ids from the ledger directory, no git, nothing recorded.** The goals directory is `plans/goals` under the state root. Without `--repo`/`--root` on the line the root comes from the executable's installation exactly as `stateroot.installationRoot` finds it (parent of the binary's `bin`, checked by `installationShape` = a `metasystem.conf` file; stateroot.go:292-307, :238-241), through `stateroot.NewResolver(top, os.Executable).StateRoot(stateroot.Goals)` (:46-48, :108-127). The default `top` runs `git rev-parse --show-toplevel` (:50, :78-90; `RootForInstallation` calls it for every adopted installation, :133-143, and `selectRoot` goes through it, intent.go:623-647): completion passes its own `top`, which returns the nearest ancestor of its argument holding a `plans/goals` directory, so no process is spawned in either layout. With `--repo P` typed earlier on the line, P (relative to the working directory) goes through the same `top`. The reader is one `os.ReadDir`, then per `*.md` one open and one read of at most 4 KiB, taking the id from the file name and the state from the first line beginning `- State: `; a file without such a line (the root record) is skipped, and so is any file that cannot be read. Candidates are `id<TAB>state`, sorted by id, prefix-filtered. The directory missing, unreadable or empty: no goal lines, still exit 0. Nothing in `internal/goal` is imported: that package journals, fetches and runs git (attention.go, journal.go), none of which a Tab may do.

**D-glue.** The zsh script, in `system completion zsh`'s output:

```
_metasystem() {
  local -a lines specs; local line
  lines=(${(f)"$("$words[1]" __complete -- "${(@)words[2,CURRENT]}" 2>/dev/null)"})
  [[ $lines[1] == ':files' ]] && { _files; return }
  for line in $lines; specs+=("${line%%$'\t'*}:${line#*$'\t'}")
  _describe -t metasystem 'metasystem' specs
}
compdef _metasystem metasystem
```

`$words[1]` is the command as typed (`./bin/metasystem`, `metasystem/bin/metasystem`), so the checkout's own engine answers. The bash script is the same shape with `"${COMP_WORDS[0]}" __complete -- "${COMP_WORDS[@]:1:COMP_CWORD}"`, `COMPREPLY` from the first column, `compgen -f` on `:files`, and `complete -F _metasystem metasystem`; no `compopt`, so it runs on 3.2.

**D-safe.** A Tab runs one process (unavoidable: the tables are in the binary) and it touches: the two in-memory tables, one readdir, up to N bounded file reads. No git, no lock, no journal, no receipt, no fetch, no hook. The process start runs `cmd/metasystem/run.go:175-187`'s `init`, a kernel probe of its own pid and an emitter that fires only when a run event is emitted; `__complete` emits none. The entry reaches its handler through main.go:287-289 and :354-357 with nothing in between.

**D-fast.** Process start is the floor: three runs of `bin/metasystem help` measure `real 0.00` (under 10 ms for the 52 MB binary). The tables are built in memory per call, as help builds them. The goal read is bounded by construction: one readdir plus one 4 KiB read per file, 170 files today; `cat` of all 170 files takes 60 ms including the shell, the in-process read a fraction of that. No cap and no cache at 125, 170 or 1000 goals; the benchmark in section 4 is the evidence.

## 4. Proof for slice 1

Each test goes red when its rule alone is removed. All in `cmd/metasystem/completion_test.go` unless named.

1. `TestCompleteOffersEveryRoutableWordAndNothingElse`: for word 1, the offered set equals `intentObjects()` + `status`, `help`, `internal`; for every object, equals its public actions; under `internal`, equals every family and entry; under each family, its verbs. Then the oracle: every offered word sequence, with `--help` appended, is routed by `dispatchWithFamiliesAndRepositoryTop` through the sentinel families of `intent_router_test.go:20-46` (its `repositoryTop` panics: routing resolves nothing) with exit 0 and an empty stderr, so nothing unroutable is offered; and for every public row, every family verb and every entry, its words are offered at their position, so everything routable is completable. Hidden rows: `goal <TAB>` lacks `fetch` and `next`; `internal goal <TAB>` has them.
2. `TestCompleteOffersEachCommandsOwnFlags`: for every public row the offered `--` words equal the non-hidden `allFlags()` names, each parses through `parseIntentArgs` with no `unknownIntentFlag`, and `--fixture-human-authority` (hidden, intent.go:108-109) is never offered; `--lineage` is offered exactly where `intentCommands()` unhides it (:130-139).
3. `TestCompleteValuesFollowThePlaceholder`: a fixture directory with three goal files (queued, parked, claimed) and a `backlog.md` root record: `goal approve <TAB>` offers the three ids with their states, `goal approve fi<TAB>` the prefix matches, `goal budget --id <TAB>` the same, `status <TAB>` the same, `backlog` never; `work build G --brief <TAB>` answers `:files`; `goal open G --origin <TAB>` answers `human` and `main`; `--reason <TAB>` answers nothing. With the directory absent: no goal lines, exit 0, stderr empty. With `--repo P` earlier on the line, P's ledger answers.
4. `TestCompleteReadsWithoutGitOrRecords`: the resolver is built with a `top` that records its calls and an `executable` pointing into the fixture; a completion leaves the fixture tree byte-identical (hash before and after), `top` was called with the installation and nothing else, and `completion.go`'s import block (read with `go/parser`) names neither `os/exec` nor `internal/goal`. `BenchmarkCompleteGoalIds` over 1000 fixture goals is evidence for D-fast, not a gate (no wall-clock assertion: internal/testenv/walltime_test.go:52).
5. `TestCompletionScriptsCallBackThroughTheTypedCommand`: the zsh script contains `"$words[1]" __complete --` and `compdef _metasystem metasystem`; the bash script `"${COMP_WORDS[0]}" __complete --` and `complete -F _metasystem metasystem` and no `compopt`; `system completion fish` exits 2 naming zsh and bash; `--json` renders the usual envelope (intent.go:690-704) with the script under `data.script`.

## 6. Later, when it hurts

- `goal open G` offers existing ids where a new one is wanted; exclude it when it annoys (it works: the verb refuses a duplicate).
- Ids filtered by the action's admissible states (approve: queued), and done ids from `records/goals/` for `goal reopen`.
- A non-repeat flag already on the line offered again; `--flag=value` in bash (`COMP_WORDBREAKS` splits on `=`); LABEL from the ledger, NAME from the enrollment, `norm`/`keep` for BOX, job ids.
- A cache when a ledger has thousands of goals; fish; a copy of the script in `fpath` instead of the `eval` line.

## 7. Not in it

No change to any verb, parser, help page or table field; no new package; no framework. No completion of internal verbs' own options (they have their own parsers: after `internal FAMILY VERB` nothing is offered). No PATH installation of the binary. No network, git, lock, record or hook on a Tab.

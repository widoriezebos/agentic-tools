## 1. What is typed, and where the binary is

`metasystem` is on nobody's PATH: an interactive zsh answers `metasystem not found`, and `~/.local/bin` holds no link. The binary is `<installation>/bin/metasystem`, an untracked build artifact of `go run ./cmd/devgate build` (README.md:179; docs/architecture.md:11-13), one per checkout. Wido's history (`~/.zsh_history`) shows how it is reached: 50 lines `./bin/metasystem goal approve`, 13 `bin/metasystem goal approve`, 20 `./bin/metasystem goal set-budget`, 12 `goal set-pin`, 11 `goal unapprove`, 12 `goal enroll-terminal`, 12 `session stop`, and from the repository top `metasystem/bin/metasystem status --repo .`; nearly every line carries `--id G --by Wido`. Never a bare `metasystem`. Two consequences: the completion must be registered for the basename and answer for any path spelling, and each call back must run the binary the person typed, so the checkout they sit in answers with its own tables (tmux `human:11` sits in `agentic-tools-ui/metasystem`, the other windows in `agentic-tools-m1e`). Both shells do the basename lookup: zsh's `_set_command` sets `_comp_command2="${command:t}"` (`/usr/share/zsh/5.9/functions/_set_command:21-26`), `_normal` dispatches on the full word, then that tail, then `-default-` (`_normal:37-40`; `_dispatch:46-56`, which unquotes each name first, `:51`); bash tries the full pathname, then "the portion following the final slash" (bash(1), Programmable Completion). Wido's zsh loads oh-my-zsh and then runs `compinit` itself (`~/.zshrc:75`, `:113-114`); bash on this Mac is 3.2.57, which has `complete -F`, `COMP_WORDS` and `compgen` but no `compopt`.

The router has no framework to hook: `dispatchWithFamiliesAndRepositoryTop` (cmd/metasystem/main.go:250-292) routes `help`, `internal`, `status`, then an object to `dispatchObject` (:299-327), then a one-word entrypoint or family to `dispatchInternal` (:345-383). Its tables are `intentCommands()` (cmd/metasystem/intent.go:114-142; one `intentCommand` per (object, action), :52-88, with `usage`, `flags`, `maxArgs`, `hidden`, `passthrough`), `intentObjects()` (:1029-1039), `registeredFamilies()` (main.go:100-226) and `registeredTopLevelEntries()` (:63-87). Two kinds of row. A parsed row goes through `parseIntentArgs` (intent.go:340-395): `allFlags()` adds `--repo` and `--json` (:287-289), `lookupFlag` resolves aliases (:291-303), an unknown option is refused (:361), `--` ends the options (:344-347), a word that does not start with one or two dashes is positional (:353-356), a `rest` option takes every later word (:47, :363-376: `work build --check COMMAND...`, cmd/metasystem/intent_work.go:201, the only one), and a value option takes the next word literally even when it starts with a dash (:381-390). A passthrough row (`passthroughAction`, cmd/metasystem/intent_table.go:29-56: 17 rows, receipt add/status/retro, experiment record/challenge/status/check, session status/handoff/isolate/wait, test plan/add/remove/baseline/list/status) hands its words to an owner with its own parser (`runPassthrough`, :58-84); help shows `helpFlags()` (intent.go:1230-1237): a passthrough row's documented `flags` only, a parsed row's `allFlags()`. The ledger's open goals are one file each, `plans/goals/<id>.md` (internal/goal/file.go:4; `stateroot.RelativeRoot(Goals)` is `plans/goals`, internal/stateroot/stateroot.go:271-290): line 1 is `# <id>`, line 3 `- State: <state>` (the writer, file.go:1716-1717; the parser takes the id from the `# ` line, :559-564; the id is also the file stem, `goalIDFromPath`, internal/goal/reconcilepub.go:241-248). Done and abandoned goals live in `records/goals/` (434 files); `plans/goals/backlog.md` is the ledger's root record, not a goal (approval.go:178, :473), and has no State line. Today: 170 files, 125 queued, 34 parked, 8 approved, 2 claimed.

## 2. Slice 1: what exists after it

**D-words.** Two words. `metasystem __complete -- WORD...` is a one-word process entrypoint in `registeredTopLevelEntries()` (launcher `cmd/metasystem/completion.go`, evidence `__complete`): the shell glue starts it, nobody types it, and `metasystem internal` lists it as it lists `up` (main.go:453-470). `metasystem system completion SHELL` is a public parsed row beside `system enroll` (cmd/metasystem/intent_process.go:123-131): audience human, `maxArgs` 1, SHELL one of `zsh` and `bash` (spelled `zsh|bash` in its usage line), any other word refused with exit 2 naming both; it prints the glue script for that shell and reads nothing. `system` is an administration object, so its help scope is administration by itself (`helpScope`, cmd/metasystem/intent_help.go:137-145). `intentObjectSummaries["system"]` (intent.go:1006) gains "completion". Wido adds one line after `compinit` in `~/.zshrc` (after line 114): `[ -x ~/LocalStorage/GitHub/agentic-tools-ui/metasystem/bin/metasystem ] && eval "$(~/LocalStorage/GitHub/agentic-tools-ui/metasystem/bin/metasystem system completion zsh)"`. The script embeds no table, so any checkout's binary prints the same one.

**D-protocol.** WORD... are the shell words after the command name up to and including the word under the cursor, which may be empty. The `--` is not optional: `helpAware` turns a lone `--help` into help (cmd/metasystem/helpers.go:140-152), and the entry itself answers `--help` with `usage: metasystem internal __complete -- WORD...` and exit 0, an unknown first word with `does not take X; nothing was done` and exit 2, no words with that usage on stderr and exit 2, as every entrypoint must (section 5). After `--` it prints one candidate per line, `WORD<TAB>DESCRIPTION` (the tab and description optional), already filtered by the current word's prefix, and before them zero, one or two directive lines, each starting with a colon: `:prefix N` says the cursor word is a joined option value whose first N bytes (`--name=`) the shell must keep and not complete; `:files` says the shell completes file names for what follows. They combine, `:prefix N` first (`--brief=notes=v1/de` answers `:prefix 8` then `:files`). Exit 0 in every case after `--`, and nothing on stderr; the glue discards stderr as well, so no error ever lands in the command line.

**D-derive: every position is answered from the router's own tables.** Word 1: `intentObjects()`, `status`, `help`, `internal`, with `intentObjectSummaries` as descriptions. After an object: `objectActions(object)` (intent.go:1060-1068), public rows only, summaries as descriptions. After `help`: the objects, then that object's actions (`runIntentHelp`, intent_help.go:243-300). After `internal`: every family name and every one-word entrypoint (`__complete` included; it is a routed word and `metasystem internal` lists it); after `internal FAMILY`: its verbs with their summaries (main.go:100-226); after `internal FAMILY VERB` nothing (their parsers are their own). After `OBJECT ACTION`, or after `status` (the row with the empty action, cmd/metasystem/intent_table.go:551-568), the row `findIntentAction` returns (intent.go:276-279) decides, walking the earlier words as its parser does: a `rest` option ends everything, nothing is offered after it; `--` ends the options, every later word is positional; an option with a value consumes the next word as that value, dash or not, and a joined `--name=value` consumes none; the remaining words are positionals, counted. Then, for the current word: after a value option, the value kind of that option (below), whatever the word's spelling (`--brief --draft=v1/de` is a separate value, no directive); when the walk itself finds the current word to be a joined option `--name=part` (a word in option position, not a consumed value), the directive `:prefix N` with N the byte length of `--name=`, then the value kind filtered by `part`, candidates printed without that prefix; else a current word starting with `-` offers every `helpFlags()` name that is not `hidden` (intent.go:43), as `--name`, its `usage` as description, aliases accepted but not offered; else the k-th positional is offered by the k-th placeholder after the action across the row's usage lines. Value kinds, from the spelling of `intentFlag.value` or the usage placeholder, and nothing else: `G`, `[G]`, `G...`, `G2` are goal ids (83 usage placeholders, 13 `value: "G"` flags and one `G2`; `status G` at intent_table.go:554 among them); `FILE`, `FILE...`, `PATH`, `DIR` answer `:files` (`design check FILE...`, `design review FILE`, `--brief FILE`, `--repo PATH`, `--installation DIR`); a lowercase choice list offers its words (`human|main`, `yes|no|unknown`, `strong|weak|unknown`, `1|2|3`); every other spelling offers nothing: `TEXT`, `NAME`, `N`, `ID`, `REF`, `TARGET`, `J`, `DURATION`, `INSTALLATION`, `LABEL`, `BOX`, `COMMIT`, `GRANT`, `CODE`, `COMMAND`, `j2:ID`, `DEPENDENT=REASON`, and `ROOT`, which names a delegate-chain root (`work wait --chain`, intent_work.go:242) or a critic root (`work review --critic`, cmd/metasystem/intent_delivery.go:96), never a path. Hidden rows (`hiddenIntentEntries`, intent_table.go:532-550: `goal fetch`, `goal next`, ...) are never offered under their object; they are reached under `internal goal`. A typo earlier on the line finds no row and offers nothing.

**D-goals: ids from the ledger of the checkout the command acts on, no git, nothing recorded.** The command's checkout is what `selectRoot` selects (intent.go:623-647): the `--repo` (or `--root`) value typed earlier on the line, joined to the working directory when relative (:624-630), else the working directory; the executable's installation is never consulted (Astra TC-01: from the repository top, `metasystem/bin/metasystem goal approve --repo . <TAB>` must find `metasystem/plans/goals`; another checkout's binary must answer with the current checkout's goals). Completion makes the same two calls `selectRoot` makes, `ResolveLayout(path)` then `RootForInstallation(layout.InstallationRoot)` (:631-634), on `stateroot.NewResolver(top, executable)` (stateroot.go:46-48) whose `top` is pure: the nearest ancestor holding a `.git` entry (file or directory), which is what `git rev-parse --show-toplevel` answers once the resolver has scrubbed the steering variables (:78-104; the default `top` spawns git, :50), and whose `executable` returns an error (neither call reads it). What comes back, precisely: for the nested template, `ResolveLayout` names `<repo>/metasystem` with `Template` true (:186, :196; `templateMode` is the base name `metasystem` plus the conf key, :320-323, internal/config/template.go:18-21), `RootForInstallation` returns it unchanged (:133-140), goals are `<repo>/metasystem/plans/goals`, from the repository top and from inside `metasystem/` alike; for an adopted installation, the installation is the nearest ancestor holding `metasystem.conf` inside the repository (`installationAncestor`, :201-217; `installationShape`, :238-241) and `RootForInstallation` returns `top(installation)`, the repository top (:141), so goals are `<repository>/plans/goals` even when the installation sits beneath it; for a directory in no repository, `adoptedAncestor` (:220-233) may still name an installation but `RootForInstallation` fails as it does for the verbs, and no goal id is offered. `ResolveLayout` stats and resolves symlinks itself (:160-168). The reader is one `os.ReadDir` of that directory, then per `*.md` one open and one read of at most 4 KiB, taking the id from the file name and the state from the first line beginning `- State: `; a file without such a line (the root record) is skipped, and so is any file that cannot be read. Candidates are `id<TAB>state`, sorted by id, prefix-filtered. Nothing found, unreadable or empty: no goal lines, still exit 0. Nothing in `internal/goal` is imported: that package journals, fetches and runs git (attention.go, journal.go), none of which a Tab may do.

**D-glue.** The zsh script, in `system completion zsh`'s output:

```
_metasystem() {
  local -a lines specs; local line
  lines=(${(f)"$("${(Q)words[1]}" __complete -- "${(@Q)words[2,CURRENT]}" 2>/dev/null)"})
  [[ $lines[1] == ':prefix '* ]] && { compset -p ${lines[1]#:prefix }; shift lines }
  [[ $lines[1] == ':files' ]] && { _files; return }
  for line in $lines; specs+=("${line%%$'\t'*}:${line#*$'\t'}")
  _describe -t metasystem 'metasystem' specs
}
compdef _metasystem metasystem
```

`$words[1]` is the command as typed (`./bin/metasystem`, `metasystem/bin/metasystem`), so the checkout's own engine answers; `(Q)` removes the shell's quoting from the executable and from every word (zshexpn(1), as `_dispatch:51` does for names), and `(@)` inside the quotes keeps empty words as arguments, so `--repo "my dir"` reaches the engine as one word and the empty cursor word stays. The glue guesses nothing about the word's shape: no pattern appears in it. Only on the engine's `:prefix N` directive, which the parser-faithful walk emits solely for a joined option value, `compset -p N` moves the first N characters of the word (`--name=`) into `IPREFIX` (zshcompwid(1), compset -p), so `_files` and `_describe` complete and insert the value after it; a separate value, however spelled (`--brief --draft=v1/de`), and a positional get no directive and are never touched, and a path holding `=` keeps it (`--brief=notes=v1/de` completes `notes=v1/de`). A pattern in the glue tested spelling, not parser context (Astra TC-08, held at the confirmation read); the one decision now lives in the Go walk, where the parser's context is. The bash script is the same shape with `"${COMP_WORDS[0]}" __complete -- "${COMP_WORDS[@]:1:COMP_CWORD}"`, `COMPREPLY` from the first column, `compgen -f` on `:files`, and `complete -F _metasystem metasystem`; no `compopt`, so it runs on 3.2; the joined form is not handled in bash (section 6).

**D-safe.** A Tab runs one process (unavoidable: the tables are in the binary) and it touches: the two in-memory tables, a few stats on the way up to the repository top, one readdir, up to N bounded file reads. No git, no lock, no journal, no receipt, no fetch, no hook. The process start runs `cmd/metasystem/run.go:175-187`'s `init`, a kernel probe of its own pid and an emitter that fires only when a run event is emitted; `__complete` emits none. The entry reaches its handler through main.go:287-289 and :354-357 with nothing in between.

**D-fast.** Process start is the floor: three runs of `bin/metasystem help` measure `real 0.00` (under 10 ms for the 52 MB binary). The tables are built in memory per call, as help builds them. The goal read is bounded by construction: one readdir plus one 4 KiB read per file, 170 files today; `cat` of all 170 files takes 60 ms including the shell, the in-process read a fraction of that. No cap and no cache at 125, 170 or 1000 goals; the benchmark in section 4 is the evidence.

## 6. Later, when it hurts

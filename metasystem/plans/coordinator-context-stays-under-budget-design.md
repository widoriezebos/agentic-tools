## 1. What the measurements say

On m1e on 2026-09-12, `metasystem goal list` printed 19.3 MB of JSON for 645 goals: approved 11, claimed 3, done 311, open 167, parked 4, queued 149. `History`, containing every ledger entry for every goal, occupied 18.3 MB; `NextStep` occupied 0.58 MB and `Intent` 0.51 MB. These are rounded byte measurements supplied for this design. They supersede the goal page's earlier 9 MB observation. `goal show --id` printed 32 KB; `supervise status` printed 196 bytes.

Across today's three seats' Claude transcripts, a fix-forward day with no delegate rounds, tool results totalled 6.7 MB. The seats' own reads dominated: `sed` 1.34 MB over 495 calls, `grep` 0.65 MB, and `Read` 0.42 MB, with single reads reaching 58 KB. Engine output was small: one `goal show` result was 30 KB and one `goal claim` result 29 KB. Nineteen `goal list` calls contributed only 0.07 MB because the seats already piped them through `jq`. The unfiltered 19.3 MB measurement and the filtered transcript measurement describe different surfaces.

The audit days had a different mix: the coordinator loop repeatedly read `goal list`, watch results, test logs, and landing output, while the conversation accumulated toward the million-token ceiling. `artifacts/reports/delivery-deep-dive-2026-09-11/claude-sessions.md` section 1a reports coordinator means of 386 to 507 thousand prompt tokens per call, versus 76 to 126 thousand for delegates. Section 4b records automatic compactions around 967 thousand tokens, each dropping about a million, roughly one per active seat per day. Its exact count is 19 compactions across the cohort, including manual compactions at smaller sizes; the daily description is approximate.

That audit file is retained local evidence in the m1e source checkout, outside tracked source. The 2026-09-12 measurements above were taken on m1e by the seat that owns this page (goal list piped through a byte count, the three seats' transcripts summed by tool result). Both belong in the retained baseline for the implementation proof.

The decision follows both observations: remove accidental bulk at the verb, then bound conversation accumulation across all reads. A small status result is no reason to remove it; a shell filter is no protection against the next unfiltered invocation. Smaller individual responses alone cannot prevent hundreds of useful file reads from accumulating.

## 2. Bound output where each verb produces it

Paths below are relative to the metasystem installation root unless explicitly repository-relative. The Go output owner will be `internal/output`, with `MaxInlineBytes = 32 * 1024` in `internal/output/bounded.go`. This is a byte bound on the complete response visible to the caller, including diagnostics and progress, not a token estimate or a bound per printed line.

Today `cmd/metasystem/goal.go:294` accepts `goal list` flags `-fetch`, `-label`, `-pretty`, and `-root`; it defaults to JSON. `listSynced` at line 375 emits complete goal records, including History, and its `open` collection also contains the live goals repeated in state collections. The existing pretty path includes full intent text. `runGoalShow` at line 457 accepts only `-id` and `-root` and prints a JSON envelope containing the entire goal. The following output modes are proposed changes, not existing flags.

`goal list` defaults to one line per goal: `id state priority:sequence tier pin claimant next-step`. The claimant is the recorded machine plus lineage; absent values print `-`. Only the first line of the next step is shown, limited to 120 Unicode characters including a trailing `...` when shortened. Text fields have embedded controls escaped. Group by state in the order claimed, approved, open, queued, parked, done; within every bucket use the ledger's numeric priority and sequence rank, unranked goals last, then id for deterministic ties. Include each goal once, including archived goals, and retain short projection warnings. `--pretty` remains an alias for this summary.

`goal list --json` selects records without `History`, retaining root, accepted tip, and projection warnings. Use disjoint state buckets so `open` means state open; do not duplicate every live goal. `goal list --history <id>` selects only that goal's ledger entries, in recorded order, from the same accepted projection, including archived goals. With `--json` that selection is JSON. Preserve `--fetch`, repeated `--label`, and `--root`; a history id that fails the requested labels produces an explicit no-match response. No mode means whole-ledger History.

`goal show --id <id>` renders the goal page's current fields and next step without History. `--history` includes that goal's complete History; `--json` selects the corresponding structured record. This is a view, not a replacement for the integrity-protected stored page. Neither summary formatting nor omission changes the accepted ledger or its integrity checks.

For every verb, first produce the full selected representation behind the Go output boundary. If it exceeds 32,768 bytes, store the complete representation at `artifacts/agents/output/<verb>-<timestamp>.<ext>` and print one summary line giving outcome, absolute path, and exact size. Normalize a compound verb to a hyphenated name, use UTC nanosecond timestamps with exclusive creation and collision retry, and choose `.txt`, `.md`, `.json`, or `.jsonl` to match the bytes. Example: `goal-list: 645 goals; full output: /checkout/metasystem/artifacts/agents/output/goal-list-20260912T120000.123456789Z.txt; 118420 bytes`.

When JSON was requested, the one line is a typed JSON reference with `outputMode: "file"`, `verb`, `path`, `bytes`, `format`, and `outcome`. Consumers resolve it from disk before parsing the selected representation. Small JSON remains inline. Update all in-repository callers, including existing `jq` pipelines and fixtures, together with the output change. Internal Go callers use typed values or explicit result files rather than parsing a console projection. There is no unbounded console flag.

The same boundary covers `goal claim` and other ledger mutations, `goal next`, watch, health, supervision/status, delegate and critique displays, test commands, landing commands, and error paths. Protocol responses to runtime adapters use their existing typed result/file channel; large evidence goes in referenced artifacts, never in a protocol-breaking replacement for the required envelope. A file spill preserves exit status and mutation outcome. A persistence failure is explicit and bounded; it never falls back to printing the bulk or suggests a successful mutation should be repeated. Reserve and open the evidence destination before starting a mutation or subprocess.

Finite responses are withheld until their size is known. Long-lived watch and test invocations retain complete output as it arrives and show bounded progress only, reserving space for the final path line; once that allowance is used, further progress stays in the file. stdout and stderr share the invocation allowance. The original streams and their identities remain in the artifact. Nested command output is consumed by the parent and does not obtain a second console allowance.

`test run` and land already have short progress lines, but that does not bound their whole response. `cmd/metasystem/test.go:1491` prints the complete retained `TestResult` when no result path is supplied, including group detail; the launcher at `internal/proofrun/launcher.go:137` also forwards child output to its log and caller. The short `TEST-RESULT` and failing `TEST-GROUP` lines are at `test.go:1499`. Keep their decision fields visible, retain complete results and logs in files, and apply the shared bound to everything forwarded.

`scripts/agents/land.sh:263` prints step names and `-- ok`. Its coverage-delta failure at line 281 prints the full failed-step output; other failures and push retries print forty-line tails, and proof verification prints a twenty-line tail. None of those tails bounds bytes. Keep every failing package in the retained coverage report and print its count plus path. The Go output owner retains these streams before the shell's temporary step file is removed. Byte bounding never removes required proof from disk or makes a shortened log into the proof verdict.

## 3. Briefs and evidence travel by path

The current `scripts/agents/templates/brief.md` has prose Goal, Inputs, Constraints, Expected Return, and Acceptance Criteria slots without an inline size contract. `internal/dispatch/composition.go:231` embeds the full brief; lines 258 to 279 embed the prior brief, prior return, and critique register into fresh continuation packets. Critic roles return complete findings and evidence JSON (`scripts/agents/roles/design-critic.md:14`, with the same pattern in `code-critic.md`); the implementer returns complete evidence and a narrative (`roles/implementer.md:11`). Those canonical files are needed. Reading or relaying their complete bodies into coordinator conversation, or embedding them again on a follow-up, is the inflation surface.

The rule is that briefs, designs, critique bodies, delegate returns, diffs, logs, and evidence are referenced by path and digest, never copied into a dispatch message, notification, follow-up, or self-handoff. The brief template names input paths and precise sections; dispatch packets carry the brief path and bounded routing instructions. Return notifications carry outcome, material finding count or open-item count, and canonical return/evidence paths. The complete schemas and replayable `{command, observed, level}` evidence remain in the canonical files. A short observation describes the result; it does not paste the log.

Change the composition owner and its declared source recipe together: record the digest of referenced bytes and the digest of delivered reference text separately. The recipient can open required sections without pretending the full source was delivered inline. This preserves source authority and independent critique. No path-only notification can certify that its findings were addressed; the critic register still joins all findings to dispositions from the files.

Referenced inputs must be readable from the successor's actual workspace and runtime. Keep immutable files in the control root, stage verified copies for another host, and retain referenced evidence until every dependent claim, review, and weekly proof has ended. Copy a required scratch file into retained artifacts before transferring; never rely on a predecessor's temporary directory surviving. Store source identity and digest with each pointer. A missing or changed required path stops transfer with that path named. Large path inventories are manifests, also referenced by path.

Direct `sed`, `grep`, and native file reads remain part of the budget. The instruction change belongs in the brief template, role contracts, continuation contract, and `docs/orchestration.md`: request the smallest needed section, redirect broad searches to an artifact, and pass only references across sessions. Native tool delivery uses the adapter's shared Go output boundary where available; any tool surface bypassing it must still be included in the next-call accounting in section 4. A blanket 32 KB read allowance is not permission to issue an unlimited batch.

## 4. Account for the context of each call

`internal/usage` remains the single owner of runtime usage interpretation. Add per-call context samples alongside spend records, without changing what spend aggregation counts. A sample identifies the installation, seat, runtime, session, model call, observed time, source path and digest, source cursor, token components, availability, and any provider compaction/reset marker. Runtime adapters bind the actual active session to its usage source; a seat cannot select another session's smaller transcript as its own evidence.

Here cumulative per-call context means the entire accumulated prompt presented to that model invocation. It is not the sum of the prompt sizes of all preceding invocations. Two successive calls with contexts 100,000 and 110,000 have those two samples; neither has context 210,000. Output tokens do not enter the completed call's prompt figure, but become input growth when carried into its successor. Cached input counts because the model reads it even when billing is discounted.

Put `ContextBoundTokens = 150000` and `ContextCeilingTokens = 200000` in `internal/steward/context.go`, owned by that role and consumed by the command and verdict paths. The working bound starts handoff; the ceiling permits no further ordinary work. Byte limits stay in the output owner. Constants are shared Go policy, with injected values for fixtures, never independent shell settings.

The role renders exactly one context line on each coordinator response: `context: N thousand tokens this call, bound 150, ceiling 200`. Use enough decimal precision to display the integer sample without rounding a crossing down. An unavailable sample prints `context: unknown; bound 150, ceiling 200; <reason>`. Structured health carries the exact integer, source identity, and action `continue`, `handoff`, `handoff-now`, or `unknown`; it is not inferred by parsing the display sentence.

`metasystem context status --root <installation>` is the proposed hook-independent verb for that same reading and action. `RoleContext` resolves the session through the registered seat identity. The existing Stop hook health preview (`scripts/agents/supervision-hook.sh:839`) renders the line from the role, including on allowed stops. Preview reads never advance periodic alert escalation (`health.go:265`); collecting newly observed samples is idempotent by source identity and does not count repeated previews as additional model calls.

A Stop hook is too late to prevent a large intervening call by itself. Before each model invocation, the adapter contract asks the Go context policy to admit the current prompt plus pending input, retained output, and protocol overhead. It uses an exact prompt count where supplied, otherwise a verified conservative upper bound. Tool outputs share the pending allowance; text byte length may overestimate tokens but is not the measured usage record. Unbounded attachments, hidden calls, or unknown protocol overhead cannot be admitted on an assumed reserve. If the prospective prompt reaches 150,000, prepare handoff instead of ordinary work; no prompt above 200,000 is dispatched, including handoff preparation. The 50,000-token difference is recovery room, not a second working budget.

For an already running session, an accounted call at or above 150,000 starts self-handoff immediately. At 200,000 the verdict is `hand off now`. A sample above 200,000 records a failed invariant even if the handoff succeeds afterward. A runtime without automatic interception uses the same status/admission verb before requesting further context and follows its command itself. An adapter that hides internal model calls must expose that boundary before this design can claim its guarantee; observation after completion alone is insufficient.

## 5. Hand the seat to a fresh session

Add the command `metasystem context handoff --root <installation>`. It operates on the registered current seat; no manual goal selection is needed. The seat keeps its compact working state at `artifacts/agents/context/<seat>/<session>/state.json`, with schema version, installation identity, runtime, predecessor session, observed call, and these required fields:

- `heldGoal`: id, accepted revision, and recorded claimant, or explicit null when free.
- `nextStep`: the held goal's current next step and its source page path and digest.
- `openItems`: stable ids, owners, current status, and evidence pointers, including live delegate and proof activity.
- `lastLandings`: commit ids, goal ids, receipt paths, and any unfinished transport obligation; older entries live in a referenced manifest.
- `scratchPointers`: purpose, retained path, digest, and required/optional designation for each scratch artifact or manifest.
- `messagesOwed`: recipient, subject, durable draft path, authorization reference where needed, and delivery status, including unanswered human requests.

The engine fills ledger and session facts, validates the seat-written open items and pointers, and writes atomically. Keep this state below 32 KB by moving lists into manifests. `state.json` is refreshed as work changes, so handoff never depends on generating a long retrospective at the ceiling. The handoff command freezes a version under `artifacts/agents/context/<seat>/<session>/handoff-<timestamp>.json`, with the state digest, transfer id, and all required retained pointers.

Reuse the steward's staged intent and fresh brief in `internal/steward/stage.go:23`, which already writes `artifacts/agents/steward/briefs/<nonce>.md`. Its continuation contract (`scripts/agents/roles/steward-continuation.md:10`) already starts from the memory handoff and ledger. Extend that brief to name the frozen state and resume from those records in a new provider session, with no old conversation or summary compaction supplied.

`internal/steward/revive.go:256` already recognizes an explicit handoff while the old main remains alive. Extend that intent with a context-handoff reason and predecessor release/successor acknowledgement. The Go steward owns the transfer: prepare and validate state, quiesce predecessor work, publish release, launch one fresh session, then record its acknowledgement. The successor verifies the held claim and retained paths before accepting. The claim stays with the same seat and goal; the accepted ledger remains authoritative if its revision changed. No claim is silently stolen, reopened, or concluded.

The ordinary continuation currently yields to live work. For an explicit context transfer, the acknowledged release distinguishes its predecessor from a competing coordinator. Live delegates and proof processes continue under their existing owners and become items for the successor to supervise; they are not cancelled or relaunched. This requires a context-specific transfer path through the existing intent owner, since ordinary idle revival suppresses launch while delegates are active. A free seat transfers its outstanding messages and pointers without inventing a held goal, then uses `goal next` normally.

Retries reuse the same transfer id. Before release, a validation failure leaves the predecessor responsible. After release, a launch failure leaves a durable pending transfer for the steward to retry, with no second active coordinator. After acknowledgement, the predecessor exits and cannot resume work from stale state. Provider outage, a changed claim, or missing evidence is reported as such; the transfer stays recoverable and never clears ownership merely because a timer expired. The handoff command and steward retry use no model inference.

At the ceiling the existing structured stop-verdict owner in `internal/report` takes precedence over ordinary continuation prompts. It displays `hand off now: metasystem context handoff --root <installation>`, exactly one remedy command. `scripts/agents/supervision-hook.sh:1100` already delegates precedence to that Go owner; the shell transports its decision. The hook never requests compaction or another conversational explanation. The engine can execute a prepared transfer without another model call; without a hook the seat runs that same command when the health line requires it. Successful transfer permits the predecessor to end despite work that now belongs to the successor.

## 6. Runtime independence and the boundary of the promise

Principle 0 and the goal page require correctness in the Go engine, ledger verbs, and adapter contract for Claude, Codex, Devin, and future runtimes. Output files, context policy, `RoleContext`, state validation, and transfer ownership all live there. Runtime adapters supply usage and fresh-session creation; native hooks only deliver the same decision sooner. No Claude transcript parser is imported into steward policy, and no hook is the sole owner of a decision.

At least Claude and Codex must demonstrate the full path with real coordinator work. Also exercise the same verb path with hooks absent. Devin and ACP fixtures verify their supported usage shapes and explicit unavailable states. If a rostered runtime cannot expose individual calls or fresh-session transfer, that is a remaining adapter obligation, not an exception to the goal. Do not mark the universal goal done on the strength of two passing runtimes while another hosted coordinator is unaccounted.

The goal's phrase "no context reset or compaction" prohibits lossy in-place reset and compaction. An acknowledged fresh-session self-handoff is the explicitly required boundary, with durable state and evidence continuity. Record the predecessor and successor so a reset without that transfer cannot masquerade as success.

## 9. Risks, self-grade, and rejection

The main risk is that current runtime usage is coarser than a model call. A cheap parser change can produce convincing wrong numbers. Preserve source semantics, require call coverage, and refuse to certify aggregate-only measurements. A hook that runs only after a long sequence can notice a violation but cannot prevent it; the prospective admission boundary is required independently.

Path references can hide missing evidence, and restart can lose an unsent message or duplicate a landing. Required-path validation, retained copies, claim rechecks, and acknowledgement are part of transfer correctness. The state file can itself become large; manifests keep its entry point small without dropping obligations. File output can consume disk or break old JSON pipelines; retention ownership, bounded persistence failures, and an atomic consumer cutover are required.

Frequent fresh sessions lose cache warmth and take time to orient. The smaller delegate contexts in the audit justify testing this tradeoff; the week's report also records handoff count, orientation calls, and prompt tokens per landing. Those diagnostics cannot excuse a failed maximum or an unreachable proof. Tight context bounds may require splitting a large reading task and recording its conclusions before continuing.

Self-grade against the readings: the goal's DONE and runtime-independence clause are covered by sections 2 through 7; principle 0 has Go owners and at least two real-runtime proofs; goal 15's maximum is preserved alongside p95. The two house pages supply the status block and evidence-first numbered structure. Both required audit sections and today's differing measurements are distinguished in section 1. `goal.go` flags and current output are checked in section 2; brief/return composition is checked in section 3; usage-reader limitations, Stop preview, and existing fresh continuation are checked in sections 4 and 5. Every new boundary has an owner, failure behavior, and fixture target in section 7. Design coverage: complete; implementation and runtime proof: unproven.

## Build

1. `metasystem landing rehearse [--keep]`: builds the candidate engine from the pinned candidate commit's snapshot (`git archive HEAD` into the scratch, then `go run ./cmd/devgate build` there into a scratch bin; never the working tree; no `--engine` in this unit), stamps the record with that commit, and refuses to issue a pass when the engine's build identity (the stamp devgate build prints) differs from the recorded candidate; creates a scratch directory holding a bare origin and a clone of THIS repository at the candidate commit; commits onto the scratch main one harness commit that sets `proof.full` and `proof.cheap` in metasystem.conf to the repository's fast-static-build group plus the fixture's own package (the contract's groups and canaries unchanged), records the candidate commit id in the harness commit message, and PUSHES that commit to the scratch origin before any proof or hand-in (`landing prove --trunk` proves origin/main and reads the declarations from that commit); the rehearsal asserts that the bootstrap trunk proof's commit and the green batch's base both equal the pushed harness commit; sets `METASYSTEM_SUPERVISION_REGISTRY_HOME` to a scratch registry for itself and EVERY child (verbs, keeper, jobs), sets the scratch lane's deploy-after-push off (a scratch setting; find the setting that intent_landing_push.go ~233 honours, or add one declared in config/defaults.go), registers the scratch lane (`landing set` into the scratch clone's lane checkout, machine nickname `rehearsal`), writes the seat's launch.* roster keys into the scratch lane's conf.local (never secrets), and runs one bootstrap trunk proof of the scratch main so the full-proof clock is paid.
2. Fixture: a template under plans/rehearsal/green/ (one small Go change in a tiny package with its own test, a goal file tier 1 approved and claimed by `rehearsal`, a design record naming it) generated into a scratch goal branch and the scratch ledger per rehearsal.
3. The green scenario, driven as the skill tells the agent: `work land` the fixture; the keeper tick or `landing run` starts the lane step; merge; `landing prove --gate` (assert: skipped or green, with the recorded reason); `landing prove` (assert: depth `impact`, the reason text, no full proof ran); `landing push` to the scratch origin (assert: the scratch main moved by the merge; status says landed). The driver is Go code in the engine (not a shell script), re-entrant per scenario, with a per-scenario deadline of 10 minutes.
4. The record: records/rehearsals/<candidate tree>.json with candidate commit, engine path, scenarios run, each step's wall time, outcome; printed as a summary; on failure the scratch is kept and the path printed; on success the scratch is removed (`--keep` keeps it). The rehearsal never touches the host registry, the real lane install or the real origin; a test asserts this with a canary host registration.

## Tests

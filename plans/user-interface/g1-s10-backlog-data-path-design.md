## Outcome

A human opens Backlog and sees this repository's real goals as a list grouped by lane: every live goal placed once, Ready meaning what the engine's claim gate would admit today, badges for what the record says, named gaps for what it does not, the tip's identity and age, when the server read it, what the server's last fetch found and when the next is due. The 429 done and 1 abandoned goals sit behind one toggle. Nothing is mutable; the Brain stays absent. The server keeps the accepted tip current on its own: one non-overlapping `goal.FetchAdvance` loop, five seconds apart while a browser is connected and thirty while idle, backing off on failure, never run by a request. A clone that has not yet fetched the ref reads that plainly, with the first fetch due within seconds, and never a suggestion that records are missing; a tip the engine would refuse is refused here too, by name, beside what the loop found on the canonical branch. No ordinary case ends with a command to type; the one that does is a ref set outside the engine, which no verb heals.

`stateRoot` is `lifecycle.Roots.StateRoot`, derived by `stateroot.RootForInstallation` (`roots.go:60`): `metasystem/` here, the application's repository root when adopted (D20); the root every ledger read takes. `Observe`, under one mutex:

0. `now := h.now().UTC()`; `h.lastObserve = now`; `h.next = min(h.next, now + wait(connected))` by the rule below; one non-blocking send on `h.wake`. That is the whole of a request's effect on the loop: it sets the cadence. It neither runs, starts, nor awaits a fetch, and it is answered from the ref as it stands.
1. `goal.AcceptedLedgerTip(root)`: an error is `broken` with the engine's message; not existing is `absent` when the tip is empty, else `no-ledger`. `LiveFiles` (`plans/goals/*.md` less `backlog.md`) and `ArchivedFiles` (`records/goals/*.md`) are counted in these two states only; an unreadable directory gives `nil`, never zero. Working-tree counts, labelled so; no goal is read from them.
2. The tree. If the held tip equals this one, reuse the held `goal.ValidatedTree`. Else `goal.ReadValidatedTree(root, tip)`: a `*goal.TreeReadError` is `unreadable`, `Problems` its typed problems, `Message` its `Error()`, and it is held under the tip as well, since a commit's refusal is as immutable as its tree; any other error is `broken` with the engine's message and nothing is held. Only a `ValidatedTree`, good or refused, is ever held, keyed by `Tip`.
3. Configuration, every observation: `goal.ResolveEndpoint(root)`, then `goal.SyncModeGate(e, tip)`; an error from either is `refused` with the engine's message. `SyncMode` is `Tree.Root.SyncMode` when the root record is present.
4. `Horizon = goal.NewApprovalHorizon(Tree, now)`.
5. `Admission = backlog.Admit(goal.Projection{Root: root, Tip: tip, Tree: Tree, Horizon: Horizon})`, every observation, because it reads `metasystem.conf` and its `.local` sibling.
6. State `read`.
7. `Fetch` is the loop's state as it stands, copied under the same mutex, in every ledger state.

Held by tip: the `ValidatedTree`, that is the tip, the parsed and validated tree, its commit time, or its typed refusal, all immutable facts of one commit. Not held, and why: `ObservedAt`, `Horizon`, expiry, and staleness change while the tip stands still; the ledger state, because the ref can appear, break, or move; the endpoint, the sync-mode verdict, and the admission, because git configuration and `metasystem.conf` change independently of the tip (M4); the counts, because the worktree is not the tip. A configuration flip is therefore seen on the next observation, at the same tip, with the tree still held. This package imports no `os/exec` and runs no git: every git invocation is the owner's, under its scrub (M5). `goal.Project` is not called at all: it re-reads the tree on every call, never validates it, and gates only when it reads; its two banners are not carried, since one embeds a terminal command and both derive from facts the observation holds; this remains a wording deviation from the `g1-s2` row, recorded for the planner.

#### The freshness loop

`Run` is the `g1-s3` tick's `FetchAdvance` half, and the server owns it. `cmd/metasystem/ui.go` starts it once in the `serve` case, as one goroutine on the same context `lifecycle.Serve` takes (`ui.go:123`, `:130`), with `goal.FetchAdvance` and `WallTimers{}`, and waits for it to return after `Serve` returns, so a tick in flight finishes its CAS and its `CleanupRefs` before the process exits. Why it is acceptable where `fetchFirst` is not: `Project(e, true, now)` moves a ref on the way to answering a read, so the answer and the move are one act and a caller cannot have one without the other; here the request path answers from the ref as it stands and moves nothing (obligation O1), and the ref moves only in this goroutine, on a schedule, under the engine's own gates. The loop is not triggered by a request: a request sets the cadence and nothing else.

The tick, in the loop's goroutine: under the mutex `Outcome = running`, `StartedAt = now`; then, outside it, `e, err := goal.ResolveEndpoint(h.root)`, fresh every tick because configuration is read per observation (M4), and `fetch(e)`; then under the mutex `FinishedAt`, and `advanced` (`Advanced` true: `Tip`, `Detail`), `current` (`Advanced` false, `Detail` "already at the canonical tip"), or `failed` (`Message = err.Error()`, `Failures++`; `Failures = 0` on either success); then `NextAt` by the rule. Nothing else is written: the next `Observe` reads the ref as it always does, and a new tip is a new cache key, so there is nothing to invalidate. The tick never holds the mutex around git.

The rule. Constants: `connectedInterval` 5 s, `idleInterval` 30 s, `connectedWindow` 30 s, `backoffCap` 5 min. `connected(t)` is `t − lastObserve ≤ connectedWindow`; `interval(t)` is the connected or idle interval accordingly; `wait(t) = min(interval(t) × 2^min(Failures, 10), backoffCap)`. After a tick ending at `t`, `next = t + wait(t)`; on an `Observe` at `now`, `next = min(next, now + wait(now with connected true))`, so a request can pull an idle deadline in to five seconds but never below the backoff's wait and never to "now"; before the first tick `next` is `Run`'s start, so the first tick runs at once. `nextDue` is one pure function both callers use, and `Cadence` reports which interval applied.

The loop body: `timer := timers.NewTimer(until next)`; `select` on `timer.C()` (stop the timer, run the tick, re-arm), on `wake` (stop the timer, re-arm at `h.next`), and on `ctx.Done()` (stop the timer, write `NextAt` zero, return). The tick runs inline in this goroutine, so a second tick cannot start while one is in flight; a wake that arrives during a tick sits in the buffered channel and the deadline after the tick is computed from `lastObserve`, so a request during a tick still counts for the cadence. The manual refresh action is the pane's Refresh: it re-observes, marks the browser connected, and the pane shows when the next tick is due; it starts nothing.

Known limit, stated not solved: `FetchAdvance` calls the unbounded `CaptureTip` (`fetchadvance.go:35`); a transport that hangs holds the loop, which the pane shows as `running` since `StartedAt`. `CaptureTipBounded` (`attention.go:627`) exists for the steward; a bounded advance is `g1-s3`'s remainder or the planner's, not invented here. What the loop never does: run on a request goroutine; make a request wait; touch HEAD, the working tree, `refs/remotes/*`, or any ref but `refs/metasystem/goals/accepted` and its own `refs/metasystem/goals/fetch/<opid>`; move the accepted ref backward (`advanceAcceptedForward`, `txn.go:422` to `:449`); move it at all when `SyncModeGate`, `AcceptanceGates`, or `ValidateCommit` refuses; write a log line, since the payload carries every outcome and the journal status is `g1-s3`'s.

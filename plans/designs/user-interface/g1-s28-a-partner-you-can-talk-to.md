## Outcome

A human opens the drawer and talks with the Project Partner about the project and about what is on the page: "why is this goal waiting?", "summarise the doctrine", "what did the last three decisions decide?". The Partner reads the same checkout the pages read, remembers the conversation across page loads and server restarts, answers as it thinks, and can be stopped mid-answer. It does not write and it does not act: those come as proposals in the sheets that exist, in step 2. Which agent is the Partner is one setting, and adding an agent is one file.

## The seam is ACP, and nothing else

The Agent Client Protocol is the shape the master design names, and every runtime speaks it as a server over stdio: Devin natively (`devin acp`), Claude Code through the `claude-code-acp` adapter, Codex through the `codex-acp` adapter (one package each; the builder pins the current package names and versions). The interface has **one** client, the kit's own `internal/acp`, and a runtime is a command that starts an ACP server *plus the configuration that makes it read-only*. Step 1 admits exactly the three; a runtime the seat has not admitted is refused, because a command alone cannot certify what a server will do (Astra, outside step 1).

**The host.** The kit's client is single-turn today: a prompt exhausts the session, a repeated run re-initialises, and a cancel abandons the connection (`internal/acp/driver.go`, `turn.go`). Step 1 builds the many-turn host the master design's integration table names, `internal/ui/partner`, on `acp.Conn`: initialise once; open one session in the checkout and keep it; service updates and requests for the life of the process; settle a cancellation before admitting the next turn; select the configured model at session setup and refuse the turn when the server cannot select it; own the process's teardown and recovery. Server-side timers are fine here.

**Read-only is enforced below the protocol, and the protocol is the backstop.** Each admitted runtime is started in the configuration that forbids writes and command execution at its own level (the builder names it per runtime from the adapter's documented options and proves it by asking the running server to edit a file and to run a command, both refused without a request reaching the client); a runtime whose configuration cannot establish that is not admitted. The same configuration disables the runtime's external tools, MCP servers and network access, and no approval inherited from the seat's own settings or from an earlier session can bypass any of it: forbidding writes and commands alone does not establish "no network". At the permission point the client refuses every request it cannot classify as a read of a path inside the checkout; a refusal is shown as an activity line. The Partner therefore has no shell and no network.

**An agent request can never become a human act.** Today an act without a session cookie is admitted under the terminal's boot proof, and a local process can send such a request. From this slice on, the act routes accept a cookie-less request only while no Partner runtime is configured; with one configured, every act needs a signed-in session, and a cookie-less act answers 403 with `signIn`. The Partner's process is started with no cookie, no session and no way to obtain one; the human's name in its context is attribution, never authority.

Settings: `ui.partner.runtime` (`claude` | `codex` | `devin`, default `claude`), `ui.partner.model` (default by runtime: `claude-opus-5-5`, `gpt-6-sol`, Devin's own), `ui.partner.command.<runtime>` (defaults to the adapter's binary name). A command that is not installed, or a server that refuses to initialise or is not signed in, yields one message in the drawer with the server's own words and, for the two adapters, the line that installs them; the human's question is kept in the composer. The interface never installs anything itself.

## The conversation

One conversation per human per checkout (the session's human, else the boot proof's, else the configured one, else the seat), owned by one conversation owner on the server that decides turn identity, admission, busy state, partial text and the terminal outcome. Kept under `artifacts/agents/ui/partner/`: the transcript as one JSON line per message (`id, role, text, at, outcome: complete | stopped | failed | refused, activity[]`, and for a human's message the page context it was asked from: section, subject id, displayed revision) and the live session's id.

**Turns.** One at a time. A send carries a client-minted turn key; the server answers 202 with the turn once, and the same key again answers the same turn, so a retry after a lost answer never submits twice; a second send while busy answers 409 and the draft stays. Sending clears the draft on 202 and keeps it on any refusal. Stop cancels through the protocol and waits for the cancellation to settle; the partial text is kept, marked stopped. A process that dies mid-turn marks the turn failed with the runtime's words. A reload re-reads the conversation's snapshot, the transcript and the current turn's partial text, so the page never guesses whether a question was accepted or an answer complete.

**Memory.** The live session carries the conversation for as long as its process lives, whether or not the server can load sessions; the process idles for at most an hour. After a process loss, the next turn opens a fresh session and supplies the last twenty messages, each with its speaker and, for the human's, the page context it was asked from, as a "Conversation so far" block bounded at 8,000 characters, so an earlier "this goal" keeps the goal it meant, and says so in an activity line that names how many messages it gave; native session loading is deferred.

**What the Partner is told.** Every turn carries a structured context the server composes, not the page's label: the standing rule (it reads and explains; it does not write; it says when it cannot see something); where the human is (section, path, tab, filters); the subject's identity (a goal id or a document id with its title); the displayed revision (the accepted tip the page shows and its observation time, or the document's revision); and a bounded snapshot of the displayed facts from the server's own readers (a goal's row as the board shows it, a document's head and headings), marked as "what the human sees now", distinct from anything the Partner reads afterwards. Human name: attribution only.

**Delivery.** The page's one event stream carries Partner events as their own event type with no `id:` field, so `Last-Event-ID` stays the notifications journal's cursor and a reconnect replays notifications only; Partner text never becomes a toast. On every reconnect the page re-reads the conversation's snapshot and joins live events to it by turn id and sequence, dropping duplicates. The drawer and the focused page share one conversation state and one draft.

**The page.** The drawer's panel and the focused page render the transcript, the answer streaming in as plain paragraphs and, when complete, rendered through the reader's own inert Markdown renderer; a muted activity line while the Partner works; a Stop control in the composer's place while a turn runs. The "unavailable" chip goes.

## Built, 2026-09-23

Commit `52f714a69`. Two things the build settled that the text above did not: the Codex and Devin adapters' own read-only presets still let the session write the checkout without asking, so every runtime is started inside the operating system's sandbox with file writes under the checkout denied (`internal/ui/partner/confine.go`); where no such sandbox exists, Codex and Devin are refused by name and Claude, whose adapter keeps the contract itself, is still admitted. And `ui.partner.runtime` defaults to empty, not `claude`: a configured Partner requires a signed-in human for every act, and that must be a seat's own choice. The adapters are `@agentclientprotocol/claude-agent-acp` and `@agentclientprotocol/codex-acp`, the successors of the packages named above.

## Later, when it hurts

- Proposals: the Partner fills a sheet the human confirms, through the shared operations, with its authorship recorded and never the human's authority.
- The MCP endpoint of bounded tools, and the ACP host in the seat's process, so a sitting can carry a Partner with write tools under the brain's fences.
- "Discuss this" from a card, a row or a selection; sharing an unsaved edit as draft context.
- Native session loading across the server's own restart; usage and cost on the page from the turn's end; more than one human.
- Runtimes beyond the three, each admitted with its own read-only configuration named.

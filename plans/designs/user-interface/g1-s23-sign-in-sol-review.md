# Sol's code review of g1-s23 sign-in, commits 563ce1673 and 30f0e84e6

Produced 2026-09-22 by Codex on `gpt-5.6-sol`, read-only and static, against the master design's "Human acts from the browser" ([user-interface-design.md](../user-interface-design.md)). Verbatim; the dispositions are in [g1-s23-sign-in-with-your-code.md](g1-s23-sign-in-with-your-code.md).

I found six material issues, including two direct authority-boundary failures.

1. **Critical — the session bearer secret is recorded in History and audit files.** The cookie value is `signed.ID` ([httpd/session.go:135](../../../metasystem/internal/ui/httpd/session.go:135>)); that same ID becomes `Proof.ChannelRef` ([session/session.go:210](../../../metasystem/internal/ui/session/session.go:210>)), is written into goal History ([goal/approval.go:426](../../../metasystem/internal/goal/approval.go:426>)), and is serialized into the authority-proof artifact ([humanauthority/authority.go:991](../../../metasystem/internal/humanauthority/authority.go:991>)). Direct requests without `Origin` or Fetch Metadata are allowed ([httpd/httpd.go:448](../../../metasystem/internal/ui/httpd/httpd.go:448>)). Failure scenario: after one human approval, a brain/local process reads `channelRef` from the ledger or proof artifact and sends `Cookie: ms_session=<channelRef>` to perform another act while the session remains live. That request was never a human browser action.

2. **High — an arbitrary request body can choose the “verified” human principal.** `POST /api/session/sign-in` accepts `human` and passes it directly into `SignIn` ([httpd/session.go:115](../../../metasystem/internal/ui/httpd/session.go:115>)); when the server has no known human, `handle` accepts that supplied one-word label ([session/session.go:329](../../../metasystem/internal/ui/session/session.go:329>)), mints the proof with it, and later places it in `Actor.Human` ([act/act.go:380](../../../metasystem/internal/ui/act/act.go:380>)). Failure scenario: on an unconfigured seat, a valid-code request with `"human":"Alice"` creates authority and History attributed to Alice without the sign-in system verifying that identity. Additionally, `act.SignedIn` checks neither its human nor session ID against the proof’s `ChannelUser`/`ChannelRef` ([act/act.go:134](../../../metasystem/internal/ui/act/act.go:134>)).

3. **High — session authority is a browser-specific verb allowlist, not full human standing.** `AuthorizesSetObligation` and `AuthorizesResume` omit session proofs ([humanauthority/authority.go:221](../../../metasystem/internal/humanauthority/authority.go:221>), [authority.go:235](../../../metasystem/internal/humanauthority/authority.go:235>)); carry, abandon, split ratification, reopening abandoned work, and session stop still require terminal-specific proof. The implementation test explicitly requires session proofs to fail resume and obligation authorization ([humanauthority/session_test.go:37](../../../metasystem/internal/humanauthority/session_test.go:37>)). Failure scenario: a signed-in human can approve or reorder work but cannot resume a breach-stopped goal or set its obligation, contrary to the same-standing design.

4. **High — the replay floor fails open on storage errors or corruption.** `Persist` cannot return an error ([session/session.go:108](../../../metasystem/internal/ui/session/session.go:108>)); the production callback discards both durable-floor and status-record errors ([cmd/metasystem/ui.go:233](../../../metasystem/cmd/metasystem/ui.go:233>)). Unreadable or unknown-schema `sessions.json` silently becomes floor zero ([lifecycle/sessions.go:43](../../../metasystem/internal/ui/lifecycle/sessions.go:43>)), and a test endorses that behavior ([session_record_test.go:115](../../../metasystem/internal/ui/lifecycle/session_record_test.go:115>)). Failure scenario: disk-full/read-only storage causes sign-in to return a valid cookie without persisting the step; restart within the TOTP acceptance window permits the same code again. Normal same-state-root servers are serialized by `server.flock` ([lifecycle/serve.go:118](../../../metasystem/internal/ui/lifecycle/serve.go:118>)), but different state roots using the same seat secret have independent floors and can both accept the code.

5. **High — most admitted session acts do not record their session source in History.** Unapprove still calls `recordApprovalRelay`, which is a no-op for sessions ([goal/approval.go:654](../../../metasystem/internal/goal/approval.go:654>)); set-priority drops the proof before constructing its mutation ([goal/order.go:72](../../../metasystem/internal/goal/order.go:72>)); grant/revoke root events likewise record only the actor ([goal/verbs.go:1575](../../../metasystem/internal/goal/verbs.go:1575>)). The unapprove test explicitly asserts that session facts remain absent ([goal/session_authority_test.go:139](../../../metasystem/internal/goal/session_authority_test.go:139>)). Failure scenario: an auditor cannot tell whether a withdrawal, priority change, grant, revoke, or ordinary browser open came from terminal ancestry or a browser session.

6. **Medium — the promised unambiguous identity extension was replaced with a one-word restriction.** Terminal enrollment preserves names containing spaces ([humanauthority/authority.go:823](../../../metasystem/internal/humanauthority/authority.go:823>)), while session proofs reject whitespace and store handling demands one word ([humanauthority/authority.go:285](../../../metasystem/internal/humanauthority/authority.go:285>), [session/session.go:332](../../../metasystem/internal/ui/session/session.go:332>)). Failure scenario: `ui.human=Jane Doe` or a matching enrolled name cannot sign in, while two seats using the same short handle remain indistinguishable. The test asserts this restrictive behavior rather than encoded identity.

Other requested checks:

- I found no current-tree reader, validator, narrator, backlog projection, or fetch path that rejects `authority=session` or `SIGNED_IN_SESSION`. The parser, renderer, approval validator, attention logic, and refusal register were updated.
- No new History key is written: the implementation reuses `authorityOutcome`, `channelProvider`, `channelUser`, and `channelRef`.
- Changing the two writers from `recordApprovalRelay` to `recordApprovalProof` does not change proven or relayed behavior: relayed proofs immediately delegate to the old helper, while proven proofs remain a no-op ([goal/approval.go:411](../../../metasystem/internal/goal/approval.go:411>)).
- Expiry and sign-out are enforced server-side: expired sessions are deleted before an act, and sign-out removes the store entry and clears the cookie. The cookie has `HttpOnly`, `SameSite=Strict`, `Path=/`, and `Expires`; it lacks `Secure` and, like all cookies, is host-scoped rather than port-scoped.
- The tests asserting the wrong contract are the resume/obligation refusal, absent unapprove provenance, unreadable-floor fail-open, and one-word/client-supplied identity tests. The “other session” constructor case also supplies the same session ID rather than testing a mismatch ([act/session_test.go:80](../../../metasystem/internal/ui/act/session_test.go:80>)).

Static review only; no tests or suites were run, no files were changed, and `metasystem.conf.local` was never opened.
